1. Images as tensors, and why dense nets fail

To a computer an image is a box of numbers. A grayscale photo is a matrix of height H and width W, each entry a brightness from 0 (black) to 255 (white), or 0.0 to 1.0 after scaling. A color photo has three such matrices, one each for red, green and blue: a tensor of shape H × W × C with C = 3 channels. PyTorch stores it channels-first, (C, H, W), and a mini-batch of images is (B, C, H, W). Every shape error you will ever get in a vision model is one of these four axes in the wrong place.

Explain it like I'm 9

A dense network looks at a picture the way you would read a 150,000-digit phone number: every digit in its own slot, and if you shift the whole thing one slot over, it is a completely different number to you. A convolutional network looks at a picture the way you actually look at one: with a small magnifying glass that you slide across it, asking the same question at every spot — "is there an edge here? a corner? an eye?" — so a cat in the corner and a cat in the middle both count as cats.

Two properties make the "magnifying glass" idea work. Locality: nearby pixels are related, far ones mostly are not, so a unit should look at a small neighbourhood. Translation equivariance: a feature detector that is useful at one location is useful at every location, so its weights should be shared across positions. A layer built on these two assumptions has thousands of weights instead of millions, and it generalizes from a cat in the corner to a cat anywhere without ever having seen one there.

2. The convolution operation

A convolution slides a small matrix of weights, the kernel (or filter), across the image. At each position it multiplies the kernel elementwise with the patch of pixels underneath, sums the products, and writes one number into the output. The output is a new image, a feature map, whose value at each location says "how strongly does this patch look like the kernel's pattern?" Here is a complete worked example with a 5×5 input and a 3×3 kernel.

The math (optional): the 2-D cross-correlation that deep learning calls "convolution"
out[i, j] = b + Σc Σu=0k−1 Σv=0k−1 K[c, u, v] · X[c, i·s + u, j·s + v]

X is the input with channels c; K is one kernel of size k×k per input channel; s is the stride (1 in the figure); b is the filter's bias; the sums run over every channel and every kernel position, and the result is one output pixel at (i, j). Strictly this is cross-correlation (a true convolution flips the kernel first), but since the kernel is learned the flip is irrelevant, and every framework uses this form. Each output pixel is a dot product between the kernel and the patch beneath it: convolution is pattern matching by dot product.

Kernels are pattern detectors

Before deep learning, image processing used hand-designed kernels for decades, and they show what a kernel means. A kernel of −1s on the left and +1s on the right responds only where brightness changes from left to right: a vertical edge detector. A kernel of all 1/9 replaces every pixel with its neighbourhood average: a blur. A center-heavy kernel with negative neighbours exaggerates differences: sharpening. The identity kernel (a 1 in the middle, 0 elsewhere) leaves the image alone. A CNN's first layer learns a few dozen such kernels from data, and they turn out to look very much like these.

Key idea

A convolution layer is a bank of small, learned pattern detectors, each applied everywhere. Its weights are the kernels; its output is one feature map per kernel saying where in the image that pattern occurs. Everything else in a CNN is plumbing around this idea.

Deep dive: convolution as a sparse, weight-sharing matrix 10 min

Chapter 15 taught you that a layer is a matrix multiply followed by a nonlinearity. A convolution layer is not an exception to that rule; it is a matrix multiply with two constraints on the matrix. Seeing the matrix explicitly explains equivariance, parameter counts, transposed convolutions and why GPUs compute convolutions the way they do.

Explain it like I'm 9

A dense layer is a classroom where every student (output) is allowed to listen to every pixel and has their own private opinion about each one. A convolution is a classroom where each student may only listen to the four pixels in front of them, and — this is the strict part — all students must use the same four opinions. Fewer opinions to learn, and a student sitting one seat to the right hears exactly what their neighbour would hear if the picture slid one pixel over.

Take the smallest case that shows everything: a 3×3 image x with pixels x1…x9 and a 2×2 kernel with weights a, b, c, d. The valid output is 2×2, four numbers. Each one is a dot product of the kernel with a patch: y1 = a·x1 + b·x2 + c·x4 + d·x5. Written as a matrix acting on the flattened image, the layer is 4×9, and Figure 17.11 shows what it looks like.

The math (optional): the convolution matrix
y = M·vec(x), M ∈ ℝ(H′W′)×(HW), M[(i, j), (i+u, j+v)] = K[u, v] for 0 ≤ u, v < k, and 0 elsewhere

vec(x) is the image flattened row by row into a vector of length H·W; y is the flattened output of length H′·W′; the row index (i, j) is one output position and the column index (i+u, j+v) is one of the k² input pixels under it; K[u, v] is the kernel weight. Every row has exactly k² nonzero entries (locality) drawn from the same k² numbers (weight sharing). A dense layer with the same input and output sizes would have H′W′·HW free entries: 36 here, 50,176 × 50,176 ≈ 2.5 billion for a single 224×224 map computed from a 224×224 one.

Three things fall out of the picture. Equivariance is visible: row y2 is row y1 shifted one column to the right, so a shifted input produces a shifted output. The backward pass is also a convolution: autograd multiplies the upstream gradient by MT, and the transpose of this banded matrix is itself a convolution with the flipped kernel, spreading each output's gradient back over the patch it came from; that is exactly the operation nn.ConvTranspose2d performs, which is why decoders and U-Nets (§9) use it to grow images. Hardware: nobody builds M in memory (it is almost all zeros); instead the "im2col" trick unfolds the image into a patches-by-pixels matrix so that the whole layer becomes one dense matrix multiply of patches against kernels, which is what a GPU is fastest at. A 1×1 convolution is the degenerate case where each "patch" is a single pixel's channel vector, so the layer is literally a per-pixel dense layer across channels.

# A convolution IS a matrix multiply: build the (sparse, weight-sharing) matrix explicitly
import torch, torch.nn.functional as F
x = torch.arange(1.0, 10.0).view(1, 1, 3, 3)          # 3x3 input, values 1..9
k = torch.tensor([[1.0, 2.0], [3.0, 4.0]]).view(1, 1, 2, 2)   # 2x2 kernel a=1 b=2 c=3 d=4
conv = F.conv2d(x, k)                                  # valid conv -> 2x2 output
print("conv2d output:\n", conv[0, 0])

# The same map as a 4x9 matrix acting on the flattened 3x3 input
M = torch.zeros(4, 9)
for oi in range(2):                                    # output row
    for oj in range(2):                                # output col
        for u in range(2):                             # kernel row
            for v in range(2):                         # kernel col
                M[oi * 2 + oj, (oi + u) * 3 + (oj + v)] = k[0, 0, u, v]
print("matrix M (4 outputs x 9 inputs):\n", M)
print("M @ x.flatten() =", (M @ x.flatten()).view(2, 2))
print("same answer:", torch.allclose(M @ x.flatten(), conv.flatten()))
print(f"nonzero entries: {int((M != 0).sum())} of {M.numel()}, distinct values: {len(set(M[M != 0].tolist()))}")
# conv2d output:
#  tensor([[37., 47.],
#         [67., 77.]])
# matrix M (4 outputs x 9 inputs):
#  tensor([[1., 2., 0., 3., 4., 0., 0., 0., 0.],
#         [0., 1., 2., 0., 3., 4., 0., 0., 0.],
#         [0., 0., 0., 1., 2., 0., 3., 4., 0.],
#         [0., 0., 0., 0., 1., 2., 0., 3., 4.]])
# M @ x.flatten() = tensor([[37., 47.],
#         [67., 77.]])
# same answer: True
# nonzero entries: 16 of 36, distinct values: 4
Key idea

Convolution = a linear layer with locality and weight sharing imposed on the matrix. That is why it needs so few parameters, why it generalizes across positions, and why everything you know about linear layers (backprop, initialization, matrix multiply on GPUs) applies to it unchanged.

3. Padding, stride, dilation, channels

Three knobs control the geometry of a convolution, and one formula tells you what comes out.

  • Padding p: add p rows/columns of zeros around the input. Without it, every 3×3 layer shrinks the image by 2 and edge pixels are seen fewer times than central ones. padding=1 with a 3×3 kernel ("same" padding) keeps the size unchanged, which is what nearly every modern architecture does.
  • Stride s: move the kernel s pixels at a time instead of 1. Stride 2 halves the output size and is a cheap way to downsample (many modern nets use stride-2 convolutions instead of pooling).
  • Dilation d: insert gaps of d−1 pixels between kernel taps, so a 3×3 kernel with d = 2 covers a 5×5 area with 9 weights. It grows the receptive field without extra parameters; used in segmentation and audio (WaveNet).
The math (optional): the output-size formula
nout = ⌊ (nin + 2p − d·(k − 1) − 1) / s ⌋ + 1

nin is the input height (or width, computed separately); p the padding on each side; k the kernel size; d the dilation; s the stride; ⌊·⌋ rounds down. With d = 1 the effective kernel size is k, and the formula reads: the padded length minus the kernel, divided by the step, plus one for the starting position. Sanity checks: 28, k = 3, p = 1, s = 1 → 28 (same); 28, k = 2, s = 2 → 14 (a 2×2 pool halves); 224, k = 7, p = 3, s = 2 → 112 (ResNet's first layer). Pooling layers obey the same formula.

# The output-size formula, as a function you will reuse constantly
def conv_out(n, k, s=1, p=0, d=1):
    """Spatial size after a conv/pool layer.
    n: input size, k: kernel, s: stride, p: padding (each side), d: dilation."""
    return (n + 2 * p - d * (k - 1) - 1) // s + 1

print("28, k3, s1, p0 ->", conv_out(28, 3))            # shrinks by 2
print("28, k3, s1, p1 ->", conv_out(28, 3, p=1))       # 'same' padding
print("28, k2 pool s2  ->", conv_out(28, 2, s=2))      # halves
print("224, k7, s2, p3 ->", conv_out(224, 7, s=2, p=3)) # ResNet stem
print("32, k3, s1, d2  ->", conv_out(32, 3, d=2))      # dilation: acts like k=5
# 28, k3, s1, p0 -> 26
# 28, k3, s1, p1 -> 28
# 28, k2 pool s2  -> 14
# 224, k7, s2, p3 -> 112
# 32, k3, s1, d2  -> 28

# Chain a whole network: three conv(3, pad 1)+pool(2) blocks on a 28x28 image
n = 28
for block in range(1, 4):
    n = conv_out(n, 3, p=1)     # conv keeps size
    n = conv_out(n, 2, s=2)     # pool halves
    print(f"after block {block}: {n}x{n}")
# after block 1: 14x14
# after block 2: 7x7
# after block 3: 3x3

Multiple channels and multiple filters

Real inputs have channels: 3 for RGB, or 64 feature maps coming out of a previous layer. A kernel therefore is not k×k but Cin×k×k: it has a separate k×k slice for every input channel, and the products across all slices are summed into one output map. A layer has Cout such kernels (filters), producing Cout output maps, which stack into the next layer's input. So a conv layer maps a Cin×H×W volume to a Cout×H′×W′ volume, and its weight tensor is Cout×Cin×k×k.

The math (optional): counting parameters, worked
params = Cout · Cin · k · k + Cout

First conv of the network in §5: Cin = 1 (grayscale), k = 3, Cout = 16 → 16·1·9 + 16 = 160. Second conv: 32·16·9 + 32 = 4,640. Third: 64·32·9 + 64 = 18,496. Compare a single dense layer from a flattened 28×28 image to 128 units: 784·128 + 128 = 100,480. The three conv layers together have a quarter of that and see the whole image at every position. Note that k = 3 everywhere: two stacked 3×3 layers see a 5×5 area with 18 weights per channel pair instead of 25, and get an extra nonlinearity for free; that observation is the whole design of VGG.

Common mistake

Confusing the number of channels with the number of parameters, or with the image size. A 64-channel layer on a 512×512 image has the same weights as on a 32×32 image; what changes is the activation memory (64×512×512 floats per image ≈ 64 MB in float32) and the compute. When a model runs out of GPU memory, the cure is smaller images or smaller batches, not fewer parameters.

4. Pooling and receptive fields

After a convolution has said where a pattern occurs, the exact pixel does not matter much: an edge at column 40 or 41 is the same edge. Pooling summarizes each small window (usually 2×2) with a single number, either its maximum (max pooling, keeps the strongest response) or its average. It has no parameters, halves the height and width, cuts the compute of everything downstream by four, and buys a little translation invariance. Modern networks often replace it with stride-2 convolutions, which do the same downsampling with learned weights, but the purpose is identical: make the representation smaller and coarser as it becomes more abstract.

Global average pooling (GAP) is the extreme version used at the very end: average each final feature map over all its positions, leaving one number per channel. A 64×7×7 tensor becomes a 64-vector regardless of the input image size, and that vector feeds the classifier. It replaced the giant flatten-then-dense layers of early CNNs (which held about 96% of AlexNet's 61 M parameters), and it lets the same network run on any image size.

Receptive fields grow with depth

A unit in the first 3×3 layer sees 3×3 pixels. A unit in the second layer sees a 3×3 patch of first-layer units, which together cover 5×5 pixels. After a 2×2 pool, every step in the next layer is worth two pixels, so the receptive field grows twice as fast. Ten layers and a few pools later, a single unit sees the entire image. That growth is why depth matters in vision: only deep units can respond to whole objects, and they can only do so by composing the smaller parts detected below them.

Explain it like I'm 9

Building a Lego castle: first you snap two bricks together (an edge). Then you snap a few of those into a wall piece (a texture). Then walls into a tower (a part). Then towers into the castle (the object). Nobody looks at every brick when deciding "is this a castle?"; they look at the towers. A deep CNN builds the castle level by level, and the top level only needs to look at a few big pieces.

Deep dive: receptive-field arithmetic 8 min

Figure 17.5 shows receptive fields growing; here is how to compute them exactly for any stack of convolutions and pools, why the answer matters for choosing an architecture, and the caveat that the theoretical number overstates what the network actually uses.

Explain it like I'm 9

Two numbers describe each layer. How wide a window one unit sees on the original picture (the receptive field), and how far apart two neighbouring units' windows are on the original picture (the jump). A convolution widens the window; a stride or pool makes the jump bigger, and every later widening is measured in jumps, so everything after a pool grows faster.

The math (optional): the recursion
rl = rl−1 + (kl − 1) · dl · jl−1 jl = jl−1 · sl r0 = 1, j0 = 1

rl is the receptive field after layer l, in input pixels; jl is the jump: the distance, in input pixels, between the centres of two adjacent units of layer l; kl, sl and dl are that layer's kernel size, stride and dilation. A layer with kernel k reaches (k − 1) units further in each direction than one unit alone, and each of those units is jl−1 input pixels from the next; stride multiplies the jump; padding changes nothing here (it only shifts where the window sits). Pooling layers use the same rule with their own k and s.

Apply it to the stack in Figure 17.5: conv 3 → r = 3, j = 1; pool 2 (stride 2) → r = 3 + 1·1 = 4, j = 2; conv 3 → r = 4 + 2·2 = 8; conv 3 → r = 8 + 2·2 = 12. The pool added only one pixel itself, but it doubled the jump, so each later 3×3 layer adds four pixels instead of two. Two more useful cases are in the code: the SmallCNN of §5 ends with a receptive field of 18 pixels on a 28-pixel image — no single unit in its last layer sees the whole digit, and it is the global average pool that fuses the positions — and the ResNet-18 stem (7×7 stride 2, then 3×3 max-pool stride 2) starts at 11 pixels with a jump of 4 before a single residual block has run.

# Receptive-field arithmetic: r grows by (k-1)*jump each layer; jump multiplies by stride
def receptive_fields(layers):
    r, j = 1, 1                                # a pixel sees 1 pixel; step between neighbours = 1
    print(f"{'layer':16s} {'k':>2} {'s':>2} {'RF':>4} {'jump':>5}")
    for name, k, s in layers:
        r, j = r + (k - 1) * j, j * s
        print(f"{name:16s} {k:2d} {s:2d} {r:4d} {j:5d}")
    return r

receptive_fields([("conv3", 3, 1), ("pool2", 2, 2), ("conv3", 3, 1), ("conv3", 3, 1)])
print("\nSmallCNN (§5):")
receptive_fields([("conv3", 3, 1), ("pool2", 2, 2), ("conv3", 3, 1), ("pool2", 2, 2), ("conv3", 3, 1)])
print("\nResNet-18 stem + stage 1:")
receptive_fields([("conv7 s2", 7, 2), ("maxpool3 s2", 3, 2)] + [("conv3", 3, 1)] * 4)

Why you care. If the objects that decide the label are 20 pixels across and your network's last layer sees 18, it cannot represent them as a whole; add depth, a pool, or dilation. Conversely, a network whose receptive field vastly exceeds the image wastes the deep layers; a full ResNet-50 reaches a theoretical receptive field of 483 pixels on a 224-pixel input. That "theoretical" qualifier matters: Luo et al. (2016) showed that the influence of input pixels on a unit is roughly Gaussian, concentrated in the centre of the theoretical window, and the effective receptive field is often a third of it or less. So when small details matter (fine cracks, tiny lesions), do not trust the arithmetic alone — downsample less, use a larger input, or check empirically by measuring how much the output changes when you perturb pixels at various distances.

5. Anatomy of a CNN

Put the pieces together and a CNN is a repeated block: Conv → BatchNorm → ReLU, optionally followed by a pool. Each block keeps or halves the spatial size and usually doubles the channels, so the tensor gets shorter and wider as it flows: spatial detail is traded for semantic depth. After the last block, global average pooling produces a vector and a linear layer produces the logits (never a softmax inside the model; the loss does that, Chapter 16).

Here is that network in PyTorch, printing the shape at each stage on a random 1×28×28 image, plus the parameter count — check it against the figure.

# A small CNN that prints the tensor shape after every stage
import torch, torch.nn as nn

class SmallCNN(nn.Module):
    def __init__(self, n_classes=10):
        super().__init__()
        self.block1 = nn.Sequential(nn.Conv2d(1, 16, 3, padding=1), nn.BatchNorm2d(16), nn.ReLU(), nn.MaxPool2d(2))
        self.block2 = nn.Sequential(nn.Conv2d(16, 32, 3, padding=1), nn.BatchNorm2d(32), nn.ReLU(), nn.MaxPool2d(2))
        self.block3 = nn.Sequential(nn.Conv2d(32, 64, 3, padding=1), nn.BatchNorm2d(64), nn.ReLU())
        self.gap = nn.AdaptiveAvgPool2d(1)          # global average pooling -> (B, 64, 1, 1)
        self.head = nn.Linear(64, n_classes)        # logits, no softmax here

    def forward(self, x, verbose=False):
        for name, layer in [("block1", self.block1), ("block2", self.block2),
                            ("block3", self.block3), ("gap", self.gap)]:
            x = layer(x)
            if verbose: print(f"{name:7s} -> {tuple(x.shape)}")
        x = x.flatten(1)                            # (B, 64)
        if verbose: print(f"{'flatten':7s} -> {tuple(x.shape)}")
        return self.head(x)

net = SmallCNN()
x = torch.randn(1, 1, 28, 28)                       # one grayscale 28x28 image
logits = net(x, verbose=True)
print(f"{'logits':7s} -> {tuple(logits.shape)}")
# block1  -> (1, 16, 14, 14)
# block2  -> (1, 32, 7, 7)
# block3  -> (1, 64, 7, 7)
# gap     -> (1, 64, 1, 1)
# flatten -> (1, 64)
# logits  -> (1, 10)

n_params = sum(p.numel() for p in net.parameters())
print("total parameters:", n_params)
# Check the first conv by hand: 16 filters x (1 in-channel x 3 x 3) + 16 biases = 160
print("conv1 params:", sum(p.numel() for p in net.block1[0].parameters()))
# total parameters: 24170
# conv1 params: 160
At work

Print shapes. Every time you build or modify a CNN, run one random batch through it with a verbose forward like the one above before training anything. Off-by-one padding, a forgotten pool, a flatten in the wrong place: each shows up instantly as a wrong shape and costs an hour if you find it later through a bad accuracy number. torchinfo.summary(model, (1, 1, 28, 28)) does the same with parameter counts per layer.

Key idea

The design pattern of every CNN: stack conv → norm → activation blocks; halve the spatial size and double the channels every few blocks; finish with global average pooling and a linear head. Architectures differ in how the blocks are wired, not in this outline.

6. Landmark architectures

You do not need to memorize architectures, but you need to recognize their names and know the one idea each contributed, because those ideas are what you will choose between when picking a pretrained backbone.

ResNet and the skip connection

By 2015 the field had a puzzle: a 56-layer plain network trained worse than a 20-layer one, even on the training set. That cannot be overfitting (training error went up) and it is not vanishing gradients alone (batch norm was in use). The deeper network simply could not find the solution the shallower one found, even though it could represent it exactly by making the extra layers identity maps. The fix was to make identity the default: instead of asking a block to learn a mapping H(x), let it learn the difference F(x) = H(x) − x and add x back. If the best thing a block can do is nothing, it learns F = 0, which is easy. And gradients flow straight through the addition to earlier layers, undiminished.

Explain it like I'm 9

Imagine a long relay of editors improving a story. In a plain network each editor must rewrite the whole story from scratch, and if any one of them is having a bad day the story comes out worse than it went in. In a ResNet each editor only writes down changes on a sticky note attached to the original. An editor with nothing useful to add simply attaches a blank note, and the story passes through unharmed. Fifty editors can now be chained safely; the worst case is that nothing changes.

Inception, MobileNet, EfficientNet, and Vision Transformers

Inception asked "which kernel size?" and answered "all of them": each block runs 1×1, 3×3 and 5×5 convolutions in parallel and concatenates the maps, using cheap 1×1 convolutions to reduce channel counts first. A 1×1 convolution is a per-pixel linear layer across channels; it mixes channels without looking at neighbours and is the workhorse of every efficient architecture since.

MobileNet made convolution itself cheaper by splitting it into two steps: a depthwise convolution (one k×k kernel per input channel, no mixing across channels) followed by a pointwise 1×1 convolution (mix channels, no spatial extent). Together they approximate a full convolution at a fraction of the cost, which is what runs on your phone.

The math (optional): why depthwise-separable is cheap
full: Cin·Cout·k² separable: Cin·k² + Cin·Cout ratio ≈ 1/Cout + 1/k²

Per output pixel, a full convolution does Cin·Cout·k² multiply-adds (every filter reads every channel at every tap). The depthwise step does Cin·k² (one kernel per channel) and the pointwise step Cin·Cout. With k = 3 and Cout = 256, the ratio is about 1/256 + 1/9 ≈ 0.115: nearly 9× cheaper, at a small accuracy cost.

EfficientNet noticed that people scaled networks by making them deeper or wider or feeding larger images, and showed that scaling all three together with a single coefficient gives the best accuracy per unit of compute; its B0–B7 family lets you pick a size for your budget. Vision Transformers (ViT) drop convolution entirely: the image is cut into 16×16 patches, each patch is linearly projected to a vector, and a standard transformer (Chapter 18) attends across the patches. With little data ViTs underperform CNNs because they lack the built-in locality bias; with large-scale pretraining they match or beat them, and most of today's foundation vision models (CLIP, DINOv2, SAM) are ViTs. For a practitioner the difference matters less than it sounds: both come as pretrained backbones you fine-tune the same way.

At work: which backbone?

Default to ResNet-50 or EfficientNet-B0/B3 from torchvision or the timm library with ImageNet weights: well understood, fast, and easy to fine-tune on a laptop GPU. Reach for a ViT (e.g. DINOv2) when you have a strong GPU, want the best possible features with few labels, or need embeddings for similarity search. Use MobileNet or EfficientNet-Lite when the model must run on a phone or an edge camera. Benchmarks between top backbones differ by a percent or two; your data and labels will move results by ten.

Deep dive: why residual connections fix optimization 10 min

§6 said that a residual block makes identity "the easy default" and lets gradients "pass through undiminished". Both claims have a precise form, and once you see it you will also understand why every transformer (Chapter 18) is built from residual blocks and why removing a skip connection breaks training.

Explain it like I'm 9

Pass a message through 30 people, each of whom must repeat the whole thing from memory. Each person garbles it a little, and by the end nothing is left. Now pass a written note and let each person add a sticky note. The original always arrives, and so do the corrections. Gradients are a message travelling backwards; skip connections are the written note.

The math (optional): the identity term in the gradient
xL = xl + Σi=lL−1 Fi(xi) ⇒ ∂ℒ/∂xl = ∂ℒ/∂xL · ( 1 + ∂/∂xl Σi=lL−1 Fi(xi) )
plain network: ∂ℒ/∂xl = ∂ℒ/∂xL · Πi=lL−1 Ji

xl is the input to block l and xL the output of the last block; Fi is the residual function (the two convolutions) of block i; ℒ is the loss; Ji = ∂xi+1/∂xi is the Jacobian of block i in a plain network. Unrolling the residual recursion xi+1 = xi + Fi(xi) gives the first line: any later activation is the early one plus a sum of residuals. Differentiating gives a gradient with two parts: the "1", a direct path from the loss to xl that no block can shrink, and a sum of block contributions. In a plain network the gradient is a product of Jacobians instead; if each has typical size 0.7, thirty of them multiply to 10−5, and if each is 1.4 they multiply to 10+4. A sum of terms cannot vanish or explode that way (He et al., 2016, "Identity mappings in deep residual networks").

The code makes this concrete: the same 32 blocks, wired plain or residual, at PyTorch's default initialization. Plain: the gradient reaching the input shrinks by orders of magnitude with every few blocks and is 10−19 at depth 32, so the early layers would never learn. Residual: it stays of order 10 at every depth.

# Gradient flow at initialization: plain stack vs residual stack, deeper and deeper
import torch, torch.nn as nn
torch.manual_seed(0)
width = 64
def block(): return nn.Sequential(nn.Linear(width, width), nn.ReLU(), nn.Linear(width, width))
blocks = [block() for _ in range(32)]              # same blocks reused in both stacks
x = torch.randn(16, width, requires_grad=True)

def grad_norm_at_input(depth, residual):
    h = x
    for b in blocks[:depth]:
        h = h + b(h) if residual else b(h)          # y = x + F(x)   vs   y = F(x)
    g, = torch.autograd.grad(h.sum(), x)            # how much signal reaches the input?
    return g.norm().item()

print("depth   plain |grad|   residual |grad|")
for depth in (1, 4, 8, 16, 32):
    print(f"{depth:5d}   {grad_norm_at_input(depth, False):11.2e}   {grad_norm_at_input(depth, True):14.2e}")
# depth   plain |grad|   residual |grad|
#     1      7.71e+00         3.29e+01
#     4      1.01e-01         3.56e+01
#     8      2.91e-04         3.66e+01
#    16      1.26e-09         4.84e+01
#    32      1.12e-19         7.31e+01

Two more things the identity view explains. First, why "deeper got worse" was an optimization problem: a plain 56-layer network could in principle imitate a 20-layer one by making 36 layers compute the identity, but a stack of conv → BN → ReLU has no easy way to represent identity (ReLU alone kills negative values), so the optimizer could not find it. With y = x + F(x), identity is F = 0: weights near zero, the easiest thing gradient descent with weight decay can do. Second, a residual network behaves like an ensemble of shallow paths (Veit et al., 2016): unrolling the sum produces 2n paths through n blocks, and the gradient is dominated by the short ones, which is why you can delete individual blocks from a trained ResNet with only a mild loss in accuracy, while deleting one layer of VGG destroys it.

At work

Three practical habits follow. Initialize each block so that F(x) ≈ 0 at the start — torchvision's resnet50(zero_init_residual=True) sets the last batch-norm γ of every block to zero, and training is a little faster and more stable for it. Never "simplify" an architecture by removing skip connections, whether a ResNet, a U-Net or a transformer. And when you add a block with a different output width, add a 1×1 convolution on the skip path (the "projection shortcut") rather than dropping the skip.

7. Data augmentation

Every image dataset is too small. The cheapest way to make it bigger is to apply label-preserving random transformations on the fly during training: a flipped cat is still a cat, a slightly rotated invoice is still an invoice, a darker photo of a cracked weld is still a cracked weld. Each epoch the network sees a different version of every image, so it cannot memorize pixels and must learn the invariances you have told it about. For small datasets augmentation is routinely worth 5–15 points of accuracy, more than any architecture choice.

Common mistake

Augmenting the validation set, or augmenting with transformations that change the label. The validation pipeline must be deterministic (resize, center crop, normalize) or your metric is noisy and optimistic. And every augmentation is a claim about the world: "orientation does not matter". For satellite images that claim is true and rotations help; for photos of documents it is false and rotations hurt. Think before you flip.

8. Transfer learning and fine-tuning

Here is the most important practical fact in this chapter: you will almost never train a CNN from scratch at work. Training ResNet-50 on ImageNet takes days of GPU time and 1.3 million labeled images. But the features it learns in its early and middle layers (Figure 17.5: edges, textures, parts) are the same features every other image task needs. So you take the pretrained network, throw away its final ImageNet classifier, put a fresh head on for your classes, and train that on your few hundred or few thousand images. This is transfer learning, and it regularly turns a hopeless 300-image problem into a 95%-accuracy model in an afternoon.

Explain it like I'm 9

Someone who already reads English can learn to read medical reports in a week: they don't have to relearn letters, words and grammar, only the new vocabulary. A pretrained network already "reads pixels": edges, shapes, textures, parts. You only teach it your vocabulary — which combinations of parts mean "defective", "approved", or "species 7".

The code below is the standard torchvision fine-tuning skeleton. It downloads pretrained weights the first time, so it is shown for reference rather than executed here; it is the template to copy at work.

# Transfer learning with torchvision (downloads pretrained weights: run this at work, not here)
import torch, torch.nn as nn
from torchvision import models, transforms, datasets
from torch.utils.data import DataLoader

# 1. Preprocessing MUST match what the backbone was trained with (ImageNet stats)
train_tf = transforms.Compose([
    transforms.RandomResizedCrop(224, scale=(0.6, 1.0)),
    transforms.RandomHorizontalFlip(),
    transforms.ColorJitter(0.2, 0.2, 0.2),
    transforms.ToTensor(),
    transforms.Normalize([0.485, 0.456, 0.406], [0.229, 0.224, 0.225])])
eval_tf = transforms.Compose([
    transforms.Resize(256), transforms.CenterCrop(224), transforms.ToTensor(),
    transforms.Normalize([0.485, 0.456, 0.406], [0.229, 0.224, 0.225])])

train_ds = datasets.ImageFolder("data/train", train_tf)   # folder-per-class layout
val_ds   = datasets.ImageFolder("data/val", eval_tf)
train_dl = DataLoader(train_ds, batch_size=32, shuffle=True, num_workers=4)
val_dl   = DataLoader(val_ds, batch_size=64)

# 2. Load the pretrained backbone and replace the head
model = models.resnet18(weights=models.ResNet18_Weights.DEFAULT)
for p in model.parameters():
    p.requires_grad = False                    # stage 1: freeze everything
model.fc = nn.Linear(model.fc.in_features, len(train_ds.classes))   # new head: trainable

device = "cuda" if torch.cuda.is_available() else "cpu"
model = model.to(device)
loss_fn = nn.CrossEntropyLoss()

def run_epochs(params, lr, epochs):
    opt = torch.optim.AdamW(params, lr=lr, weight_decay=1e-2)
    sched = torch.optim.lr_scheduler.CosineAnnealingLR(opt, T_max=epochs)
    for _ in range(epochs):
        model.train()
        for xb, yb in train_dl:
            xb, yb = xb.to(device), yb.to(device)
            loss = loss_fn(model(xb), yb)
            opt.zero_grad(); loss.backward(); opt.step()
        sched.step()

# stage 1: train only the head (fast, safe, works with a few hundred images)
run_epochs(model.fc.parameters(), lr=1e-3, epochs=5)

# stage 2: unfreeze the last block + head, fine-tune with a SMALL learning rate
for p in model.layer4.parameters():
    p.requires_grad = True
run_epochs([p for p in model.parameters() if p.requires_grad], lr=1e-4, epochs=10)

torch.save(model.state_dict(), "resnet18_finetuned.pt")
At work

Three details decide whether fine-tuning works. (1) Normalize with the backbone's statistics (ImageNet mean/std for torchvision models); wrong normalization silently costs several points. (2) Keep batch norm in eval mode when fine-tuning with small batches (model.train() then set BN layers back to .eval()), or the running statistics get corrupted by your tiny batches. (3) Fine-tune with a learning rate 10–100× smaller than from-scratch training and monitor validation loss from epoch one: fine-tuning overfits fast, and the best checkpoint is often at epoch 3–8.

Key idea

Pretrained backbone + new head + careful learning rates is the default vision workflow. Training from scratch is the exception, justified only by a huge dataset in a domain unlike anything the backbone has seen.

Deep dive: transfer-learning decision math 9 min

The table in §8 gives rules of thumb by data size. This deep dive gives the reasoning behind them — how accuracy scales with labels, how many parameters you are really fitting in each strategy, and a five-minute probe that tells you which row of the table you are in before you label anything else.

Explain it like I'm 9

Learning from examples is like filling a bucket with a hose whose flow keeps weakening: the first hundred examples do most of the work, the next hundred help less, and the thousandth barely moves the level. Knowing the shape of that curve tells you whether to label more pictures or to spend the money elsewhere.

The math (optional): learning curves and effective parameters
err(n) ≈ e∞ + b · n−α, α ≈ 0.3–0.5 for fine-tuning paramshead = D·C + C paramstop block ≈ 15 M (ResNet-50 layer4)

n is the number of labeled training images; err(n) the test error you get from them; e∞ the error floor set by label noise and the backbone; b a constant; α the learning-curve exponent: published measurements for image classification put it around 0.3–0.5 (Hestness et al., 2017), with training from scratch at the shallow end and fine-tuning a pretrained backbone typically at the steep end, and your own task will have its own value. Doubling n therefore multiplies the excess error (err − e∞) by 2−α ≈ 0.7–0.8: each doubling removes 20–30% of what is left. D is the backbone's feature dimension (2,048 for ResNet-50, 512 for ResNet-18) and C the number of classes: a linear head on frozen features for a 10-class problem has 20,490 parameters; unfreezing ResNet-50's last stage adds about 15 million; unfreezing everything, 25 million.

How many labels

Two consequences of the power law. First, the curve is steep early and flat late: from 50 to 100 images per class you might gain 8 points; from 5,000 to 10,000, one point. If a pilot with 100 images per class is at 85% and you need 95%, three more doublings buy you roughly half of the gap; the rest has to come from better labels, a better backbone or a narrower task. Measure your own α by training on 25%, 50% and 100% of what you have and plotting error against n on log–log axes: the slope is −α, and extrapolating it is the most honest estimate of "how much more data" you will ever get. Second, count per class, not in total: a 40-class problem with 400 images has 10 per class, which is few-shot territory where a frozen backbone with a nearest-neighbour or logistic-regression head usually beats any fine-tuning.

When to unfreeze

Compare the parameters you would fit with the labels you have. A 20,000-parameter head on 600 images is a well-posed problem (and with only 600 images, fit it with scikit-learn's logistic regression and cross-validated L2 rather than SGD — it is faster and better). Unfreezing 15 million parameters on 600 images is not, unless the learning rate is small enough that the weights barely move, which is exactly what the 10−4–10−5 stage-2 rates in Figure 17.9 achieve. Unfreeze when both of these hold: the frozen-head model has plateaued on validation, and its training accuracy is also unimpressive. A frozen head that fits the training set well but generalizes poorly needs data and augmentation, not more trainable weights; a frozen head that cannot even fit the training set is telling you the features are wrong for your domain, and that is what unfreezing fixes.

The five-minute probe

Before deciding anything, embed a few hundred labeled images with the frozen backbone and run a k-nearest-neighbour classifier (Chapter 11) on the embeddings with cross-validation. If kNN already scores 80% or more, the domain is close to the pretraining data: stay in the top rows of the table, and much of your accuracy will come from the head alone. If kNN is near chance, the domain is far (microscopy, radar, spectrograms): plan on unfreezing most of the network, look for a backbone pretrained on similar data, and budget for more labels. The probe costs no training and tells you which of the table's rows you are in.

Key idea

Labels have diminishing returns with a known exponent; trainable parameters must be paid for with labels or with a small learning rate. Estimate α from your own data, count parameters against images per class, and let a kNN probe on frozen embeddings decide how much of the backbone to touch.

9. Beyond classification: detection, segmentation, embeddings

"Vision" at work is rarely just "which class is this image?". The same backbones power four families of task, and choosing the right family is the first decision in any project.

The math (optional): intersection over union
IoU(A, B) = |A ∩ B| / |A ∪ B| = |A ∩ B| / (|A| + |B| − |A ∩ B|)

A is the predicted box, B the true box; |·| is area. IoU is 1 for a perfect box and 0 for no overlap. Detection metrics count a prediction as correct when its IoU with a true box of the same class exceeds a threshold, usually 0.5, and then compute precision/recall as in Chapter 6; mAP (mean average precision) averages the precision–recall curve's area over classes and IoU thresholds. Segmentation uses the same IoU per class, computed on pixels, often reported as mean IoU; the Dice coefficient 2|A∩B|/(|A|+|B|) is its close cousin and a common loss for small structures.

Detection predicts a set of boxes, each with a class and a confidence. The YOLO idea: divide the image into a grid, let each cell (or anchor) predict "is there an object centered here, what box, what class?", then keep the confident, non-overlapping ones. Modern detectors (YOLOv8+, DETR) are fast enough for video and come pretrained on COCO; you fine-tune them on a few hundred boxed images. Segmentation predicts a class per pixel; the U-Net design (an encoder that shrinks the image, a decoder that grows it back, with skip connections copying fine detail across) dominates medical and industrial work. Embeddings use the backbone's penultimate vector directly: with a backbone trained contrastively (CLIP, DINOv2), nearest-neighbour search over those vectors gives visual search, duplicate detection and few-shot classification with no training at all.

At work: pick the cheapest task that answers the question

"Is there damage?" is classification (one label per image, cheapest to label). "Where is the damage?" is detection (a box). "How large is the damage?" is segmentation (a mask, 10× the labeling cost). A shocking number of projects label masks when a box would do, or boxes when a label would do. Also consider the zero-training route: embed everything with a pretrained model and see whether nearest neighbours or a logistic regression on the embeddings already solves it. It frequently does.

10. Practical tips and a full training run

The training loop for a CNN is exactly Chapter 16's loop; only the model and the data pipeline change. Here it is end to end on a synthetic task generated in NumPy so it runs in seconds on a CPU: 16×16 images of noisy vertical or horizontal stripes, a two-block CNN, cross-entropy, Adam. It reaches 100% test accuracy in a few epochs because orientation is exactly what a 3×3 kernel detects.

# Train a CNN on a synthetic image task: vertical vs horizontal stripes
import numpy as np, torch, torch.nn as nn
from torch.utils.data import TensorDataset, DataLoader
rng = np.random.default_rng(0); torch.manual_seed(0)

def make_images(n, size=16):
    X = np.zeros((n, 1, size, size), dtype=np.float32)
    y = rng.integers(0, 2, n)                          # 0 = vertical, 1 = horizontal
    for i in range(n):
        period = rng.integers(3, 6); phase = rng.integers(0, period)
        idx = (np.arange(size) + phase) % period < period // 2
        stripes = np.tile(idx, (size, 1)) if y[i] == 0 else np.tile(idx[:, None], (1, size))
        X[i, 0] = stripes + 0.4 * rng.standard_normal((size, size))   # add noise
    return torch.tensor(X), torch.tensor(y)

X_tr, y_tr = make_images(400); X_te, y_te = make_images(200)
dl = DataLoader(TensorDataset(X_tr, y_tr), batch_size=32, shuffle=True)

model = nn.Sequential(
    nn.Conv2d(1, 8, 3, padding=1), nn.ReLU(), nn.MaxPool2d(2),   # 16x16 -> 8x8
    nn.Conv2d(8, 16, 3, padding=1), nn.ReLU(), nn.MaxPool2d(2),  # 8x8 -> 4x4
    nn.AdaptiveAvgPool2d(1), nn.Flatten(), nn.Linear(16, 2))      # 2 logits
opt = torch.optim.Adam(model.parameters(), lr=3e-3)
loss_fn = nn.CrossEntropyLoss()                                   # takes logits + int labels

for epoch in range(1, 9):
    model.train()
    for xb, yb in dl:
        loss = loss_fn(model(xb), yb)
        opt.zero_grad(); loss.backward(); opt.step()
    model.eval()
    with torch.no_grad():
        acc = (model(X_te).argmax(1) == y_te).float().mean().item()
    if epoch in (1, 2, 4, 8):
        print(f"epoch {epoch}  train loss {loss.item():.3f}  test acc {acc:.3f}")
# epoch 1  train loss 0.596  test acc 0.505
# epoch 2  train loss 0.534  test acc 0.810
# epoch 4  train loss 0.096  test acc 1.000
# epoch 8  train loss 0.003  test acc 1.000

Things that matter on real images, in rough order of how often they bite:

Input normalization

Scale to [0, 1], then subtract the per-channel mean and divide by the std, using the pretrained backbone's constants when fine-tuning. Wrong stats do not error; they just cost accuracy.

Resolution vs cost

Compute grows with the square of the side length: 224→448 is 4× the work and memory. Start at 224; go up only if the objects of interest are tiny at that size (check by looking at resized images yourself).

Class imbalance

Defects are rare. Use a weighted sampler or class weights in the loss, evaluate with per-class recall and PR curves, not accuracy (Chapter 6, Chapter 13), and check that augmentation does not accidentally erase small defects.

Label quality

Vision labels are noisier than people assume. Look at 200 random training images with their labels before training. After training, inspect the highest-loss training examples: they are usually mislabeled, and fixing them beats any tuning.

Per-class confusion matrix

Overall accuracy hides that two visually similar classes are being swapped. Always print the confusion matrix and the per-class precision/recall; the errors tell you which classes need more data or a merged label.

Look at the failures

Plot the worst 50 validation errors with predicted and true labels. Patterns jump out: lighting, a background that correlates with a class, cropped objects. Every one of those is a fix that no hyperparameter search would find.

Common mistake

The background shortcut. If all your "defective" photos were taken at station B under yellow light and all "good" photos at station A, the network will learn the light, get 99% on your validation split, and fail in production. Split validation by time, site or device, not randomly by image, and check the model on a deliberately hard slice (same station, both classes) before believing any number.

Try it yourself

Modify the stripes experiment: (1) add a third class, diagonal stripes, and see whether two 3×3 blocks still suffice; (2) reduce the training set to 40 images and watch test accuracy; then add augmentation by randomly flipping and rolling the images (torch.roll) each epoch and see how much it recovers; (3) print the learned first-layer kernels (model[0].weight) and compare them with Figure 17.3.

Key idea

The model is rarely the problem. On real vision projects the accuracy is decided by label quality, the validation split, augmentation, input normalization and the choice of task, with the backbone a distant sixth. Spend your time accordingly.

Quiz

Check your understanding

1. A conv layer takes a 64-channel input, has 128 filters of size 3×3, and processes a 256×256 image. How many weights (excluding biases) does it have?

Each of the 128 filters has one 3×3 slice per input channel: 64 × 9 = 576 weights per filter, 73,728 in total (plus 128 biases). The image size does not enter; it affects memory and compute, not parameters.

2. A 32×32 input goes through a 5×5 convolution with stride 2 and padding 2. What is the output size?

⌊(32 + 2·2 − 5)/2⌋ + 1 = ⌊31/2⌋ + 1 = 15 + 1 = 16. Padding of (k−1)/2 with stride 2 halves the size, which is the standard downsampling configuration.

3. Why did 56-layer plain networks train worse than 20-layer ones before ResNet, and what does the skip connection change?

Training error (not just test error) increased with depth, so it was an optimization failure. A residual block outputs F(x) + x, so doing nothing is easy (F = 0) and the gradient reaches earlier layers through the addition undiminished.

4. You have 600 labeled photos of products and a ResNet-50 pretrained on ImageNet. The best first approach is…

Small data, similar domain: pretrained features are already good, so train the head on frozen features first. A large learning rate on unfrozen weights would destroy them; training from scratch needs orders of magnitude more images.

5. Which augmentation is wrong for a handwritten-digit classifier?

A mirror-image 2, 3, 5, 6, 7 or 9 is not a valid digit (and a 6 rotated by 180° becomes a 9); the label does not survive the transformation. Every augmentation is a claim that the label is invariant to it.

6. A manager asks for "a model that measures how much of each solar panel is covered by dust". Which task family is this?

"How much area" needs a per-pixel answer: segmentation, with fraction covered computed from the mask. If the question were only "is this panel dirty?", classification would do and be 10× cheaper to label.

output[1,1]: window rows 1–3, cols 1–3 = [[1,2,3],[0,1,2],[1,0,1]] times [[1,0,−1],…] → (1−3) + (0−2) + (1−1) = −4. output[2,0]: rows 2–4, cols 0–2 = [[1,0,1],[2,1,0],[0,2,1]] → (1−1) + (2−0) + (0−1) = 1. With padding the window at the border overlaps zeros, so fewer nonzero products contribute and edge responses are partly "half-kernel" responses; that is why some architectures use reflection padding.

Pick an image problem from your organization (quality inspection, document sorting, product matching, anything with a camera). Chapter summary

  • An image is a C×H×W tensor (batch: B×C×H×W). Dense layers on pixels explode in parameters and cannot handle shifted objects.
  • Convolution slides a small learned kernel over the image: each output pixel is the dot product of the kernel with the patch beneath. Local weights, shared everywhere.
  • Output size = ⌊(n + 2p − d(k−1) − 1)/s⌋ + 1. "Same" padding for 3×3 is p = 1; stride 2 halves; dilation widens the view for free.
  • A filter is Cin×k×k and sums over channels; a layer has Cout filters and Cout·Cin·k² + Cout parameters, independent of image size.
  • Pooling and strided convs shrink the map; receptive fields grow with depth; features go edges → textures → parts → objects.
  • The universal pattern: conv → BN → ReLU blocks, halve size/double channels, global average pool, linear head to logits.
  • ResNet's skip connection (y = F(x) + x) made deep nets trainable; 1×1 convs, depthwise-separable convs and compound scaling made them cheap; ViTs replace convolution with attention over patches.
  • Augment training images with label-preserving transforms; never augment validation; never use a transform the label does not survive.
  • At work: pretrained backbone + new head; train head frozen, then unfreeze the top with a 10–100× smaller learning rate; normalize with the backbone's stats.
  • Classification, detection (boxes, IoU), segmentation (per-pixel), embeddings (similarity): same backbone, different head. Pick the cheapest task that answers the question, and look at your failures.
