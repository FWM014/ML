1. Why a framework: autograd

In Chapter 15 you derived the backward pass of a two-layer network by hand: a page of chain-rule algebra for a model with a few hundred weights. Now imagine a network with fifty layers, skip connections, normalization layers and a custom loss. Deriving gradients by hand is not merely tedious; it is where bugs live. Every serious deep-learning framework exists to remove that job from you, and the mechanism that does it is called automatic differentiation, or autograd.

Explain it like I'm 9

Imagine building a LEGO tower and writing down every brick you add, in order, on a receipt. If someone later asks "how much did the third brick contribute to the tower's height?", you do not need to rebuild anything: you read the receipt backwards. Autograd is the receipt. Every time you multiply, add or squash a tensor, PyTorch writes down what you did. When you call backward(), it reads the receipt from the end to the start and hands each weight its gradient.

The receipt is a computation graph. Every operation on a tensor that requires gradients creates a node that remembers its inputs and how to differentiate itself. The forward pass builds the graph as a side effect of computing the answer; backward() walks it in reverse, multiplying local derivatives along the way. That is exactly the chain rule from Chapter 15, executed by a machine that never forgets a term.

Three practical consequences follow. First, you only ever write the forward pass; the backward pass is derived for you, correctly, every time. Second, gradients are only computed for tensors that ask for them (requires_grad=True) — data tensors do not carry gradients, and that is what keeps memory manageable. Third, the graph is rebuilt on every forward pass ("define-by-run"), so ordinary Python if statements and loops inside a model just work. That dynamic style is why PyTorch won over researchers and then over industry.

# Tensors, requires_grad and the autograd graph
import torch
torch.manual_seed(0)

x = torch.tensor([1.0, 2.0, 3.0])          # plain data: no gradient tracked
w = torch.tensor([0.5, -1.0, 2.0], requires_grad=True)   # a parameter
b = torch.tensor(0.1, requires_grad=True)

y_hat = (w * x).sum() + b                 # forward: builds a graph as it runs
loss = (y_hat - 4.0) ** 2                 # scalar loss
print(f"y_hat = {y_hat.item():.2f}   loss = {loss.item():.2f}")
print("loss.grad_fn:", type(loss.grad_fn).__name__)   # the graph node that made loss

loss.backward()                           # walk the graph backwards: chain rule
print("dloss/dw =", w.grad)               # = 2*(y_hat-4)*x
print("dloss/db =", round(b.grad.item(), 2))   # = 2*(y_hat-4)
print("x.grad  =", x.grad)                # None: we never asked for it
# y_hat = 4.60   loss = 0.36
# loss.grad_fn: PowBackward0
# dloss/dw = tensor([1.2000, 2.4000, 3.6000])
# dloss/db = 1.2
# x.grad  = None
Key idea

Forward builds, backward reads. Every tensor operation records itself in a graph; loss.backward() replays the graph in reverse and deposits a gradient in each parameter's .grad. Gradients accumulate across calls, which is why every training loop must clear them before each backward pass.

PyTorch has a small cast of objects. Once you can name what each one owns and what it is responsible for, every tutorial, codebase and error message becomes readable.

Think of a bakery. The Dataset is the pantry (every ingredient, one at a time). The DataLoader is the assistant who brings you trays of 32 ingredients at once, in a random order so you never bake the same tray twice in a row. The Module is the recipe with its adjustable amounts (the parameters). The loss is the taste test. The optimizer is the rule for adjusting the amounts after each taste test. The device is which kitchen you are standing in; you cannot mix ingredients from two kitchens.

Tensors and requires_grad

A tensor is a NumPy array with two extras: it can live on an accelerator, and it can participate in autograd. By default a tensor made from data does not track gradients; parameters inside a Module do. The dtype matters more than in NumPy: models default to float32, and a float64 input silently produces a "expected Float but found Double" error. Convert explicitly, as the code above does with dtype=torch.float32. Integer class labels for CrossEntropyLoss must be int64 (torch.long).

nn.Module and parameters

A Module is a container that knows its learnable parameters and how to compute its output. You get two things for free: model.parameters() (an iterator over every weight, recursively through submodules — this is what you hand to the optimizer) and model.state_dict() (an ordered dictionary of every parameter and buffer, which is what you save to disk). nn.Sequential is a Module that chains layers; for anything with branches or reuse, write a class with __init__ and forward. The train()/eval() switch changes the behavior of dropout and batch norm, and forgetting it is one of the two or three most common bugs in the field.

Dataset and DataLoader

For tabular data that fits in memory, TensorDataset plus a DataLoader is all you need. The DataLoader gives you shuffling (essential for SGD; unshuffled sorted data trains badly), batching, and multi-process loading for the cases where reading an item is expensive (images from disk, tokenization). Set shuffle=True for training and False for validation.

At work

Scale features exactly as you would for logistic regression (Chapter 8): fit a StandardScaler on the training split only, then transform train, validation and test. Neural networks are far more sensitive to unscaled inputs than tree models are; an unscaled column with values in the thousands will dominate every gradient and the loss will stall or explode. If a network "will not learn", unscaled inputs are the first thing to check.

3. Anatomy of a training loop

Every PyTorch training loop, from a two-layer MLP to a large language model, is the same five steps repeated for each mini-batch. Learn them as a sequence you can type without thinking, because you will type them thousands of times.

  1. Forward. logits = model(xb). The model reads its current parameters and produces raw outputs. Autograd records the graph.
  2. Loss. loss = loss_fn(logits, yb). One scalar. If it is not a scalar, backward() will complain.
  3. Zero the gradients. opt.zero_grad(). Gradients accumulate into .grad by design (useful for gradient accumulation across micro-batches); if you forget this, every step uses the sum of all previous gradients and training silently degrades.
  4. Backward. loss.backward(). Autograd walks the graph and writes a gradient into every parameter.
  5. Step. opt.step(). The optimizer reads each .grad and updates each parameter according to its rule (plain SGD, momentum, Adam…).

Here is the whole thing, with the two pieces every real loop also needs: an evaluation pass under torch.no_grad() (no graph, less memory, faster) and early stopping that keeps the best weights seen on the validation set.

# A complete PyTorch training loop with validation and early stopping
import torch, torch.nn as nn
from torch.utils.data import TensorDataset, DataLoader
from sklearn.datasets import make_moons
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import StandardScaler
torch.manual_seed(0)

X, y = make_moons(n_samples=600, noise=0.25, random_state=42)
X_tr, X_va, y_tr, y_va = train_test_split(X, y, test_size=0.25, random_state=0, stratify=y)
sc = StandardScaler().fit(X_tr)                     # scale on TRAIN only
to_t = lambda a: torch.tensor(a, dtype=torch.float32)
X_tr, X_va = to_t(sc.transform(X_tr)), to_t(sc.transform(X_va))
y_tr, y_va = to_t(y_tr).unsqueeze(1), to_t(y_va).unsqueeze(1)   # shape (n, 1)

train_dl = DataLoader(TensorDataset(X_tr, y_tr), batch_size=32, shuffle=True)

model = nn.Sequential(nn.Linear(2, 32), nn.ReLU(), nn.Linear(32, 32), nn.ReLU(), nn.Linear(32, 1))
loss_fn = nn.BCEWithLogitsLoss()                    # expects raw logits, NOT sigmoid output
opt = torch.optim.Adam(model.parameters(), lr=1e-2)

best_val, best_state, patience, bad = float("inf"), None, 5, 0
for epoch in range(1, 41):
    model.train()
    for xb, yb in train_dl:
        logits = model(xb)              # 1. forward
        loss = loss_fn(logits, yb)      # 2. loss
        opt.zero_grad()                 # 3. clear old gradients
        loss.backward()                 # 4. backward (autograd)
        opt.step()                      # 5. update weights
    model.eval()
    with torch.no_grad():               # no graph needed for evaluation
        val_loss = loss_fn(model(X_va), y_va).item()
        val_acc = ((model(X_va) > 0).float() == y_va).float().mean().item()
    if val_loss < best_val - 1e-4:
        best_val, bad = val_loss, 0
        best_state = {k: v.clone() for k, v in model.state_dict().items()}
    else:
        bad += 1
    if epoch % 5 == 0:
        print(f"epoch {epoch:2d}  val_loss {val_loss:.3f}  val_acc {val_acc:.3f}")
    if bad >= patience:
        print(f"early stop at epoch {epoch}, best val_loss {best_val:.3f}")
        break
model.load_state_dict(best_state)       # roll back to the best epoch
# epoch  5  val_loss 0.190  val_acc 0.927
# epoch 10  val_loss 0.154  val_acc 0.940
# epoch 15  val_loss 0.169  val_acc 0.940
# early stop at epoch 15, best val_loss 0.154

Notice the details that distinguish a correct loop from a demo: features scaled on the training split only; labels shaped (n, 1) to match the model output; model.train() / model.eval() toggled every epoch; validation under no_grad; the best state_dict cloned (not referenced — the tensors would keep changing) and restored at the end. The loop stopped at epoch 15 because validation loss had not improved for five epochs: that is early stopping doing its job as a regularizer (Chapter 7).

Loss functions and the output layer they expect

This is the single most common source of silently-wrong deep learning code. Each loss expects a specific kind of model output. Get it wrong and the code runs, the loss goes down a little, and the model is mediocre for a reason you cannot see.

TaskLossModel output (last layer)TargetWhy it's built this way

Common mistake

Putting a sigmoid or softmax at the end of the model and then using BCEWithLogitsLoss / CrossEntropyLoss. The loss applies the activation again. Probabilities get squashed a second time, gradients shrink toward zero near confident predictions, and the model trains slowly to a worse optimum. The rule: the model outputs logits; the loss owns the activation. Apply sigmoid/softmax only at inference time when you actually want probabilities.

The math (optional): why logits and the loss belong together
BCEWithLogits(z, y) = max(z, 0) − z·y + log(1 + e−|z|)

Here z is the logit and y ∈ {0, 1} the target. Algebraically this equals −[y·log σ(z) + (1−y)·log(1−σ(z))], the ordinary log-loss on the sigmoid σ(z). The rewritten form never computes log(σ(z)) directly, so it cannot produce log(0) = −∞ when z is very negative; a separate sigmoid followed by BCELoss can. The same trick (log-sum-exp) is inside CrossEntropyLoss. Numerical stability is the practical reason the framework insists on logits.

4. Optimizers: SGD to AdamW

The optimizer decides how a gradient becomes a weight update. Plain gradient descent (Chapter 5) moves each weight a fixed fraction of its gradient: w ← w − η·g. On the loss surfaces of real networks that rule is fragile. Losses are shaped like long, narrow ravines: steep across, almost flat along. A step small enough not to bounce off the steep walls is far too small to make progress along the floor. Every optimizer since 1990 is a fix for that picture.

Explain it like I'm 9

Plain SGD is a person walking downhill in fog who stops after every step, looks at the slope under their feet, and steps that way. In a narrow canyon they keep bouncing wall to wall. Momentum is a heavy ball rolling downhill: it remembers which way it was going, so the wall-to-wall bounces cancel out and the downhill motion adds up. Adam is a ball that also notices "this direction is always bumpy, take smaller steps there; that direction is always smooth, take bigger steps there."

The math (optional): momentum and Nesterov
vt = β·vt−1 + gt wt+1 = wt − η·vt

gt is the gradient of the mini-batch loss at step t; vt is the velocity, an exponentially decaying sum of past gradients; β (usually 0.9) is how much of the old velocity survives each step; η is the learning rate. Because Σβk = 1/(1−β) = 10 for β = 0.9, the velocity can grow to about ten times a consistent gradient, which is the acceleration along the ravine floor. Nesterov momentum (nesterov=True) evaluates the gradient at the look-ahead point w − η·β·v instead of at w; it corrects overshooting slightly earlier and is the variant usually preferred with SGD.

Adaptive methods: RMSProp, Adam, AdamW

Momentum treats every weight with one learning rate. But different weights see gradients of wildly different scales: an embedding row that appears once per thousand examples gets tiny, rare gradients; a bias in the last layer gets large, constant ones. RMSProp keeps a running average of each weight's squared gradient and divides the step by its square root, so every weight moves by roughly the same amount regardless of its gradient's raw scale. Adam combines that with momentum on the gradient itself, plus a correction for the fact that the running averages start at zero.

The math (optional): Adam
mt = β1mt−1 + (1−β1)gt st = β2st−1 + (1−β2)gt2
m̂t = mt/(1−β1t) ŝt = st/(1−β2t) wt+1 = wt − η · m̂t / (√ŝt + ε)

mt is the momentum (first moment) of the gradient with decay β1 = 0.9; st is the running mean of the squared gradient (second moment, computed per weight) with decay β2 = 0.999; the hats are bias corrections so the first steps are not artificially tiny; ε ≈ 10−8 avoids division by zero. Reading the update: the step direction is the smoothed gradient, and its size in every coordinate is about η because the gradient is divided by its own typical magnitude. That is why Adam's learning rate is "unit-free" and why 10−3 works across so many problems.

AdamW is Adam with weight decay applied directly to the weights (w ← w − η·λ·w) instead of being added to the gradient. In Adam the added L2 gradient gets divided by √ŝ like everything else, which makes the regularization strength depend on gradient scale and effectively disables it for weights with large gradients. AdamW decouples the two. It is the default in essentially all modern training recipes.

Below, one network, one starting point (same seed), five optimizers, sixty full-batch steps each. The numbers are for the same problem, so they can be compared directly.

# Same net, same data, same seed — five optimizers
import torch, torch.nn as nn
from sklearn.datasets import load_breast_cancer
from sklearn.preprocessing import StandardScaler

X, y = load_breast_cancer(return_X_y=True)
X = torch.tensor(StandardScaler().fit_transform(X), dtype=torch.float32)
y = torch.tensor(y, dtype=torch.float32).unsqueeze(1)

def make_net():
    torch.manual_seed(0)                     # identical starting weights every time
    return nn.Sequential(nn.Linear(30, 16), nn.ReLU(), nn.Linear(16, 1))

def train(opt_name, **kw):
    net = make_net()
    opt = getattr(torch.optim, opt_name)(net.parameters(), **kw)
    loss_fn = nn.BCEWithLogitsLoss()
    for step in range(60):                   # full-batch, 60 steps
        loss = loss_fn(net(X), y)
        opt.zero_grad(); loss.backward(); opt.step()
    return loss.item()

for name, kw in [("SGD", dict(lr=0.05)),
                 ("SGD", dict(lr=0.05, momentum=0.9)),
                 ("RMSprop", dict(lr=0.01)),
                 ("Adam", dict(lr=0.01)),
                 ("AdamW", dict(lr=0.01, weight_decay=0.01))]:
    tag = name + ("+momentum" if kw.get("momentum") else "")
    print(f"{tag:14s} final loss {train(name, **kw):.3f}")
# SGD            final loss 0.266
# SGD+momentum   final loss 0.062
# RMSprop        final loss 0.029
# Adam           final loss 0.053
# AdamW          final loss 0.053

Plain SGD at this learning rate has barely started; momentum is four times further along; the adaptive methods are further still. This ranking after a fixed small budget is typical, and it is why the adaptive methods dominate practice. It is not a statement about final accuracy after a long, well-tuned run: SGD with momentum and a good schedule matches or beats Adam on many vision benchmarks, which is why you still see it in ResNet recipes. But it needs more tuning to get there.

5. The learning rate and its schedules

If you tune one hyperparameter, tune this one. The learning rate η controls how far each step moves. Too high and the update overshoots the valley floor, the loss oscillates or explodes to NaN. Too low and training crawls, often stalling on a plateau that looks like convergence but is not. Every other hyperparameter interacts with it, and a "bad architecture" is very frequently a bad learning rate.

The LR range test

Instead of guessing, measure. Start from a tiny learning rate (10−6) and increase it geometrically every batch up to something absurd (10), recording the loss at each step. Plot loss against learning rate on a log axis. The loss is flat at first (rate too small to matter), then drops steeply (the useful region), then bottoms out and explodes. A good constant learning rate is about one order of magnitude below the point where the loss is lowest; a good maximum for a one-cycle schedule is just before the loss starts rising. The whole test takes one short epoch and replaces hours of trial and error.

Schedules: change η during training

A large learning rate early makes fast progress and escapes bad regions; a small one late settles into a sharp minimum. No single constant does both, so we schedule it. A short warmup at the start (linearly increasing from ~0 over a few hundred steps or a few epochs) is cheap insurance: it lets the adaptive optimizer's running statistics and the batch-norm layers stabilize before large steps are taken. It matters most for transformers and for large batches.

# Learning-rate schedules: watch the LR change per epoch
import math, torch, torch.nn as nn
net = nn.Linear(4, 1)
opt = torch.optim.SGD(net.parameters(), lr=0.1)

# warmup for 3 epochs, then cosine decay to ~0 over the remaining 9
warm, total = 3, 12
def lr_lambda(e):                       # multiplier applied to the base lr=0.1
    if e < warm:
        return (e + 1) / warm
    return 0.5 * (1 + math.cos(math.pi * (e - warm) / (total - warm)))
sched = torch.optim.lr_scheduler.LambdaLR(opt, lr_lambda)

for epoch in range(total):
    # ... train one epoch here ...
    opt.step()              # optimizer step(s) come first
    sched.step()            # then the scheduler, once per epoch
    print(f"epoch {epoch+1:2d}  lr = {opt.param_groups[0]['lr']:.4f}")

Two mechanics to remember: schedulers are stepped after the optimizer (once per epoch for epoch-based schedules, once per batch for OneCycleLR), and ReduceLROnPlateau.step() takes the validation metric as an argument because it decides based on it. Keep the scheduler's state in your checkpoint together with the optimizer's.

Batch size and its interaction with the learning rate

Larger batches give a less noisy gradient, so they tolerate (and need) a larger learning rate: the practical rule for SGD is that doubling the batch size lets you roughly double η ("linear scaling"), for Adam closer to √2. Very small batches (8–32) add noise that acts as a regularizer and often generalize slightly better; very large batches train faster per epoch on a GPU but can generalize worse unless the rate and warmup are re-tuned. For tabular MLPs, 64–256 is the sweet spot. Pick the batch size for hardware efficiency first, then tune the learning rate for that batch size, not the other way round.

Key idea

The learning rate is a property of the (model, optimizer, batch size, loss scale) combination, not of the problem. Change any of those and re-tune it, ideally with a range test. When something stops working after a "harmless" change, the learning rate is the first suspect.

6. Initialization and normalization

A deep network is a long product of matrices and nonlinearities. Numbers that pass through it either stay in a reasonable range or they don't; if they don't, they shrink to zero or blow up geometrically with depth, and so do the gradients coming back. Initialization and normalization are the two tools that keep the signal's scale under control, one at time zero and one throughout training.

Explain it like I'm 9

Whisper a message down a line of 50 friends. If each friend repeats it a little quieter, by friend 50 there is nothing to hear (vanishing). If each repeats it a little louder, by friend 50 it is a scream (exploding). Initialization picks how loud each friend starts. Normalization puts a volume knob between every pair of friends that resets the message to normal loudness before passing it on.

Initialization: Xavier/Glorot and He/Kaiming

Take a linear layer with nin inputs, each of variance 1, and weights drawn independently with variance σ2. The output is a sum of nin terms, so its variance is nin·σ2. To keep the output variance equal to the input variance you need σ2 = 1/nin. That is Xavier (Glorot) initialization, the right choice for tanh and sigmoid networks. A ReLU zeroes half of its inputs and so halves the variance; to compensate, He (Kaiming) initialization uses σ2 = 2/nin. PyTorch's nn.Linear and nn.Conv2d default to a Kaiming-uniform variant, so in practice you rarely set this by hand — but you should know what it is doing, because a custom layer or a hand-built weight tensor with torch.randn (variance 1) will not train at depth.

The math (optional): variance preservation
Var(z) = Var(Σi wixi) = nin · Var(w) · Var(x) ⇒ Var(w) = 1/nin (Xavier) or 2/nin (He, after ReLU)

z is one pre-activation output of the layer; xi are its nin inputs, assumed independent with zero mean and equal variance; wi the weights, independent of the inputs with zero mean. Variances of independent products add, giving the factor nin. Setting Var(w) = 1/nin makes Var(z) = Var(x) layer after layer. With ReLU, E[ReLU(z)2] = ½Var(z) for symmetric z, so the weight variance is doubled to compensate. Glorot's original formula averages fan-in and fan-out, 2/(nin+nout), to also protect the backward pass.

Batch normalization and layer normalization

Initialization fixes the scale at step zero; training then moves the weights and the scale drifts again. Normalization layers re-standardize activations on every forward pass. Batch norm (nn.BatchNorm1d/2d) standardizes each feature (each neuron, or each channel in a CNN) using the mean and variance of the current mini-batch, then multiplies by a learned scale γ and adds a learned shift β so the network can undo the normalization if it wants. At evaluation time it uses running averages collected during training, which is why model.eval() matters. Layer norm (nn.LayerNorm) standardizes across the features of each single example, so it does not depend on the batch at all; it is the norm of choice for transformers and sequence models (Chapter 18) and for tiny batches.

Why they help. Normalization keeps every layer's input in the range where the activation function and the optimizer behave well, regardless of what earlier layers did. The practical effects: you can use a learning rate several times larger, training is far less sensitive to initialization, deep networks train at all, and batch norm adds a little noise (each example is normalized with a different batch's statistics) that acts as a regularizer. The original "internal covariate shift" explanation is mostly folklore; the more careful account is that normalization smooths the loss landscape, making gradients more predictable from step to step.

Common mistake

Evaluating with model.train() still on, or training with batch size 1–4 while using batch norm. In train mode batch norm normalizes each example with the statistics of whatever batch it happens to be in, so predictions for one example depend on its neighbors — and with a batch of one, the variance is undefined. Always call model.eval() before validation and inference, and if your batches must be tiny, use layer norm (or group norm in CNNs) instead.

7. Regularization and gradient clipping

A neural network with a few thousand parameters can memorize a few thousand rows of tabular data perfectly; everything in Chapter 7 about overfitting applies with extra force. Deep learning has four standard regularizers, and at work you will use all four together.

Weight decay

Pull every weight gently toward zero on every step: w ← w − η·λ·w. It is L2 regularization by another name (Chapter 5), and it discourages any single weight from becoming large enough to fit noise. With AdamW it is set through weight_decay and applied decoupled from the adaptive scaling, as discussed in §4. Typical values: 10−2 for AdamW, 5×10−4 for SGD. Do not decay the biases and normalization parameters; it does not help and slightly hurts (advanced recipes build two parameter groups for this reason).

Dropout

During training, each unit's output is set to zero with probability p, independently on every forward pass, and the survivors are scaled by 1/(1−p) so the expected sum stays the same. At test time nothing is dropped. The network can never rely on one specific unit being present, so it learns redundant, distributed features, and every forward pass trains a slightly different sub-network; the test-time network is an implicit average of all of them. p = 0.1–0.3 for hidden layers of an MLP is the useful range; 0.5 was the original paper's value and is usually too much for modern networks with batch norm.

Data augmentation and early stopping

Data augmentation creates new training examples by applying label-preserving transformations: flips, crops and color jitter for images (Chapter 17), synonym swaps and back-translation for text, small Gaussian noise or feature dropout for tabular data. It is the most effective regularizer when it is available, because it adds genuine information about the invariances of the problem. Early stopping, which you saw in the training loop, is the cheapest: monitor validation loss and keep the best weights. Use a patience of 5–20 epochs depending on how noisy the validation metric is, and always restore the best checkpoint rather than the last.

Gradient clipping

Occasionally a batch produces an enormous gradient (an outlier row, an unlucky combination of a large learning rate and a steep region) and one step throws the weights somewhere terrible. Clipping rescales the whole gradient vector so its norm is at most a threshold: nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0), called between backward() and step(). It is essential for recurrent networks and transformers and harmless elsewhere; a max norm of 1.0 is the near-universal default. It also returns the pre-clip norm, which is the cheapest gradient-health monitor you can log.

Here is the full "regularized MLP" recipe: batch norm, dropout, AdamW weight decay, clipping — plus the loss-at-initialization sanity check from §8 and saving/loading via state_dict.

# Regularized MLP: dropout + weight decay (AdamW) + gradient clipping + save/load
import torch, torch.nn as nn, io
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.preprocessing import StandardScaler
torch.manual_seed(0)

X, y = load_breast_cancer(return_X_y=True)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.25, random_state=0, stratify=y)
sc = StandardScaler().fit(X_tr)
t = lambda a: torch.tensor(a, dtype=torch.float32)
X_tr, X_te = t(sc.transform(X_tr)), t(sc.transform(X_te))
y_tr, y_te = t(y_tr).unsqueeze(1), t(y_te).unsqueeze(1)

class MLP(nn.Module):
    def __init__(self, d_in, hidden=64, p_drop=0.3):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(d_in, hidden), nn.BatchNorm1d(hidden), nn.ReLU(), nn.Dropout(p_drop),
            nn.Linear(hidden, hidden), nn.BatchNorm1d(hidden), nn.ReLU(), nn.Dropout(p_drop),
            nn.Linear(hidden, 1))
    def forward(self, x):
        return self.net(x)

model = MLP(30)
print("parameters:", sum(p.numel() for p in model.parameters()))
# parameters: 6465
opt = torch.optim.AdamW(model.parameters(), lr=1e-3, weight_decay=1e-2)   # decoupled L2
loss_fn = nn.BCEWithLogitsLoss()

# sanity check: loss at init for a balanced binary problem should be ≈ ln(2) = 0.693
model.eval()
with torch.no_grad():
    print(f"loss at init: {loss_fn(model(X_tr), y_tr).item():.3f}")
# loss at init: 0.685

for epoch in range(15):
    model.train()                           # dropout ON, batchnorm uses batch stats
    perm = torch.randperm(len(X_tr))
    for i in range(0, len(X_tr), 32):
        idx = perm[i:i+32]
        loss = loss_fn(model(X_tr[idx]), y_tr[idx])
        opt.zero_grad(); loss.backward()
        nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)   # gradient clipping
        opt.step()

model.eval()                                # dropout OFF, batchnorm uses running stats
with torch.no_grad():
    acc = ((model(X_te) > 0).float() == y_te).float().mean().item()
print(f"test accuracy: {acc:.3f}")
# test accuracy: ≈ 0.944

# --- save & load: persist the state_dict, not the object ---
torch.save(model.state_dict(), "mlp.pt")
fresh = MLP(30)                              # must rebuild the same architecture
fresh.load_state_dict(torch.load("mlp.pt"))
fresh.eval()
with torch.no_grad():
    same = torch.allclose(fresh(X_te), model(X_te))
print("reloaded model gives identical outputs:", same)
# reloaded model gives identical outputs: True
Key idea

Regularizers stack, and each targets a different failure. Weight decay limits weight magnitude; dropout limits co-adaptation; augmentation encodes invariances; early stopping limits training time; clipping limits single-step damage. A tabular MLP at work typically wants all of them at mild settings rather than one at a strong setting.

8. The debugging recipe and reading curves

Networks fail silently. A bug in a tree model usually throws an exception; a bug in a neural network produces a model that trains to 71% accuracy instead of 94% and nobody notices for a month. The defense is a fixed sequence of cheap checks that you run before training on the full data. Experienced practitioners do these reflexively.

  1. Check shapes at every boundary. Print xb.shape, model(xb).shape, yb.shape for one batch. A (64,) target against a (64, 1) output broadcasts into a 64×64 matrix inside MSELoss and trains on garbage without any error.
  2. Check the loss at initialization. Before any training, a C-class classifier with near-uniform outputs should have cross-entropy ≈ ln(C): 0.693 for two classes, 2.303 for ten. Much higher means the last layer's outputs are too large (bad init or unscaled inputs); much lower means you are leaking labels or the classes are imbalanced (then compare with ln of the prior).
  3. Overfit a single batch. Take 16 examples and train on them alone for a few hundred steps. Training loss must go to essentially zero. If it cannot memorize 16 rows, no amount of data will help: the model, loss, or update code is wrong.
  4. Watch for NaN and inf. A NaN loss is almost always the learning rate (too high), a log of zero (using BCELoss on unclamped probabilities), or a division by a zero variance. Add torch.isnan(loss) to your logging.
  5. Look at the gradients. Log the gradient norm every step (clip_grad_norm_ returns it for free). Zero means a dead ReLU network or a detached graph; growing without bound means the rate is too high; a sudden spike identifies a bad batch.
  6. Then scale up. Only now train on the full data, with the validation loop, and read the curves.
# The debugging recipe in code: overfit ONE batch before training on everything
import torch, torch.nn as nn
from sklearn.datasets import load_breast_cancer
from sklearn.preprocessing import StandardScaler
torch.manual_seed(0)

X, y = load_breast_cancer(return_X_y=True)
X = torch.tensor(StandardScaler().fit_transform(X), dtype=torch.float32)
y = torch.tensor(y, dtype=torch.float32).unsqueeze(1)
xb, yb = X[:16], y[:16]                    # a single batch of 16

model = nn.Sequential(nn.Linear(30, 32), nn.ReLU(), nn.Linear(32, 1))
loss_fn = nn.BCEWithLogitsLoss()
opt = torch.optim.Adam(model.parameters(), lr=1e-2)
print("shapes: x", tuple(xb.shape), "logits", tuple(model(xb).shape), "y", tuple(yb.shape))
# shapes: x (16, 30) logits (16, 1) y (16, 1)

for step in range(201):
    loss = loss_fn(model(xb), yb)
    opt.zero_grad(); loss.backward()
    gnorm = torch.nn.utils.clip_grad_norm_(model.parameters(), 1e9)   # measure, don't clip
    opt.step()
    if step % 50 == 0:
        is_nan = torch.isnan(loss).item()
        print(f"step {step:3d}  loss {loss.item():.4f}  grad-norm {gnorm:.3f}  nan? {is_nan}")
# loss must go to ~0. If it doesn't, the bug is in your code, not your data.
# step   0  loss 0.6292  grad-norm 1.514  nan? False
# step  50  loss 0.0002  grad-norm 0.001  nan? False
# step 100  loss 0.0001  grad-norm 0.001  nan? False
# step 150  loss 0.0001  grad-norm 0.001  nan? False
# step 200  loss 0.0001  grad-norm 0.000  nan? False
Explain it like I'm 9

Before you take a new bicycle on a 50 km ride, you ride it around the block. If it cannot do the block, the ride is not going to happen. "Overfit one batch" is riding around the block: the tiniest possible task that still exercises every part of the machine.

Reading training curves

Once the full run is going, the pair of curves — training loss and validation loss (or metric) per epoch — is your primary instrument. Four shapes cover almost everything you will see.

At work

Log every run: hyperparameters, git commit, data version, seed, per-epoch train/val loss and metric, gradient norm, learning rate. A spreadsheet or a lightweight tracker (MLflow, Weights & Biases, or a CSV per run) is fine. The reason is not tidiness: two weeks in, the question "what changed between the run that worked and the one that didn't?" will be the only question that matters, and memory will not answer it. Chapter 21 covers experiment tracking properly.

9. Hardware, precision, checkpoints, reproducibility

GPUs and the device

A GPU makes the matrix multiplications in a network 10–100× faster than a CPU. Using one in PyTorch takes two lines: move the model to the device once, and move each batch to the device inside the loop. The rule that produces most device errors is simple: every tensor in one operation must be on the same device. The other rule: a tensor on the GPU cannot be turned into a NumPy array or plotted until it comes back with .cpu(). For tabular MLPs of the size in this chapter, a CPU is fine and often faster once you count the data-transfer overhead; GPUs pay off for images, text, and anything with millions of parameters.

Mixed precision

Modern GPUs multiply 16-bit floats several times faster than 32-bit ones and use half the memory. Automatic mixed precision (torch.autocast) runs the matmuls in float16 or bfloat16 and keeps the numerically sensitive pieces (loss, normalization, optimizer state) in float32. With float16 small gradients underflow to zero, so a GradScaler multiplies the loss by a large factor before backward() and divides the gradients afterwards. bfloat16 has the range of float32 and needs no scaler; prefer it on hardware that supports it. On a CPU none of this helps, so the code below is written to switch itself off.

Checkpointing and saving models

Save the state_dict, not the model object: it is a plain dictionary of tensors, robust to code refactors, and loads into any module with matching parameter names. To resume training rather than merely reuse weights, you must also save the optimizer state (Adam's moment estimates), the scheduler state and the epoch counter, or the resumed run will behave differently from an uninterrupted one. Save a checkpoint every epoch and keep the best-validation one separately; you will need it after a preemption, a crash, or a bad late epoch.

# Device placement, mixed precision and checkpointing (needs a GPU to matter; shown for reference)
import torch, torch.nn as nn

device = "cuda" if torch.cuda.is_available() else "cpu"
model = MLP(30).to(device)                              # move parameters once
opt = torch.optim.AdamW(model.parameters(), lr=1e-3, weight_decay=1e-2)
sched = torch.optim.lr_scheduler.CosineAnnealingLR(opt, T_max=50)
scaler = torch.amp.GradScaler(enabled=(device == "cuda"))   # stops fp16 grads underflowing

for epoch in range(50):
    for xb, yb in train_dl:
        xb, yb = xb.to(device), yb.to(device)            # move each batch
        with torch.autocast(device_type=device, dtype=torch.float16, enabled=(device == "cuda")):
            loss = loss_fn(model(xb), yb)                # matmuls run in fp16, loss in fp32
        opt.zero_grad(set_to_none=True)
        scaler.scale(loss).backward()                    # scale loss up before backward
        scaler.unscale_(opt)                             # unscale so clipping sees true grads
        nn.utils.clip_grad_norm_(model.parameters(), 1.0)
        scaler.step(opt); scaler.update()                # skips the step if grads overflowed
    sched.step()

    # checkpoint EVERYTHING needed to resume, not just the weights
    torch.save({"epoch": epoch, "model": model.state_dict(), "opt": opt.state_dict(),
                "sched": sched.state_dict(), "scaler": scaler.state_dict()}, "ckpt.pt")

# resume later
ckpt = torch.load("ckpt.pt", map_location=device)
model.load_state_dict(ckpt["model"]); opt.load_state_dict(ckpt["opt"])
sched.load_state_dict(ckpt["sched"]); start_epoch = ckpt["epoch"] + 1

# reproducibility: seeds first, determinism second (slower, and not always available)
torch.manual_seed(0); import random, numpy as np; random.seed(0); np.random.seed(0)
torch.use_deterministic_algorithms(True, warn_only=True)

Reproducibility

Seed everything — torch, numpy, Python's random, and the DataLoader's workers — and you will get the same run twice on the same machine with the same library versions. You will not get bit-identical results across GPU models, driver versions, or between CPU and GPU: some CUDA kernels (and some CPU ones, depending on thread count) sum in a nondeterministic order. torch.use_deterministic_algorithms(True) forces deterministic kernels where they exist, at a speed cost, and raises for the operations that have none. The honest position at work: seed for debuggability, report results as a mean over 3–5 seeds, and treat run-to-run variance of a fraction of a percent as noise rather than as evidence.

Common mistake

Comparing two configurations with one run each. On small datasets the seed alone can move validation accuracy by a percentage point or more. Before concluding that "dropout 0.2 beats 0.3", run each three times and look at the spread. Most of the hyperparameter folklore you will read online is single-seed noise.

When to use an MLP vs a gradient-boosted tree on tabular data

Be honest with yourself here, because the field has measured this repeatedly. On typical business tables (tens of columns, thousands to a few million rows, mixed numeric and categorical, missing values, skewed distributions), a well-tuned gradient-boosted tree (Chapter 10) matches or beats a well-tuned MLP most of the time, with less preprocessing, less tuning, and faster training. Quiz

Check your understanding

1. Your training loop omits opt.zero_grad(). What happens?

Autograd adds to .grad by design. Without clearing, every update is driven by a growing sum of stale gradients; training degrades silently. (Some code exploits this deliberately for gradient accumulation across micro-batches, then clears every k steps.)

2. A colleague's binary classifier ends with nn.Sigmoid() and is trained with nn.BCEWithLogitsLoss(). The loss decreases but accuracy is mediocre. What is wrong?

BCEWithLogitsLoss applies its own sigmoid. A second one compresses the outputs into (0, 1) before the loss sees them, which caps the achievable confidence and shrinks gradients. Remove the final activation.

3. A 10-class classifier prints a cross-entropy loss of 2.30 before any training. What does that tell you?

A network with small initial weights predicts roughly uniform probabilities; cross-entropy of a uniform guess over C classes is ln(C). A much larger value means outputs are too large at init; a much smaller value suggests leakage.

4. Training loss is jagged, stuck well above where a simple baseline gets, and occasionally jumps to NaN. The first thing to try is…

Jagged, non-decreasing loss and NaNs are the signature of a learning rate that is too high (Figure 16.4, Figure 16.9 panel C). Clipping prevents the single catastrophic step; lowering the rate fixes the cause.

5. Why does batch norm require calling model.eval() before validation?

In train mode batch norm uses the mean/variance of the mini-batch, so a prediction depends on which other examples are in the batch. In eval mode it uses the running averages accumulated during training. Gradient computation is a separate switch (torch.no_grad()).

6. You have 40,000 rows, 25 numeric and categorical columns, a few missing values, and a week. The most defensible first model is…

On ordinary tabular data a GBM is the strongest accuracy-per-effort choice and handles missing values and categoricals natively. Build it first; an MLP is justified only if it beats that baseline on the same validation split.

Exercises

Exercise 16.1 — Break the loop on purpose

Take the training loop from §3 and introduce each of these bugs one at a time, re-running each time: (a) delete opt.zero_grad(); (b) add nn.Sigmoid() as the final layer; (c) pass y_tr with shape (n,) instead of (n, 1); (d) set lr=1.0. For each, record what the loss curve looks like at epochs 5, 10, 15 and which check from the §8 recipe would have caught it.

Show answer

(a) Loss falls for a few batches then stalls or oscillates as stale gradients accumulate; the gradient-norm log grows steadily — caught by "plot grads". (b) Loss decreases slowly and plateaus higher (around 0.3–0.4 instead of 0.15); the model cannot produce confident predictions — caught by the "loss at init" check being suspicious (≈ 0.63 rather than 0.69, since squashed outputs are pulled toward 0.5 twice) and by "overfit one batch" failing to reach ~0. (c) BCEWithLogitsLoss raises a shape-mismatch error; with MSELoss it would broadcast silently — caught by "check shapes". (d) Loss jumps around and typically hits NaN within an epoch — the learning-rate signature; caught by the NaN check and Figure 16.9 C.

Exercise 16.2 — An LR range test by hand

On the breast-cancer MLP from §7, run 100 mini-batch steps with the learning rate growing geometrically from 10−5 to 10 (multiply by ≈ 1.15 each step). Record (lr, loss) pairs and plot loss against log(lr). Identify the steepest-descent region and the explosion point. Then train normally at one-tenth of the "loss minimum" learning rate and at the explosion point, and compare.

Show answer

You should see loss flat around 0.69 for lr < 10−4, a steep drop between roughly 10−3 and 3×10−2, a minimum around 10−2–3×10−2, and divergence above ≈ 0.1–0.3 (exact values depend on the seed and batch). A constant rate of ≈ 2×10−3 trains smoothly to ~0.06 loss; the explosion-point rate oscillates or NaNs. The test costs seconds and replaces guessing.

Exercise 16.3 — Do it at work: MLP vs GBM on your own table

Take a tabular dataset you actually use (or load_wine if you have none to hand). Build a proper split (Chapter 7), a scaled MLP using the §10 default configuration with early stopping, and a LightGBM or XGBoost model with defaults. Compare on the held-out set with the metric that matters to your business, run the MLP with three seeds, and write a five-line memo: which model, by how much, with what uncertainty, at what training cost, and what you would need to change for the other one to win.

Show answer

There is no fixed answer, but expect: the GBM within a few minutes matches or beats the untuned MLP; the MLP's three seeds spread by a noticeable fraction of the gap; the MLP becomes competitive only after scaling, embeddings for high-cardinality columns, and some tuning of lr and weight decay. If the MLP wins clearly, check for leakage in your features first, then for high-cardinality categoricals — that is the usual honest reason.

Chapter summary

  • Autograd records every tensor operation in a graph; backward() replays it in reverse. You write the forward pass only. Gradients accumulate, so clear them every step.
  • The cast: Tensor, Module (parameters, state_dict), loss, optimizer, Dataset/DataLoader, device. Scale inputs; use float32; labels int64 for cross-entropy.
  • The loop: forward → loss → zero_grad → backward → step, per batch; then eval() + no_grad() validation and early stopping with the best state_dict restored.
  • Models output logits. BCEWithLogitsLoss and CrossEntropyLoss own the sigmoid/softmax. Never apply both.
  • Momentum averages gradients so ravine bounces cancel; Adam also normalizes step size per weight; AdamW decouples weight decay. Default: AdamW, lr 1e-3, wd 1e-2.
  • The learning rate is the hyperparameter. Too high: jagged, NaN. Too low: crawl. Measure with a range test; schedule with warmup + cosine or ReduceLROnPlateau; re-tune when batch size changes.
  • He/Xavier init keeps activation variance ≈ 1 through depth; batch norm (across the batch) and layer norm (across features) keep it there during training. Call eval() before inference.
  • Regularizers stack: weight decay, dropout 0.1–0.3, augmentation, early stopping, clipping at 1.0.
  • Before a real run: check shapes, loss at init ≈ ln(C), overfit one batch, watch NaNs and gradient norms. Then read the curves: healthy / overfitting / LR too high / underfitting.
  • Save state_dict plus optimizer and scheduler state; seed everything but report over several seeds. On plain tables, the GBM is the baseline an MLP must beat.
