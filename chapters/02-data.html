Data: The Raw Material

Models are only ever as good as the table they were trained on. This chapter teaches you to read a dataset like an expert: what its columns really are, how to split it so your results are honest, how to spot the leaks that make a model look brilliant right up until launch day, and how to audit data quality before you trust a single number.

Beginner ⏱ 70 min read · Prereqs: Ch 1

By the end of this chapter you will be able to

  • Classify any column (numeric, categorical, boolean, datetime, text, ID) and say what the model can and cannot do with it.
  • Split a dataset into train / validation / test correctly, and choose random, stratified, time-based or group splits for the right reasons.
  • Recognise the three kinds of data leakage and run a "smell test" on any suspiciously good result.
  • Perform a first-pass exploratory data analysis (EDA) in pandas in under 30 minutes and know which findings matter.
  • Catalogue data-quality defects (sentinels, units, encodings, time zones) and fix them without silently destroying information.
  • Judge whether you have enough labelled data, and whether the labels mean what people think they mean.

1. The kinds of data ML eats

Chapter 1 told you a model is a function learned from data. Here is the practical corollary: every model in this book, from linear regression to a transformer, ultimately consumes a matrix of numbers. Rows are examples, columns are features. The whole art of "data" is getting the messy world into that matrix without lying to yourself about what the numbers mean.

Data arrives in four common shapes, and each one needs a different route into the matrix:

Structured data lives in tables with a schema: every row has the same columns and each column has a type. Databases, spreadsheets and CSV exports are structured. Unstructured data has no fixed schema: emails, support tickets, photos, call recordings, PDFs. Roughly 80% of the data inside a company is unstructured, and roughly 80% of the ML that actually ships at most companies is done on structured tables. That asymmetry is not a coincidence: tables are where the labels are, and where a model can be plugged into a decision.

Explain it like I'm 9

Imagine a robot that can only eat spreadsheets. A spreadsheet goes straight in. A story has to be chopped into words and counted ("the word crash appears twice") before the robot can eat it. A photo has to be turned into a huge grid of brightness numbers. A temperature chart has to be sliced into "what happened in the last 7 days" chunks. Different food, same robot.

The rest of this chapter focuses on tabular data, because that is where you will spend most of your working life, and because every lesson here (splits, leakage, quality, labels) applies unchanged to text and images once they have been converted.

2. Column types, and the ID trap

Before you model anything, walk every column and answer one question: what kind of thing is this? The answer decides how the column must be encoded, which statistics make sense, and whether it belongs in the model at all.

Common mistake

Leaving IDs in the feature matrix. A customer ID, order number or row index is unique per row, so a flexible model (a tree, a boosting model) can memorise "ID 100042 → churned." Training accuracy shoots to 100%, test accuracy is garbage, and because IDs are often assigned sequentially they can also smuggle in time ("high IDs are recent customers, and recent customers churn less") that will not hold next year. IDs are for joining tables and for grouping rows in a split; they are never features. The same trap applies to anything that is unique per row: free-text notes, timestamps to the second, file names.

At work

Ask for the data dictionary (what each column means, its unit, who produces it, when it is written) before you ask for the data. If one does not exist, write it as you go: a table with column name, type, unit, source system, and "known when?" (see §5). Half the modelling disasters I have reviewed trace back to a column whose meaning nobody actually checked.

3. The churn dataset we will use all chapter

Every idea from here on is illustrated on one dataset: 2,000 customers of a subscription service, and whether each one cancelled (churned) in the following quarter. It is synthetic, so we know the truth, but its columns are the ones you will actually find in a customer table. Recall from Chapter 1: features are the columns the model may look at (X), and the label is the column we want to predict (y).

# The churn dataset used throughout this chapter (synthetic, but realistic columns)
import numpy as np, pandas as pd
rng = np.random.default_rng(42)
n = 2000
df = pd.DataFrame({
    "customer_id":      np.arange(100001, 100001 + n),
    "signup_date":      pd.to_datetime("2021-01-01") + pd.to_timedelta(rng.integers(0, 1400, n), "D"),
    "plan":             rng.choice(["basic", "plus", "premium"], n, p=[.5, .3, .2]),
    "age":              rng.integers(18, 75, n),
    "tenure_months":    rng.integers(1, 60, n),
    "monthly_spend":    rng.gamma(4, 12, n).round(2),
    "support_calls":    rng.poisson(1.2, n),
    "days_since_login": rng.integers(0, 90, n),
    "autopay":          rng.random(n) < 0.6,
})
# the hidden truth: churn is driven by inactivity, support pain, short tenure, no autopay
logit = -2.6 + 0.035*df.days_since_login + 0.5*df.support_calls - 0.02*df.tenure_months - 0.6*df.autopay
df["churned"] = (rng.random(n) < 1/(1+np.exp(-logit))).astype(int)

print(df.shape)
print(df.dtypes)
print(f"churn rate = {df.churned.mean():.1%}")
# (2000, 10)
# customer_id                  int64
# signup_date         datetime64[us]
# plan                           str
# age                          int64
# tenure_months                int64
# monthly_spend              float64
# support_calls                int64
# days_since_login             int64
# autopay                       bool
# churned                      int64
# churn rate = 26.2%

Walk the columns with Figure 2.2 in hand: customer_id is an identifier (drop). signup_date is a datetime (derive tenure; keep for time splits). plan is nominal categorical, or ordinal if you believe basic < plus < premium is a meaningful order. age, tenure_months, monthly_spend are numeric. support_calls is a count. days_since_login is numeric but really a recency signal. autopay is boolean. churned is the label: binary, so this is classification, and at 26% positive it is moderately imbalanced (a model that always says "stays" is already 74% accurate; remember that when you read accuracy numbers later).

Key idea

A dataset is not a pile of numbers; it is a set of claims about the world ("this customer made 3 calls", "this customer churned"). Every column was produced by some process at some time. Knowing that process, especially when each value becomes known, is what separates a feature you can use from a leak that will sink the project.

4. Train, validation, test: holding data back

You have 2,000 labelled customers. The temptation is to train on all of them; more data, better model. But then how would you know how good the model is? Scoring it on the same rows it memorised tells you nothing about the next 2,000 customers, which is the only thing anyone cares about (Chapter 1 called this generalization). So we hold data back.

Explain it like I'm 9

If a teacher gives you the exact exam questions to study, then gives you the same exam, your 100% proves nothing. A fair teacher gives you practice problems (train), a few mock exams to see which study method works (validation), and keeps the real exam locked in a drawer until the very end (test). You only open the drawer once.

What each set is for

  1. Training set. The rows the algorithm sees while fitting parameters. Bigger is better, up to a point (§8).
  2. Validation set. Rows you score on while you develop: comparing logistic regression with a forest, picking a tree depth, deciding whether a feature helps. Because you make dozens of choices by looking at this score, it drifts optimistic: you are, in effect, fitting yourself to it. In Chapter 7 you will usually replace a single validation set with k-fold cross-validation, which uses the training data more efficiently; the role stays the same.
  3. Test set. Rows nobody looks at until the model is final. It exists precisely because the validation score is no longer trustworthy. Score once. If you then go back and change the model "because the test score was disappointing", the test set has become a second validation set and you no longer have an honest estimate.

Typical proportions

Dataset sizeTrain / Val / TestWhy
< 5,000 rows60 / 20 / 20, or 80 / 20 with k-fold CV inside the 80Every row is precious; use CV so no row is wasted on a single validation split.
5,000 – 500,00070 / 15 / 15 or 80 / 10 / 10A few thousand test rows give a tight enough estimate.
Millions98 / 1 / 11% of 10 million is 100,000 rows: more than enough to estimate a score to ±0.3 points.

The proportions are a trade-off, and the widget below lets you feel it. A small test set gives a noisy score: with 100 test rows, an accuracy of 75% has a 95% confidence interval of roughly ±8.5 points, so you literally cannot tell a 72% model from a 78% one. A small training set gives a weaker model. Neither number is free.

The math (optional)

The accuracy you measure on a test set is a sample proportion. Its standard error, and the usual 95% interval, are

SE = √( p(1−p) / ntest ), 95% CI ≈ p ± 1.96 · SE

p is the measured accuracy (as a fraction), ntest is the number of test rows, and 1.96 is the normal-distribution multiplier for 95% (Chapter 3). With p = 0.75 and n = 400 the half-width is 1.96 · √(0.1875/400) ≈ 0.042, i.e. ±4.2 points. Quadrupling the test set halves the interval.

Random, stratified, time-based, group: which split, and when it is mandatory

How you choose the rows for each set matters as much as the proportions. A plain random shuffle is the default, and it is wrong more often than beginners expect. The question to ask is: "When this model is used for real, how will the new rows differ from the rows I trained on?" Your split must reproduce that difference.

# A stratified 60 / 20 / 20 split, done as two cuts (re-creates df from the block above)
import numpy as np, pandas as pd
from sklearn.model_selection import train_test_split
rng = np.random.default_rng(42); n = 2000
df = pd.DataFrame({"customer_id": np.arange(100001, 100001+n),
    "signup_date": pd.to_datetime("2021-01-01") + pd.to_timedelta(rng.integers(0, 1400, n), "D"),
    "plan": rng.choice(["basic","plus","premium"], n, p=[.5,.3,.2]), "age": rng.integers(18, 75, n),
    "tenure_months": rng.integers(1, 60, n), "monthly_spend": rng.gamma(4, 12, n).round(2),
    "support_calls": rng.poisson(1.2, n), "days_since_login": rng.integers(0, 90, n), "autopay": rng.random(n) < 0.6})
logit = -2.6 + 0.035*df.days_since_login + 0.5*df.support_calls - 0.02*df.tenure_months - 0.6*df.autopay
df["churned"] = (rng.random(n) < 1/(1+np.exp(-logit))).astype(int)

X = df.drop(columns=["churned"]); y = df["churned"]
# cut 1: 80% train+val, 20% test.  stratify=y keeps the churn rate equal on both sides.
X_trval, X_test, y_trval, y_test = train_test_split(X, y, test_size=0.20, stratify=y, random_state=0)
# cut 2: 25% of the remaining 80% becomes validation  ->  60 / 20 / 20 overall
X_train, X_val, y_train, y_val = train_test_split(X_trval, y_trval, test_size=0.25, stratify=y_trval, random_state=0)
for name, part in [("train", y_train), ("val", y_val), ("test", y_test)]:
    print(f"{name:5s} n={len(part):4d}  churn rate={part.mean():.3f}")
# train n=1200  churn rate=0.262
# val   n= 400  churn rate=0.263
# test  n= 400  churn rate=0.263
# Time-based and group splits on the same data (df built exactly as above)
import numpy as np, pandas as pd
from sklearn.model_selection import GroupShuffleSplit
rng = np.random.default_rng(42); n = 2000
df = pd.DataFrame({"signup_date": pd.to_datetime("2021-01-01") + pd.to_timedelta(rng.integers(0, 1400, n), "D")})

# --- time-based: sort by date, cut at a date, never shuffle
df = df.sort_values("signup_date")
cut = df["signup_date"].quantile(0.8)
train_t, test_t = df[df.signup_date < cut], df[df.signup_date >= cut]
print("time split :", len(train_t), len(test_t), "| test starts", test_t.signup_date.min().date())

# --- group split: pretend customers belong to ~300 companies; all rows of a company stay together
df["company_id"] = rng.integers(0, 300, n)
gss = GroupShuffleSplit(n_splits=1, test_size=0.2, random_state=0)
tr_idx, te_idx = next(gss.split(df, groups=df["company_id"]))
overlap = set(df.company_id.iloc[tr_idx]) & set(df.company_id.iloc[te_idx])
print("group split:", len(tr_idx), len(te_idx), "| companies in both:", len(overlap))
# time split : 1600 400 | test starts 2024-01-26
# group split: 1624 376 | companies in both: 0
At work

Decide the split strategy in the problem-definition meeting, not in the notebook. Ask: "Will this model score customers we have never seen (→ group split)? Will it score next month's data (→ time split)? Both (→ group-aware time split)?" Then write the split code once, save the row IDs of each set to a file, and make every experiment load the same file. Re-splitting with a different seed for each experiment is how teams end up comparing models on different data without noticing.

5. Data leakage: the #1 silent killer

Leakage is when information that would not be available at prediction time sneaks into training. The model learns to use it, scores brilliantly on your test set (which has the same leak), and then falls apart in production where the information is missing. It is silent because nothing errors. In fact everything looks better than usual. An unusually good result is the main symptom.

Explain it like I'm 9

You are trying to guess whether it will rain tomorrow. Your friend hands you a list of clues, and one of the clues is "did people carry umbrellas tomorrow?" You will guess perfectly every time, and learn nothing about weather. On the day you actually have to predict, that clue does not exist yet. That clue is a leak.

Three realistic examples

1. The refund column (target leakage)

A churn model includes refund_issued. Refunds are processed after a cancellation request, so the column is essentially the label with a delay. Offline AUC 0.94. In production, the model must score customers who have not cancelled yet, so the column is always 0; AUC collapses to what the other features give, around 0.73. The code below reproduces this exactly.

2. Feature selection before the split (contamination)

A team with 300 patients and 2,000 gene-expression features picks the 20 genes most correlated with the disease using all 300 patients, then cross-validates a classifier on those 20. Cross-validated accuracy: 75%. The genes were chosen using the held-out patients' labels, so every fold has already seen its own test answers. Done correctly (selection inside each fold), accuracy is 50% because in this example the data were pure noise.

3. Averages that include tomorrow (temporal leakage)

A demand forecast uses "average daily sales of this product" as a feature, computed over the whole dataset. For a row from March, that average includes April through December. The model learns that products with high averages sell well, which is trivially true and completely useless on the day you actually forecast. Fix: rolling averages that end strictly before each row's date.

# Example 1 reproduced: a leaky feature that is a consequence of the label
import numpy as np, pandas as pd
from sklearn.model_selection import train_test_split
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.metrics import accuracy_score, roc_auc_score
rng = np.random.default_rng(42); n = 2000
df = pd.DataFrame({"customer_id": np.arange(100001, 100001+n),
    "signup_date": pd.to_datetime("2021-01-01") + pd.to_timedelta(rng.integers(0, 1400, n), "D"),
    "plan": rng.choice(["basic","plus","premium"], n, p=[.5,.3,.2]), "age": rng.integers(18, 75, n),
    "tenure_months": rng.integers(1, 60, n), "monthly_spend": rng.gamma(4, 12, n).round(2),
    "support_calls": rng.poisson(1.2, n), "days_since_login": rng.integers(0, 90, n), "autopay": rng.random(n) < 0.6})
logit = -2.6 + 0.035*df.days_since_login + 0.5*df.support_calls - 0.02*df.tenure_months - 0.6*df.autopay
df["churned"] = (rng.random(n) < 1/(1+np.exp(-logit))).astype(int)

# refunds are issued BECAUSE the customer cancelled: 75% of churners, 3% of stayers
df["refund_issued"] = (((df.churned == 1) & (rng.random(n) < 0.75)) |
                      ((df.churned == 0) & (rng.random(n) < 0.03))).astype(int)
honest = ["age", "tenure_months", "monthly_spend", "support_calls", "days_since_login", "autopay"]
leaky  = honest + ["refund_issued"]
y = df["churned"]
for name, cols in [("honest", honest), ("leaky ", leaky)]:
    Xtr, Xte, ytr, yte = train_test_split(df[cols], y, test_size=0.2, stratify=y, random_state=0)
    m = GradientBoostingClassifier(random_state=0).fit(Xtr, ytr)
    print(f"{name}: test acc={accuracy_score(yte, m.predict(Xte)):.3f}  AUC={roc_auc_score(yte, m.predict_proba(Xte)[:,1]):.3f}")
# honest: test acc=0.735  AUC=0.729
# leaky : test acc=0.925  AUC=0.939

Note what the test set did not do: it did not catch the leak. The test rows have the same refund column, so the leaky model looks wonderful on them. A held-out set protects you from overfitting, not from leakage. Only understanding where each column comes from does that. The widget shows what happens next: the model ships, the refund column is 0 for every customer who has not cancelled yet, and the score falls to roughly what the honest features alone can deliver, or worse, because the model learned to lean on a column that no longer varies.

# Example 2 reproduced: feature selection outside vs. inside cross-validation, on PURE NOISE
import numpy as np
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.model_selection import cross_val_score, StratifiedKFold
rng = np.random.default_rng(0)
X = rng.normal(size=(300, 2000))          # 300 patients, 2000 "genes" of random noise
y = rng.integers(0, 2, 300)               # coin-flip labels: there is NOTHING to learn
cv = StratifiedKFold(5, shuffle=True, random_state=0)

# WRONG: choose the 20 "best" features using ALL rows, then cross-validate
X_sel = SelectKBest(f_classif, k=20).fit_transform(X, y)
wrong = cross_val_score(LogisticRegression(), X_sel, y, cv=cv).mean()
# RIGHT: selection lives inside the Pipeline, so each fold selects using only its own training rows
right = cross_val_score(make_pipeline(SelectKBest(f_classif, k=20), LogisticRegression()), X, y, cv=cv).mean()
print(f"selection outside CV: {wrong:.2f}   selection inside pipeline: {right:.2f}   (truth: 0.50)")
# selection outside CV: 0.75   selection inside pipeline: 0.50   (truth: 0.50)
Key idea

Anything that is fitted must be fitted on training rows only: scalers, imputers, encoders, feature selectors, the model itself. The mechanical way to guarantee this is to put every fitted step inside a scikit-learn Pipeline and call .fit() exactly once, on the training set. Chapter 8 makes this the default way you build everything.

The leakage smell test

Run this checklist whenever a result looks better than you expected, and once more before you present anything.

  1. Is the score too good? Accuracy above 95%, AUC above 0.95, or a big jump after adding one feature: assume leakage until proven otherwise. Real business problems are noisy.
  2. Known when? For every feature, write the moment its value is written to the database. If that moment is after the moment you will make the prediction, it leaks.
  3. Is any feature caused by the label? Refunds, cancellation reasons, "account closed" flags, collections calls, complaint tickets filed after the decision. Anything downstream of the outcome.
  4. Which one feature does the model love? Look at feature importance (Chapter 20). If one column dominates, look at it very hard.
  5. Was anything fitted on all rows? Scaling, imputation, target encoding, feature selection, dimensionality reduction, oversampling: all of them, before or after the split?
  6. Are there duplicates or near-duplicates across the split? Same customer, same image with a different filename, same document re-uploaded.
  7. Is time ordered and did you shuffle it? If rows have dates, does your test set sit strictly after your training set?
  8. Does the label define the population? If the dataset only contains customers who called support, a model trained on it will not work on customers who did not.
Common mistake

Oversampling the minority class before splitting. Techniques such as SMOTE create synthetic churners that are interpolations of real churners. If you oversample and then split, copies of test-set churners end up in training. Accuracy on the "test" set becomes meaningless. Always split first; resample only the training fold, inside a pipeline (Chapter 13).
