Overfitting, Bias–Variance & Validation

A model that scores 99% on the data it was trained on has told you nothing. This chapter is about the only thing that matters — performance on data the model has never seen — and the discipline that makes that number trustworthy: diagnosing bias and variance, regularizing, and validating without fooling yourself.

1. The only thing that matters

Chapters 5 and 6 taught you to fit models and to measure them. This chapter asks the question that separates people who build models from people who build models that work: measured on what?

A model is a function learned from a training set. If you evaluate it on that same training set, you are asking "how well did you memorize the answer key?" The answer is always flattering and almost always irrelevant. The model will be used on tomorrow's customers, next month's transactions, new patients. The number you care about is the error on data the model has never seen — generalization error — and the only honest way to estimate it is to hold data back and never let the model learn from it.

Why does training error lie? Because a flexible model can fit two things at once: the real pattern (which repeats in new data) and the random noise in the particular rows it was given (which does not). Training error rewards fitting both. Test error rewards only the first. The gap between them is the model's dishonesty, and everything in this chapter is about measuring and shrinking that gap.

Explain it like I'm 9

Two kids study for a math test. One learns how to do the problems. The other memorizes the answers to the practice sheet: "question 3 is 42". Both get 100% on the practice sheet. Only one passes the real test, which has different numbers. Training error is the practice sheet. Test error is the real exam. The memorizer has overfit.

Here is the same lesson in numbers. A deep decision tree (Chapter 9) can memorize any training set, so its training accuracy is 100% by construction; its validation accuracy on the breast-cancer data is around 92%. A regularized logistic regression trains to about 98% and validates at about 97%. The tree looks better on the training set and is worse where it counts. If you remember one sentence from this chapter: never report a training-set number as if it were performance.

Key idea

Three datasets, three jobs. Training set: the model learns from it. Validation set: you learn from it — which model, which hyperparameters, which threshold. Test set: nobody learns from it; it is opened once, at the end, to report the number. If you peek at the test set to make a decision, it has silently become a validation set and you no longer have an honest estimate.

2. Underfitting and overfitting

Take fourteen noisy measurements of a smooth curve and fit polynomials of increasing degree (Chapter 5's PolynomialFeatures). Three regimes appear, and you will meet them in every model family for the rest of the book:

Underfitting

The model is too simple to capture the pattern. Both training and test error are high. Symptom: adding more data does not help; the model has already learned everything it is capable of learning.

Good fit

The model captures the repeatable pattern and ignores the noise. Training error is a bit below test error (a small gap is normal and healthy), and test error is close to the irreducible noise floor.

Overfitting

The model is flexible enough to memorize noise. Training error is near zero; test error is high and rising with complexity. Symptom: a large train–test gap that shrinks when you add data or simplify the model.

Plot both errors against model complexity and you get the most important picture in applied ML: training error falls forever, test error is U-shaped, and the job is to find the bottom of the U.

Drive it yourself. The widget fits a polynomial to 30 noisy training points (blue) and evaluates it on 30 held-out test points (orange) that came from the same curve. Watch the bars as you raise the degree: the blue bar (training error) only ever shrinks; the orange bar (test error) bottoms out around degree 3–5 and then explodes.

# Polynomial degree sweep: training error falls forever; validation error turns back up
import numpy as np
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import PolynomialFeatures, StandardScaler
from sklearn.linear_model import LinearRegression
from sklearn.model_selection import validation_curve, KFold

rng = np.random.default_rng(0)
X = rng.uniform(0, 1, 40)[:, None]                            # 40 points on [0, 1]
y = np.sin(2 * np.pi * X.ravel()) + rng.normal(0, 0.3, 40)    # true curve + noise

model = make_pipeline(PolynomialFeatures(), StandardScaler(), LinearRegression())
degrees = [1, 2, 3, 5, 9, 12]
cv = KFold(n_splits=5, shuffle=True, random_state=0)
tr, va = validation_curve(model, X, y, param_name="polynomialfeatures__degree",
                          param_range=degrees, cv=cv, scoring="neg_mean_squared_error")
print("degree   train MSE   valid MSE")
for d, t, v in zip(degrees, -tr.mean(axis=1), -va.mean(axis=1)):
    print(f"{d:6d}   {t:9.3f}   {v:9.3f}")
print("(noise variance is 0.3² = 0.09: no model can beat that on validation)")

Common mistake

Reading "degree 12 has the lowest training error" as "degree 12 is the best model". In the output above the training MSE keeps falling all the way to degree 12 while the validation MSE has been climbing since degree 3. Choose hyperparameters by the validation column, always. The training column is only useful for diagnosing the gap.

3. Bias and variance, precisely

"Underfitting" and "overfitting" describe symptoms. Bias and variance name the two underlying causes of error, and naming them tells you what to do about them. The classic picture is a dartboard.

Explain it like I'm 9

You weigh yourself on two bathroom scales ten times each. Scale A always says 3 kg too much, every time: that is bias — consistently wrong in the same direction. Scale B is right on average, but each reading is off by a random few kilos: that is variance — unreliable from try to try. A great scale has neither. A cheap one has both.

Now the precise version. Fix a test input x. Imagine drawing many training sets, fitting your model to each, and looking at the spread of predictions f̂(x). The expected squared error at x splits cleanly into three pieces:

The math (optional)
E[(y − f̂(x))²] = Bias[f̂(x)]² + Var[f̂(x)] + σ²
Bias[f̂(x)] = E[f̂(x)] − f(x) Var[f̂(x)] = E[(f̂(x) − E[f̂(x)])²]

f(x) is the true (unknown) function; y = f(x) + ε is what we observe, with noise ε of variance σ². f̂(x) is our model's prediction, which is random because the training set is random; E[·] averages over all the training sets we might have drawn. Bias is the systematic gap between the average prediction and the truth: a model family too simple to represent f has bias no amount of data can remove. Variance is how much the prediction jumps around from one training set to another: a model flexible enough to chase noise has high variance, and more data or regularization shrinks it. σ² is the irreducible noise: no model, however good, beats it (the dashed floor in Figure 7.2). The three terms add, so total error can only be reduced by attacking bias or variance — and most levers that lower one raise the other. That is the bias–variance tradeoff.

Why this matters in practice: the decomposition tells you that "make the model bigger" and "make the model smaller" are not opposites of one lever but two different cures for two different diseases. Bigger models lower bias and raise variance; smaller models (and regularization) lower variance and raise bias; more data lowers variance without touching bias. Get the diagnosis right and the treatment is obvious. Get it wrong and you will spend a week collecting data for a model that was underfitting all along.

Key idea

Modern flexible models (boosted trees, neural networks) live on the high-variance side by default. The practical craft of ML is therefore mostly variance control: regularization, early stopping, ensembling (Chapter 10 — averaging many high-variance models is a direct attack on the variance term), and getting more data. Bias problems are rarer and usually show up as "I need a better feature", which is Chapter 8.

Deep dive: the bias–variance decomposition, derived 9 min
Explain it like I'm 9

Ask a hundred kids to guess the number of sweets in a jar after each looks at a different photo of it. Two things make the guesses wrong: all of them might lean too low because the photo hides the back of the jar (that is bias, the same for everyone), and each kid's guess wobbles depending on which photo they got (that is variance). And even if every guess were perfect, the jar might get one sweet added after the photo was taken (that is noise). Squared error adds those three up.

Precisely. Fix a test input x. The observed target is y = f(x) + ε with noise ε of mean 0 and variance σ². The model's prediction f̂(x) depends on the random training set; write f̄(x) = E[f̂(x)] for its average over training sets. Then:

The math (optional)

Step 1, add and subtract f̄. y − f̂ = (f − f̄) + (f̄ − f̂) + ε. The three brackets are: the systematic gap (a fixed number for this x), the fluctuation of this particular fit around the average fit, and the noise.

Step 2, square and take expectations. E[(y − f̂)²] = E[(f − f̄)²] + E[(f̄ − f̂)²] + E[ε²] + 2·(cross terms).

Step 3, the cross terms vanish. (f − f̄) is a constant, and E[f̄ − f̂] = f̄ − E[f̂] = 0, so the first cross term is 0. ε is independent of the training set and has mean 0, so E[(f − f̄) ε] = 0 and E[(f̄ − f̂) ε] = E[f̄ − f̂] · E[ε] = 0.

Step 4, name the survivors. E[(f − f̄)²] = (f̄ − f)² = Bias²; E[(f̄ − f̂)²] = Var[f̂]; E[ε²] = σ². Hence

E[(y − f̂(x))²] = Bias[f̂(x)]² + Var[f̂(x)] + σ²

Averaging over test inputs gives the same identity for the expected test MSE. Two remarks: the decomposition is exact for squared error and only approximate for other losses (for log-loss and 0/1 loss the pieces interact); and "E over training sets" is a thought experiment you can never run on real data, which is why the next code block runs it on simulated data instead.

# Bias², variance and noise, estimated by simulation: many training sets, the same test inputs
import numpy as np
rng = np.random.default_rng(0)
f = lambda x: np.sin(2 * np.pi * x); sigma = 0.3
x_test = np.linspace(0.05, 0.95, 50); f_test = f(x_test)

def fit_and_predict(degree, n=30):
    x = rng.uniform(0, 1, n); y = f(x) + rng.normal(0, sigma, n)          # one random training set
    return np.polyval(np.polyfit(x, y, degree), x_test)                    # its predictions at the test inputs

for degree in (1, 3, 9):
    preds = np.array([fit_and_predict(degree) for _ in range(500)])       # 500 training sets -> 500 curves
    bias2 = np.mean((preds.mean(axis=0) - f_test) ** 2)                    # (average curve − truth)², averaged over x
    var   = np.mean(preds.var(axis=0))                                     # scatter of the curves, averaged over x
    y_test = f_test + rng.normal(0, sigma, preds.shape)                    # fresh noisy targets for every curve
    mse   = np.mean((preds - y_test) ** 2)                                 # the expected test error, measured directly
    print(f"degree {degree}:  bias² = {bias2:.3f}   variance = {var:.3f}   noise = {sigma**2:.3f}   "
          f"sum = {bias2 + var + sigma**2:.3f}   measured test MSE = {mse:.3f}")
# degree 1:  bias² = 0.155   variance = 0.022   noise = 0.090   sum = 0.267   measured test MSE = 0.267
# degree 3:  bias² = 0.003   variance = 0.013   noise = 0.090   sum = 0.106   measured test MSE = 0.106
# degree 9:  bias² = 0.017   variance = 3.593   noise = 0.090   sum = 3.700   measured test MSE = 3.711

Read the table against Figure 7.1. The straight line has large bias (0.155: its average curve is simply the wrong shape) and small variance (0.022: every training set gives nearly the same line). The cubic has almost no bias and modest variance, and its total, 0.106, sits just above the noise floor of 0.090, which is as good as any model can do. The degree-9 polynomial has small bias but a variance of 3.6: each training set produces a wildly different curve, and averaging 500 of them would give a fine estimate, which is exactly the idea behind bagging and random forests (Chapter 10). In every row the three pieces sum to the directly measured test MSE, as the algebra promises.

Key idea

The decomposition explains why ensembling works: averaging many high-variance models leaves the bias untouched and divides the variance by (roughly) the number of independent models. It also explains why regularization is a trade, not a free lunch: it lowers variance by pulling every fit toward the same simpler answer, which raises bias. The best model is the one whose sum is smallest, not the one whose bias is zero.

4. Diagnosis: learning curves and the recipe

You have a model that is not good enough. Is it bias or variance? Two numbers usually settle it: the training score and the validation score. But the most informative tool is the learning curve: train on 10%, 25%, 50%, 100% of the data and plot both scores against the training-set size.

# Learning curves: does more data help? (high variance → yes; high bias → no)
import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import learning_curve, StratifiedKFold
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.tree import DecisionTreeClassifier

X, y = load_breast_cancer(return_X_y=True)
cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=0)
sizes = np.array([0.1, 0.25, 0.5, 0.75, 1.0])

for name, model in [("logistic (C=0.1)", make_pipeline(StandardScaler(), LogisticRegression(C=0.1, max_iter=1000))),
                    ("deep tree", DecisionTreeClassifier(random_state=0))]:
    n, tr, va = learning_curve(model, X, y, train_sizes=sizes, cv=cv, scoring="accuracy", random_state=0)
    print(name)
    print("  n_train :", n)
    print("  train   :", np.round(tr.mean(axis=1), 3))
    print("  valid   :", np.round(va.mean(axis=1), 3))
# logistic (C=0.1)
#   n_train : [ 45 113 227 341 455]
#   train   : [0.978 0.973 0.977 0.983 0.982]
#   valid   : [0.807 0.953 0.97  0.975 0.975]
# deep tree
#   n_train : [ 45 113 227 341 455]
#   train   : [1. 1. 1. 1. 1.]
#   valid   : [0.81  0.884 0.912 0.907 0.926]

Read the output: the logistic model's training and validation accuracies meet at about 0.98 — small gap, no plateau problem, the model is fine. The deep tree's training accuracy is 1.000 at every size while validation lags 8–19 points behind: textbook high variance, and the gap is still closing at the largest size, so more data (or pruning, Chapter 9) would help.

At work

Before any modeling meeting, produce two numbers per candidate model: cross-validated score and training score. The pair tells the whole story in five seconds and stops the most common argument in the room ("let's try a bigger model" when the problem is variance, or "let's get more data" when the problem is bias). If you can add a learning curve on one slide, do; it is the most persuasive argument for or against a data-collection budget.

5. Regularization: L2, L1 and friends

Regularization is the general name for any change to training that trades a little bias for a lot of variance reduction. The most important form adds a penalty on the size of the weights to the loss. The intuition: a model that fits noise typically does so with large, delicately balanced coefficients (look at how a high-degree polynomial swings). Charging rent for every unit of coefficient makes those wild fits expensive, so the optimizer prefers smaller, smoother solutions.

Explain it like I'm 9

Regularization is a budget. Your model can "spend" coefficient size to fit the data, but every coin it spends costs something. With a small budget it can only afford the big, obvious patterns. With an unlimited budget it buys every wiggle in the data, including the ones that were just noise. The penalty strength sets the budget.

L2 (Ridge): shrink everything

The math (optional)
Lossridge(w) = ∑i (yi − ŷi)² + α ∑j wj²

∑i(yi − ŷi)² is the ordinary data-fit term from Chapter 5. ∑j wj² is the squared L2 norm of the weight vector (the bias/intercept w0 is not penalized). α (alpha; some books write λ) is the regularization strength: α = 0 gives ordinary least squares; α → ∞ drives every weight to zero and predicts the mean. Because the penalty is smooth, Ridge has a closed-form solution, w = (XᵀX + αI)⁻¹Xᵀy, and the "+αI" is also what makes it numerically stable when features are correlated. For logistic regression scikit-learn uses the same L2 penalty but parameterizes it as C = 1/α: smaller C means stronger regularization, which trips everyone up at least once.

L1 (Lasso): shrink, and switch some off

The math (optional)
Losslasso(w) = ∑i (yi − ŷi)² + α ∑j |wj|
Losselastic(w) = ∑i (yi − ŷi)² + α [ ρ ∑j |wj| + (1 − ρ) ∑j wj² ]

Lasso replaces the squared penalty with the absolute value (the L1 norm). The consequence is dramatic: as α grows, coefficients do not merely shrink, they hit exactly zero one after another, so Lasso performs automatic feature selection. The absolute value has no derivative at zero, so there is no closed form; it is solved by coordinate descent. (One caution when reading the code: scikit-learn's Lasso and ElasticNet divide the data term by 2n while Ridge does not, so an alpha of 1 means different strengths in different estimators; compare alpha values within one estimator, never across.) Elastic net mixes the two with a ratio ρ (l1_ratio in sklearn): it keeps Lasso's sparsity but, when several features are highly correlated, tends to keep them as a group rather than arbitrarily picking one — usually the safer choice on real business data.

Why L1 makes zeros: the geometric picture

Penalizing the weights is equivalent to fitting the data as well as possible subject to a budget on the weights' size. Draw the budget region in weight space and the loss as contour ellipses around the unpenalized optimum; the solution is where the smallest contour first touches the region.

Deep dive: why L2 shrinks and L1 zeroes, in one dimension 6 min
Explain it like I'm 9

Two ways to make a kid quieter. Ridge says "speak at two-thirds of your volume": everyone gets quieter, nobody goes silent. Lasso says "everyone talk 10 decibels lower": the loud kids get quieter, and the kids who were already whispering below 10 decibels go completely silent. Lasso creates silence; Ridge only ever turns things down.

Precisely. Take one coefficient and pretend the data term is simply (w − wols)², where wols is the unpenalized estimate (this is exactly the situation for a standardized feature that is uncorrelated with the others, and a good approximation otherwise). Adding each penalty and setting the derivative to zero gives a closed form:

The math (optional)

Ridge: minimize (w − wols)² + α w². Derivative: 2(w − wols) + 2αw = 0 ⇒ w = wols / (1 + α). A multiplicative shrink: proportional, smooth, and never exactly zero unless wols was.

Lasso: minimize (w − wols)² + α|w|. For w > 0 the derivative is 2(w − wols) + α = 0 ⇒ w = wols − α/2, valid only if that is still positive; symmetrically for w < 0. If |wols| ≤ α/2 neither branch is valid and the minimum sits at the kink, w = 0. Together: w = sign(wols) · max(|wols| − α/2, 0), the soft-thresholding operator. A subtractive shrink: every coefficient loses the same amount, and anything smaller than that amount is set to exactly zero.

α is the penalty strength and wols the unpenalized coefficient; the factor ½ comes from the derivative of the square. The absolute value's kink at zero, where the derivative jumps from −α to +α, is what creates the dead zone; a smooth penalty like w² has no kink and no dead zone.

# One coefficient at a time: L2 divides, L1 subtracts a constant and clips at zero
import numpy as np
w_ols = np.array([3.0, 1.0, 0.3, -0.2])                    # unpenalised estimates of four coefficients
print("alpha   ridge = w/(1+α)             lasso = sign(w)·max(|w| − α/2, 0)")
for alpha in (0.0, 0.5, 1.0, 2.0):
    ridge = w_ols / (1 + alpha)
    lasso = np.sign(w_ols) * np.maximum(np.abs(w_ols) - alpha / 2, 0)
    print(f"{alpha:4.1f}    {np.array2string(ridge, precision=2, floatmode='fixed'):26s} {np.array2string(lasso, precision=2, floatmode='fixed')}")
# alpha   ridge = w/(1+α)             lasso = sign(w)·max(|w| − α/2, 0)
#  0.0    [ 3.00  1.00  0.30 -0.20]  [ 3.00  1.00  0.30 -0.20]
#  0.5    [ 2.00  0.67  0.20 -0.13]  [ 2.75  0.75  0.05 -0.00]
#  1.0    [ 1.50  0.50  0.15 -0.10]  [ 2.50  0.50  0.00 -0.00]
#  2.0    [ 1.00  0.33  0.10 -0.07]  [ 2.00  0.00  0.00 -0.00]

Look at the two small coefficients, 0.3 and −0.2. Ridge at α = 2 turns them into 0.10 and −0.07: still there, still "a feature the model uses". Lasso zeroes both at α = 1 and the 1.0 coefficient at α = 2, while the big coefficient is merely reduced from 3.0 to 2.0. This is Figure 7.6 in miniature: Ridge's paths glide toward zero and never arrive; Lasso's paths hit zero one at a time, smallest first. With correlated features the one-dimensional picture is only approximate (coordinate descent iterates the soft threshold over the features, each time on the residual left by the others), which is why Lasso, faced with two near-copies of a feature, tends to keep one and zero the other, and why elastic net, which adds a little Ridge, spreads the weight instead.

Common mistake

Reading Lasso's zeros as "these features are irrelevant". A zeroed feature may simply be a slightly weaker copy of a kept one; change the sample and the roles can swap. Use Lasso's selection as a candidate list to be checked with domain knowledge and a stability check (refit on bootstrap samples and count how often each feature survives), not as a verdict.

Common mistake

Regularizing unscaled features. The penalty charges the same rent per unit of coefficient, but a coefficient on a feature measured in thousands is naturally tiny and one on a feature in [0, 1] is naturally large. Without StandardScaler (inside the pipeline!), the penalty silently punishes small-unit features and ignores large-unit ones. The second most common mistake: forgetting that sklearn's LogisticRegression regularizes by default (C=1.0), and that smaller C is more regularization.

6. Early stopping and the best regularizer of all

Early stopping

Any model trained iteratively — gradient descent on a network, rounds of boosting — traces the U-curve over time: early on it learns the broad pattern, later it starts memorizing noise. Evaluate on the validation set after every epoch and stop when validation loss stops improving. This is early stopping, and it is regularization with a clock instead of a penalty: fewer steps means the weights have had less opportunity to grow large.

More data: the regularizer that lowers variance for free

Look back at the variance term. Every regularizer above lowers it by constraining the model, which costs a little bias. More training data lowers variance without adding bias: with more rows, noise averages out and the model has less room to mistake a fluke for a pattern. That is why the learning curve is the first thing to check: if the validation curve is still climbing at 100% of your data, the cheapest improvement may be a bigger extract from the warehouse, not a smarter algorithm.

At work

When a stakeholder asks "would more data help?", do not guess. Run learning_curve on what you have and show them Figure 7.4's shape. A flat validation curve means "no, we need better features or a different model". A still-rising one means "yes, and roughly this much". This single plot has saved more budget in my career than any hyperparameter search.

7. Cross-validation done right

Why one split is not enough

The simplest honest evaluation is a single hold-out split: train on 80%, validate on 20%. It works, but the validation score depends on which 20% you happened to hold out. On 569 rows, a 20% validation set has 114 examples, so a single misclassified row moves accuracy by almost a full point, and different random splits give visibly different answers. Choosing between two models on a difference of 0.5% with one split is choosing by coin flip.

k-fold cross-validation fixes this by using every row for validation exactly once. Shuffle the development data, cut it into k equal folds, and run k rounds: in round i, fold i is the validation set and the other k−1 folds are the training set. You get k scores; report their mean (a much steadier estimate) and their standard deviation (which tells you how much to trust a difference between models).

# Cross-validation: one split is a noisy estimate; k-fold gives a mean AND a spread
import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split, StratifiedKFold, cross_val_score
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression

X, y = load_breast_cancer(return_X_y=True)
model = make_pipeline(StandardScaler(), LogisticRegression(C=0.1, max_iter=1000))

# 1) Five different single hold-out splits → five different "answers"
singles = []
for seed in range(5):
    X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.2, stratify=y, random_state=seed)
    singles.append(model.fit(X_tr, y_tr).score(X_te, y_te))
print("single-split accuracies:", np.round(singles, 3), "→ spread", round(max(singles) - min(singles), 3))

# 2) Stratified 5-fold CV: every row is validated exactly once
cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=0)
scores = cross_val_score(model, X, y, cv=cv, scoring="accuracy")
print("5-fold accuracies:      ", np.round(scores, 3))
print(f"mean = {scores.mean():.3f} ± {scores.std():.3f}")

# 3) Repeated k-fold shrinks the noise further (5 x 5 = 25 fits)
from sklearn.model_selection import RepeatedStratifiedKFold
rcv = RepeatedStratifiedKFold(n_splits=5, n_repeats=5, random_state=0)
rs = cross_val_score(model, X, y, cv=rcv, scoring="accuracy")
print(f"5x5 repeated: mean = {rs.mean():.3f} ± {rs.std():.3f}  ({len(rs)} fits)")
# single-split accuracies: [0.965 0.982 0.982 0.974 0.974] → spread 0.018
# 5-fold accuracies:       [0.956 0.991 0.974 0.982 0.973]
# mean = 0.975 ± 0.012
# 5x5 repeated: mean = 0.975 ± 0.014  (25 fits)
Explain it like I'm 9

To find out how good a goalkeeper is, you don't watch one penalty kick — the shooter might have slipped. You watch many kicks from many shooters and average. k-fold is "many kicks": every part of the data gets a turn at being the surprise.

Deep dive: why K-fold scores are correlated, and what the ± really means 8 min
Explain it like I'm 9

Five judges score a cake. You would trust five independent opinions. But these five judges tasted mostly the same slices, and only one small slice each was different. If the batter was unusually sweet, all five say "too sweet" together. Their agreement does not mean the cake is reliably too sweet; it means they shared the same batter. K-fold's five scores share the same batter.

Precisely. In 5-fold cross-validation, any two rounds share three of their four training folds: 75% of the rows that trained model 1 also trained model 2. The five scores are therefore positively correlated, not independent draws. The average of correlated numbers is still an unbiased estimate of "the score a model trained on 80% of this data would get", but its variance is larger than std/√k pretends, and there is a stronger result: no estimator computed from the k scores alone can be unbiased for that variance (Bengio and Grandvalet, 2004). The figure shows the overlap; the code measures the consequence.

# The k fold scores overlap in training data, so std/√k understates how much the CV mean really wobbles
import numpy as np
from sklearn.linear_model import Ridge
from sklearn.model_selection import KFold, cross_val_score

rng = np.random.default_rng(0)
w_true = rng.normal(size=20)                                  # one fixed "world"
def fresh_dataset(n=100):
    X = rng.normal(size=(n, 20)); return X, X @ w_true + rng.normal(0, 2.0, n)

naive_se, cv_means = [], []
for _ in range(300):                                          # 300 fresh datasets from the same world
    X, y = fresh_dataset()
    s = cross_val_score(Ridge(alpha=1.0), X, y, cv=KFold(5, shuffle=True, random_state=0), scoring="r2")
    cv_means.append(s.mean()); naive_se.append(s.std(ddof=1) / np.sqrt(5))
print(f"error bar one CV run would report as std/√k : ± {np.mean(naive_se):.4f}")
print(f"actual spread of the CV mean across datasets : ± {np.std(cv_means):.4f}")
print(f"the naive bar is {np.std(cv_means) / np.mean(naive_se):.1f}x too small")
# error bar one CV run would report as std/√k : ± 0.0581
# actual spread of the CV mean across datasets : ± 0.0745
# the naive bar is 1.3x too small

Here the naive bar is about 30% too narrow; on smaller datasets and with more flexible models the factor is often 2 or more. Three practical rules follow. (1) Compare models on the same folds and look at the per-fold differences (a paired comparison): the shared-batter effect cancels when both models taste the same slices, so the std of the differences is a far better guide than the std of either model's scores. (2) Use repeated k-fold to shrink the fold-assignment noise, but do not divide by √(k·r) as if the k·r scores were independent; they overlap even more. Report the mean and the spread and say "spread across folds", not "standard error". (3) Keep a locked test set for the final number. It is the only fresh data you have, and its own interval (Chapter 3's SE = √(p(1−p)/n)) is honest because its rows never trained anything.

At work

When two candidate models differ by less than the spread of their per-fold scores, say so plainly ("we cannot distinguish them on this data") and pick the simpler or cheaper one. A leaderboard sorted to the third decimal on 5-fold scores is sorting noise, and the shared-training-data effect makes the noise look smaller than it is.

The family of splitters, and which one to use at work

Plain k-fold assumes rows are independent and identically distributed. Real business data usually breaks that assumption in one of two ways — groups (many rows per customer, patient, device) or time — and using the wrong splitter produces validation scores that are confidently, invisibly wrong.

Groups. If a patient contributes ten rows and three land in the validation fold while seven train the model, the model has effectively seen that patient already; the validation score measures "how well do we predict for patients we know" when the business question is "how well do we predict for patients we have never met". GroupKFold keeps every group on one side of the line.

Time. If you shuffle time-stamped rows, the model trains on March and June to predict April — it learns from the future. Scores look wonderful; the deployed model, which only ever has the past, disappoints. TimeSeriesSplit respects the arrow of time; Chapter 14 builds on it.

# Splitters for structured data: groups and time. Never let the same customer, or the
# future, leak from training into validation.
import numpy as np
from sklearn.model_selection import GroupKFold, TimeSeriesSplit, KFold

groups = np.array([0,0,0, 1,1,1, 2,2,2, 3,3,3])   # 12 rows from 4 customers
X = np.arange(12).reshape(-1, 1)

print("GroupKFold: a customer is never in both train and validation")
for tr, va in GroupKFold(n_splits=4).split(X, groups=groups):

for tr, va in TimeSeriesSplit(n_splits=3, test_size=3).split(X):

Common mistake: leakage through preprocessing

Fitting the scaler, imputer or feature selector on all the data and then cross-validating the model. The validation folds have leaked their means, variances and selected features into training. The fix is mechanical: put every preprocessing step in a Pipeline and pass the pipeline to cross_val_score, so each fold refits preprocessing on its own training portion. Chapter 8 makes this the default way you build anything.

The sacred test set, and nested CV in one paragraph

Cross-validation is where you make decisions. Every time you compare two models, tune a hyperparameter, or pick a threshold on the validation folds, you nudge your choices toward whatever happens to work on that data. After fifty such decisions the CV score is optimistic — you have overfit the validation set with your own hands. That is why the test set is sacred: it was never part of a decision, so its one score is honest. Touch it once, after everything is frozen. If the test score disappoints, you do not get to "try one more thing" and re-test; that would make it a validation set.

Nested cross-validation is the fully honest version when you have no separate test set and must both tune and estimate from the same data: an outer loop holds out a fold for estimation; inside each outer training portion, an inner loop does the tuning. The outer scores are unbiased by tuning because the tuning never saw them. It costs kouter × kinner fits, so it is used for small data and final reports rather than daily iteration. In code it is one line: pass a GridSearchCV object to cross_val_score.

# Nested CV: tune alpha in the inner loop, estimate honestly in the outer loop
import numpy as np
from sklearn.datasets import load_diabetes
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import Ridge
from sklearn.model_selection import GridSearchCV, KFold, cross_val_score

X, y = load_diabetes(return_X_y=True)
pipe = make_pipeline(StandardScaler(), Ridge())
inner = GridSearchCV(pipe, {"ridge__alpha": [0.01, 0.1, 1, 10, 100]}, cv=KFold(5, shuffle=True, random_state=1))
outer = KFold(5, shuffle=True, random_state=2)
scores = cross_val_score(inner, X, y, cv=outer, scoring="r2")
print("nested-CV R² per outer fold:", np.round(scores, 3))
print(f"honest estimate: {scores.mean():.3f} ± {scores.std():.3f}")
print("chosen alpha on full data:", inner.fit(X, y).best_params_)
# nested-CV R² per outer fold: [0.442 0.479 0.491 0.454 0.494]
# honest estimate: 0.472 ± 0.021
# chosen alpha on full data: {'ridge__alpha': 1}
Key idea

Validation data is for choosing; test data is for reporting. Any data that influenced a choice can no longer give you an honest report. Cross-validation is a way to choose well with all your development data; the test set is a way to report honestly with none of it spent.

8. The full protocol and rules of thumb

Here is the whole workflow on one page. It is the same for a two-hour prototype and a year-long production system; only the amount of iteration in step 3 changes.

  1. Split first, then explore. Even exploratory data analysis on the test set leaks: you notice a pattern, engineer a feature for it, and the test set is no longer a surprise. Split, lock, then look.
  2. Match the splitter to the deployment question. New customers → group split. Next quarter → time split. Rare positives → stratify. A random split answers "how well do we interpolate among rows like these", which is rarely the question.
  3. Use a pipeline so preprocessing lives inside the folds.
  4. Compare models on CV mean, sanity-check with CV std. If two models differ by less than about one standard deviation, you cannot tell them apart; prefer the simpler one.
  5. Freeze, retrain on everything, test once. Then write the number down with the confidence it deserves: a test set of 200 rows cannot distinguish 91% from 93%.

Data size versus model capacity: rules of thumb

Rows of labelled dataWhat tends to workValidation strategy

Two heuristics that survive contact with reality: (1) you want at least ten times as many training rows as free parameters for a linear model, and far more for flexible models — but regularization and validation, not this ratio, are what actually keep you safe; (2) the number that limits you is almost always the count of the rare class, or the number of independent groups, not the row count.

Quiz

Check your understanding

1. A model has training accuracy 99.5% and cross-validated accuracy 84%. What is the diagnosis and the first thing to try?

A large gap between training and validation performance is the signature of overfitting (high variance). The cures are more data, regularization, a simpler model, or ensembling. A bigger model would make it worse.

2. Both training and validation error are high and nearly equal, and they stopped improving after 20% of the data was used. Which action is most likely to help?

Curves that plateau early with a small gap mean high bias: the model cannot represent the pattern. More data or more regularization will not move the plateau. Increase capacity or improve the features.

3. Why does L1 (Lasso) regularization produce coefficients that are exactly zero while L2 (Ridge) does not?

Geometrically, the L1 constraint is a diamond (in 2-D) whose corners lie on the axes; the first contour to touch the region usually does so at a corner, where one or more weights are exactly zero. The L2 circle has no corners, so the touching point generically has all weights nonzero.

4. In scikit-learn's LogisticRegression, which setting gives the strongest regularization?

C is the inverse of the regularization strength (C = 1/α). Smaller C means a larger penalty and smaller coefficients. C = 0.01 is strong regularization; C = 100 is nearly none.

5. You are predicting which customers will churn next quarter from three years of monthly records, with many rows per customer. Which cross-validation scheme is appropriate?

The deployed model will predict the future for customers it has seen in the past, so validation must respect time (no training on months after the validation period). Shuffled folds leak the future and mix each customer's rows across train and validation, inflating the score.

6. After tuning on the validation folds you score the test set and get 88%. A colleague suggests trying two more hyperparameter settings and re-scoring the test set to see if it improves. What is wrong with this?

Any decision made using the test set biases it upward. Tune on validation folds (or nested CV), freeze, and score the test set once. If you must keep tuning, you no longer have a test set and should say so.

Exercise 7.2 — Find the leak

A colleague reports 97% cross-validated accuracy predicting equipment failures from sensor logs, using KFold(shuffle=True) after running StandardScaler().fit_transform(X) on the full dataset and dropping the 200 least-correlated features. Each machine contributes thousands of rows spanning two years. List every leak you can find and say how to fix each.

Show answer

Three leaks. (1) Preprocessing leak: the scaler and the feature selection were fit on all rows, including validation folds — put both in a Pipeline so they are refit inside each fold. (2) Group leak: rows from the same machine are split across train and validation, so the model recognizes machines rather than failure signatures — use GroupKFold with machine id as the group (if the deployed model must work on new machines). (3) Time leak: shuffling lets the model train on readings after a failure to predict readings before it — use TimeSeriesSplit (or a time-based cut-off per machine). Expect the honest score to be dramatically lower than 97%; that is the point.

Chapter summary

  • Only performance on unseen data matters. Training error lies because a flexible model fits noise as happily as signal.
  • Underfitting: both errors high. Overfitting: training error low, validation error high, large gap. Test error is U-shaped in model complexity.
  • Error = bias² + variance + noise. Bias is systematic (wrong model family); variance is instability across training sets (fitting noise). Levers usually trade one for the other; more data cuts variance for free.
  • Learning curves diagnose: an early high plateau with a small gap means bias (more data won't help); a large slowly closing gap means variance (it will).
  • L2 (Ridge) shrinks all coefficients; L1 (Lasso) zeroes some (feature selection); elastic net mixes them. Standardize first. In sklearn, larger alpha or smaller C = stronger regularization.
  • Every model has a capacity knob (depth, rounds, neighbours, dropout); early stopping regularizes iterative models with a clock.
  • One validation split is noisy; k-fold uses every row for validation once and gives a mean ± std. Stratify for classification; use GroupKFold for repeated entities and TimeSeriesSplit for anything with a clock.
  • Preprocessing goes inside the pipeline so it is refit per fold; otherwise it leaks.
  • Validation data is for choosing; test data is for reporting. Split first, freeze everything, retrain on all development data, score the test set once.
  • The count that limits you is the rare class or the number of independent groups, not the row count.
