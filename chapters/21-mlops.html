1. The notebook-to-production gap

The running example for this chapter is a churn model at a subscription business. After Chapter 13 you have a tuned gradient-boosted pipeline with AUC 0.87 in a notebook; retention wants a list of at-risk customers every Monday, and the product team wants a score inside the app when a customer opens the cancellation page. Between "AUC 0.87 in a notebook" and "a score in the app" lies everything this chapter covers, and it is where most ML projects die — not because the model is bad, but because nobody owned the system around it.

In 2015 a group of Google engineers published a paper with a figure that has become the emblem of the field: a tiny black box labelled "ML code" surrounded by much larger boxes for data collection, feature extraction, configuration, serving, monitoring and infrastructure. The point was that the model is the smallest component of an ML system, and that all the surrounding components accumulate a special kind of technical debt: hidden feedback loops, undeclared consumers, pipelines nobody understands, and behaviour that changes when the world changes.

Explain it like I'm 9

Baking one great cake at home is cooking. Running a bakery that ships 10,000 identical cakes a day is a different job: you need the same flour every time (data), the recipe written down exactly (code and config), ovens that don't drift in temperature (infrastructure), someone tasting a cake from every batch (monitoring), and a plan for what to do when the milk supplier changes (retraining). MLOps is the bakery, not the cake.

Here is the honest version of what "production" means for the churn model, and what breaks in each part:

StageWhat it must doHow it usually breaks
ReproduceRebuild the exact model from the exact data and code, months later.Unpinned library versions, un-seeded splits, a CSV someone overwrote.
PackageBundle preprocessing + model + metadata into one loadable artifact.Pickle saved with sklearn 1.3, loaded with 1.5: silent numerical drift or a crash.
ServeReturn predictions where and when the business needs them.The Monday batch job takes nine hours; the REST endpoint times out under load.
ValidateRefuse bad inputs before the model sees them.A schema change upstream turns monthly_spend into cents; predictions go wild for a week.
MonitorNotice when inputs, outputs or accuracy change.Nobody looks. Labels arrive 30 days late, so accuracy is discovered a quarter late.
Retrain & roll outReplace the model without breaking anything.The new version is deployed at 17:00 on a Friday to 100% of traffic with no rollback path.
Key idea

MLOps is software engineering plus two things that ordinary software does not have: the behaviour of the system is learned from data, so it can change without anyone changing code; and the correct answer arrives late or never, so you cannot test it the way you test a login page. Everything in this chapter is a response to those two facts.

2. Reproducibility & experiment tracking

Six months from now a regulator, an auditor or simply your own future self will ask: "How exactly was churn-v1.3 built?" You need to be able to answer with a command, not a memory. Reproducibility has four ingredients, and teams usually have one or two of them.

  1. Seeds. Every source of randomness — the train/test split, the model (random_state), the bootstrap in a forest, data shuffling in a data loader, NumPy's global generator — gets a fixed seed that is stored with the run. Note the honest limit: GPU kernels and multi-threaded tree builders can still produce tiny non-determinism; record the seed anyway, and compare metrics with a tolerance.
  2. Pinned environment. A requirements.txt with exact versions (scikit-learn==1.9.1, not >=1.4), or a lock file, or a container image tag. "Latest" is not a version.
  3. Versioned data and code. Code goes in git — that part is easy. Data is too big for git, so tools such as DVC store a small hash file in git that points to the real file in object storage; lakeFS and Delta Lake give the storage itself git-like branches and commits. The cheapest version that works: never overwrite a training extract, write it to a path containing the date and a content hash, and record that path with the run.
  4. Lineage. Every artifact points back to what produced it: model → training run → (data version, code commit, environment, parameters). If you can walk that graph, you can reproduce; if you can't, you have a file called model_final_v2_REAL.pkl.

Experiment tracking with MLflow

An experiment tracker is a database of runs plus a UI. You wrap training in a run, log parameters, metrics and artifacts, and the tracker records who ran what, when, from which commit. MLflow is the most common open-source choice; Weights & Biases, Neptune and the cloud vendors' offerings do the same job. The pattern is always the same:

# MLflow: track a run, log artifacts, register the model (needs a running MLflow server or local ./mlruns)
import mlflow, mlflow.sklearn
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.metrics import roc_auc_score

mlflow.set_tracking_uri("http://mlflow.internal:5000")      # or "file:./mlruns" for a laptop
mlflow.set_experiment("churn")

params = {"n_estimators": 300, "max_depth": 3, "learning_rate": 0.05, "random_state": 0}
with mlflow.start_run(run_name="gbm-depth3") as run:
    mlflow.log_params(params)
    mlflow.set_tags({"data_snapshot": "s3://ml-data/churn/2026-09-01", "git_sha": "4c1e7b2"})
    pipe = make_pipeline(StandardScaler(), GradientBoostingClassifier(**params)).fit(X_tr, y_tr)
    auc = roc_auc_score(y_te, pipe.predict_proba(X_te)[:, 1])
    mlflow.log_metric("test_auc", auc)
    mlflow.log_artifact("reports/shap_summary.png")           # any file: plots, model card, reference profile
    mlflow.sklearn.log_model(pipe, artifact_path="model",
                             input_example=X_tr.head(3),        # records the input schema (signature)
                             registered_model_name="churn")     # creates version N in the Model Registry

# Promote in the registry (MLflow >= 2.9 uses aliases instead of the old Staging/Production stages)
client = mlflow.MlflowClient()
client.set_registered_model_alias("churn", alias="staging", version=4)
# ... run acceptance tests against models:/churn@staging, then:
client.set_registered_model_alias("churn", alias="production", version=4)
model = mlflow.sklearn.load_model("models:/churn@production")   # what the serving code loads

You do not need MLflow to get 80% of the benefit. The essential thing is an append-only record of every run with its parameters, metrics, data fingerprint and library versions. A JSON-lines file in a shared bucket does this in twenty lines, and a small team can run on it for a year before the UI becomes worth the server:

# A plain-Python experiment log: one JSON line per run, append-only, greppable
import json, time, hashlib, platform, os, tempfile
import numpy as np, sklearn
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import cross_val_score
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier

LOG = os.path.join(tempfile.gettempdir(), "experiments.jsonl")

def log_run(name, params, metrics, data_fingerprint, tags=()):
    rec = {"run_id": hashlib.sha1(f"{name}{time.time_ns()}".encode()).hexdigest()[:10],
           "ts": time.strftime("%Y-%m-%dT%H:%M:%S"), "name": name, "params": params, "metrics": metrics,
           "data_sha": data_fingerprint, "sklearn": sklearn.__version__, "python": platform.python_version(),
           "tags": list(tags)}
    with open(LOG, "a") as f: f.write(json.dumps(rec) + "\n")
    return rec["run_id"]

X, y = load_breast_cancer(return_X_y=True)
data_sha = hashlib.sha1(np.ascontiguousarray(X).tobytes() + y.tobytes()).hexdigest()[:12]   # what data did we train on?

candidates = {
    "logreg_C1":  make_pipeline(StandardScaler(), LogisticRegression(C=1.0, max_iter=2000)),
    "logreg_C01": make_pipeline(StandardScaler(), LogisticRegression(C=0.1, max_iter=2000)),
    "rf_200":     RandomForestClassifier(n_estimators=200, random_state=0),
}
for name, model in candidates.items():
    t0 = time.time()
    auc = cross_val_score(model, X, y, cv=5, scoring="roc_auc")
    rid = log_run(name, model.get_params(deep=False) if "rf" in name else {"C": model[-1].C},
                  {"cv_auc_mean": round(auc.mean(), 4), "cv_auc_std": round(auc.std(), 4), "fit_seconds": round(time.time() - t0, 2)},
                  data_sha, tags=["baseline-sweep"])
    print(f"{rid}  {name:<12} AUC = {auc.mean():.4f} ± {auc.std():.4f}")

# Reading the log back is one line of pandas — no server required
import pandas as pd
runs = pd.read_json(LOG, lines=True)
best = runs.loc[runs["metrics"].apply(lambda m: m["cv_auc_mean"]).idxmax()]
print(f"\nbest run: {best['name']} (run_id {best['run_id']}, data {best['data_sha']}, sklearn {best['sklearn']})")
os.remove(LOG)
# 17a855bea0  logreg_C1    AUC = 0.9952 ± 0.0040      (run ids are time-based and will differ)
# 7d74a19c6f  logreg_C01   AUC = 0.9951 ± 0.0047
# 30c1d24370  rf_200       AUC = 0.9900 ± 0.0087
#
# best run: logreg_C1 (run_id 17a855bea0, data 959f826a15c6, sklearn 1.9.1)
Common mistake

Logging the metric but not the data. "AUC 0.87" is meaningless without the fingerprint of the data it was measured on, because the next extract will have different rows, a different label window, and possibly a different label definition. Hash the training data (or store its version) with every run. When two runs disagree, the first question is always "same data?" and you want the answer in the log, not in Slack.

At work

Start with the JSON log on day one of any project — it is free and it forces the habit. Move to MLflow (or whatever your company runs) when a second person needs to see your runs, or when you have more than ~50 of them. The migration is trivial because the schema is the same: params, metrics, tags, artifacts. What is not trivial is recovering the runs you never logged.

3. Packaging a model & the registry

What exactly is "the model"? Not the estimator. The thing serving needs is the whole pipeline: imputation, scaling, encoding, feature construction and the estimator, fitted together, so that raw production rows go in and predictions come out (Chapter 8). If preprocessing lives in a notebook cell and only the estimator is saved, the serving code has to re-implement the preprocessing, and it will do so slightly differently — which is the training–serving skew of Section 5, self-inflicted.

Pickle and joblib: convenient and dangerous

scikit-learn pipelines are saved with joblib.dump (pickle with efficient NumPy arrays). Two risks come with it. Version coupling: a pickle stores object internals, not a specification, so loading it under a different scikit-learn version may fail loudly, or — worse — load and predict slightly different numbers. scikit-learn emits an InconsistentVersionWarning; treat it as an error. Security: unpickling executes arbitrary code embedded in the file. Never load a pickle you did not produce, and sign or checksum the ones you did. The practical answer is a bundle: the pipeline plus metadata — library versions, model version, feature names, training data fingerprint, expected input schema — saved under a version-stamped filename, with a loader that refuses mismatches.

# Packaging: save the WHOLE pipeline with a version-stamped name, and refuse to load under a different sklearn
import os, json, tempfile, joblib, sklearn, numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression

X, y = load_breast_cancer(return_X_y=True)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.25, random_state=0)
pipe = make_pipeline(StandardScaler(), LogisticRegression(max_iter=2000)).fit(X_tr, y_tr)

MODEL_VERSION = "churn-v1.3.0"                       # bump on every retrain that ships
outdir = tempfile.mkdtemp()
path = os.path.join(outdir, f"{MODEL_VERSION}_sklearn{sklearn.__version__}.joblib")
joblib.dump({"pipeline": pipe, "sklearn_version": sklearn.__version__, "model_version": MODEL_VERSION,
             "n_features": X_tr.shape[1], "test_auc": float(pipe.score(X_te, y_te))}, path)
print("saved:", os.path.basename(path), f"({os.path.getsize(path)/1024:.1f} KB)")

def load_model(path, strict=True):
    bundle = joblib.load(path)                       # WARNING: unpickling runs arbitrary code — only load files you trust
    if bundle["sklearn_version"] != sklearn.__version__:
        msg = f"model pickled with sklearn {bundle['sklearn_version']}, runtime has {sklearn.__version__}"
        if strict: raise RuntimeError(msg)
        print("WARNING:", msg)
    return bundle

b = load_model(path)
same = np.allclose(b["pipeline"].predict_proba(X_te), pipe.predict_proba(X_te))
print(f"loaded {b['model_version']}: predictions identical to the in-memory model = {same}")

# Simulate the failure mode: a bundle saved by a different library version
b_old = dict(b, sklearn_version="1.2.2")
joblib.dump(b_old, os.path.join(outdir, "old.joblib"))
try:
    load_model(os.path.join(outdir, "old.joblib"))
except RuntimeError as e:
    print("refused to load:", e)
# saved: churn-v1.3.0_sklearn1.9.1.joblib (2.4 KB)
# loaded churn-v1.3.0: predictions identical to the in-memory model = True
# refused to load: model pickled with sklearn 1.2.2, runtime has 1.9.1

ONNX (Open Neural Network Exchange) is the alternative for models that must run outside Python or with a frozen runtime: skl2onnx converts most scikit-learn pipelines, and onnxruntime executes them in C++, Java, C# or the browser, typically several times faster than Python and with no version coupling to scikit-learn. The trade-off is that not every transformer converts, and you must verify numerically that the ONNX graph reproduces the Python predictions.

The model registry

A registry is a catalogue of model versions with a lifecycle. Every trained candidate becomes a numbered version; a version is promoted through stages by people or by automated gates; serving code loads "the production version" by alias rather than by file path, so a promotion or a rollback is a metadata change, not a redeploy.

Explain it like I'm 9

A registry is like the shelf of approved recipes in the bakery kitchen. Anyone can write a new recipe card (candidate), but only the head baker can move a card to the "we bake this" slot (production) — and the old card goes into a drawer, not the bin, in case tonight's cakes come out wrong and you need yesterday's recipe back by morning.

4. Serving patterns & the inference service

"Deploy the model" means one of four very different things, and choosing the wrong one is the most expensive early mistake in MLOps. The question that decides it is not "what is fashionable" but two numbers: how fast must a prediction be available after the input exists (latency tolerance), and how many predictions per second (throughput).

Batch scoring

A scheduled job scores every row (all customers, every night) and writes the results to a table. The consumer reads the table. Simplest, cheapest per prediction, easiest to test — and predictions are hours old. Right for the Monday retention list, weekly demand forecasts, monthly risk scores.

Real-time REST (online)

A service loads the model and answers HTTP requests one row at a time in tens of milliseconds. Needed when the input only exists at request time (the customer is on the cancellation page now). Requires a running service, autoscaling, monitoring, on-call.

Streaming

The model sits on a message stream (Kafka, Kinesis, Pub/Sub) and scores every event as it flows through, writing scores to another stream or store. For continuous high-volume events: fraud on every transaction, anomaly detection on sensor data.

Embedded / edge

The model is compiled into the application (mobile app, browser via ONNX, a device, a database UDF). Zero network latency, works offline, hard to update, must be small. Keyboard prediction, on-device vision, in-database scoring.

A real-time inference service

When the decision does need to happen at request time, the standard shape is a small HTTP service: load the model bundle once at start-up, validate every request against a schema, predict, log, return. FastAPI with pydantic gives you the schema validation, an OpenAPI spec and async handling for free. The service below is the entire pattern; everything a real one adds (auth, rate limiting, tracing) is generic web engineering.

# app.py — a minimal, production-shaped inference service (run: uvicorn app:app --host 0.0.0.0 --port 8000)
import os, time, logging, uuid
import numpy as np, pandas as pd, joblib
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field, field_validator

log = logging.getLogger("churn-api")
app = FastAPI(title="churn-api")
BUNDLE = joblib.load(os.environ.get("MODEL_PATH", "/models/churn-v1.3.0.joblib"))   # loaded ONCE, not per request
PIPE, VERSION = BUNDLE["pipeline"], BUNDLE["model_version"]

class Customer(BaseModel):                          # the input schema IS the contract with callers
    customer_id: str
    age: int = Field(ge=18, le=100)
    monthly_spend: float = Field(ge=0, le=5000)
    plan: str
    support_calls: int = Field(ge=0, le=50, default=0)

    @field_validator("plan")
    def known_plan(cls, v):
        if v not in {"basic", "plus", "premium"}: raise ValueError(f"unknown plan {v!r}")
        return v

class Prediction(BaseModel):
    customer_id: str
    churn_probability: float
    model_version: str
    request_id: str

@app.get("/health")                                 # liveness: is the process up?
def health(): return {"status": "ok", "model_version": VERSION}

@app.get("/ready")                                  # readiness: can it actually predict? (load balancer checks this)
def ready():
    PIPE.predict_proba(pd.DataFrame([{"age": 40, "monthly_spend": 30.0, "plan": "basic", "support_calls": 1}]))
    return {"ready": True}

@app.post("/predict", response_model=Prediction)
def predict(c: Customer):
    t0 = time.perf_counter(); rid = uuid.uuid4().hex[:12]
    X = pd.DataFrame([c.model_dump(exclude={"customer_id"})])
    try:
        p = float(PIPE.predict_proba(X)[0, 1])
    except Exception as e:                            # never leak a stack trace to the caller
        log.exception("prediction failed"); raise HTTPException(status_code=500, detail="prediction failed")
    # structured log line = the raw material for monitoring (Section 7): inputs, output, version, latency
    log.info({"request_id": rid, "model_version": VERSION, "features": X.iloc[0].to_dict(),
              "prediction": p, "latency_ms": round((time.perf_counter() - t0) * 1000, 2)})
    return Prediction(customer_id=c.customer_id, churn_probability=p, model_version=VERSION, request_id=rid)
# Dockerfile — pin everything; the image tag is the environment version
FROM python:3.11-slim
WORKDIR /srv
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt     # exact pins: scikit-learn==1.9.1, fastapi==0.115.0, ...
COPY app.py .
COPY models/churn-v1.3.0.joblib /models/               # or mount it at runtime and pass MODEL_PATH
ENV MODEL_PATH=/models/churn-v1.3.0.joblib
RUN useradd -m api && chown -R api /srv /models          # do not run as root
USER api
EXPOSE 8000
HEALTHCHECK --interval=30s --timeout=3s CMD python -c "import urllib.request as u; u.urlopen('http://localhost:8000/ready')"
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000", "--workers", "2"]

Three details in that service are the difference between a demo and a system. The model is loaded once at start-up, not per request (loading a joblib file per request is a classic 100× slowdown). There are two health endpoints: /health says the process is alive, /ready proves it can predict — Kubernetes and load balancers use the second to decide whether to send traffic, which is what makes zero-downtime deploys possible. And every request writes a structured log line with the inputs, the output, the model version and the latency; that log is the monitoring data of Section 7.

Input validation: the bouncer at the door

Pydantic validates types and ranges per request. For batch jobs you need the same discipline applied to a whole table: does it have the expected columns, are the types right, are values in the training range, how many nulls? A batch that fails validation should stop the pipeline and page someone, not produce ten thousand confident nonsense scores. The function below is the shape of that check; pandera and great_expectations are the libraries that do it with more ceremony.

# Data validation at the door: schema, types, ranges, nulls. Fail loudly BEFORE the model sees bad rows.
import numpy as np, pandas as pd

SCHEMA = {                                       # learned from the training data, frozen with the model
    "age":           {"dtype": "number", "min": 18,  "max": 100, "nullable": False},
    "monthly_spend": {"dtype": "number", "min": 0,   "max": 5000, "nullable": False},
    "plan":          {"dtype": "category", "values": {"basic", "plus", "premium"}, "nullable": False},
    "support_calls": {"dtype": "number", "min": 0,   "max": 50, "nullable": True},
}

class DataValidationError(ValueError): pass

def validate(df, schema=SCHEMA, max_null_frac=0.05, max_out_of_range_frac=0.01):
    problems = []
    missing = set(schema) - set(df.columns); extra = set(df.columns) - set(schema)
    if missing: problems.append(f"missing columns: {sorted(missing)}")
    if extra:   problems.append(f"unexpected columns: {sorted(extra)}")
    for col, rule in schema.items():
        if col not in df: continue
        s = df[col]; null_frac = s.isna().mean()
        if null_frac > (max_null_frac if rule["nullable"] else 0):
            problems.append(f"{col}: {null_frac:.1%} nulls (nullable={rule['nullable']})")
        if rule["dtype"] == "number":
            if not pd.api.types.is_numeric_dtype(s): problems.append(f"{col}: expected numeric, got {s.dtype}"); continue
            oor = ((s < rule["min"]) | (s > rule["max"])).mean()
            if oor > max_out_of_range_frac: problems.append(f"{col}: {oor:.1%} of rows outside [{rule['min']}, {rule['max']}]")
        else:
            bad = set(s.dropna().unique()) - rule["values"]
            if bad: problems.append(f"{col}: unknown categories {sorted(bad)}")
    if problems: raise DataValidationError("; ".join(problems))
    return True

rng = np.random.default_rng(0); n = 40
good = pd.DataFrame({"age": rng.integers(18, 80, n), "monthly_spend": rng.gamma(2, 20, n).round(2),
                     "plan": rng.choice(["basic", "plus", "premium"], n), "support_calls": rng.integers(0, 6, n).astype(float)})
good.loc[3, "support_calls"] = np.nan                      # one null in a nullable column: fine
print("good batch:", validate(good))

bad = good.copy(); bad.loc[0, "age"] = 340; bad.loc[5, "plan"] = "gold"; bad = bad.drop(columns="support_calls")
try:
    validate(bad)
except DataValidationError as e:
    print("bad batch rejected ->", e)
# good batch: True
# bad batch rejected -> missing columns: ['support_calls']; age: 2.5% of rows outside [18, 100]; plan: unknown categories ['gold']
At work

Generate the schema from the training data at training time — min, max, categories, null rate per column — and save it in the model bundle. Then validation in production is "does this batch look like what the model was trained on?", which is exactly the right question, and it updates itself automatically on every retrain. Loosen the bounds a little (e.g. 1st–99th percentile ± 20%) so legitimate new extremes don't page you, and log — don't block — soft violations.

5. Training–serving skew & feature stores

Training–serving skew is the gap between the features the model saw in training and the features it receives in production, and it is the most common cause of "the model was great offline and useless online." The sources are mundane: the training feature spend_last_30d was computed in SQL over a warehouse table, the serving feature is computed in Python from a cache with a different definition of "day"; training used the value as of the label date, serving uses the value now; training filled nulls with the median, serving fills them with zero. Each is a small bug; together they cost more accuracy than any modelling choice.

Explain it like I'm 9

You practise for a spelling test with words your teacher reads out slowly. On the day, a different teacher reads them fast with an accent. You knew the words, but the input changed, so you score worse. A model that trained on features computed one way and is served features computed another way has the same problem — and unlike you, it can't tell that the accent changed.

You do not need a feature-store product to get the benefit. The discipline is: (1) feature logic lives in one piece of code that both training and serving import — the sklearn Pipeline is exactly this for row-level transforms; (2) aggregate features (last-30-day spend, counts, ratios) are computed by one job that writes both the training table and the serving cache; (3) training data is built with point-in-time joins, i.e. the feature value as of the label timestamp, never the current value. Then test the skew: take a sample of production requests, recompute their features offline, and assert the values match. A skew test that runs in CI catches the "different definition of day" bug before it costs a quarter.

Common mistake

Computing training features from the current state of the database. A model that predicts churn from days_since_last_login where the value is today's, but the label is from six months ago, is trained on the future: churned customers have not logged in since they churned, so the feature is a near-perfect leak. Offline AUC 0.98, production AUC 0.62. Point-in-time correctness is not optional.

6. CI/CD for ML: tests that matter

Ordinary software has unit tests: given this input, expect that output. ML systems need those too, for the feature code and the service. But the model itself cannot be tested that way — nobody knows what the "right" probability for customer 42 is. So ML pipelines add three families of tests that ordinary code does not have:

Data tests

Schema (columns, types), value ranges, null rates, category sets, row counts within expected bounds, no duplicate keys, label rate within a plausible band, no leakage columns (a denylist of names and a check that no feature has AUC > 0.95 alone). Run before every training job and every batch score.

Model tests

Metric on a frozen test set is above a threshold and not worse than the current production model by more than a tolerance. Invariance tests: changing a feature that should not matter (customer ID, name) does not change the prediction. Directional tests: raising support_calls does not lower churn probability. Calibration within tolerance. Prediction latency under budget.

Pipeline tests

The whole train → evaluate → package → load → predict path runs end-to-end on a small sample in under a few minutes. The saved bundle loads in a fresh process and reproduces the in-memory predictions. The service starts, /ready returns 200, and a golden request returns the golden output.

# tests/test_model.py — model tests that run in CI against the candidate bundle (pytest)
import joblib, pandas as pd, numpy as np, pytest
from sklearn.metrics import roc_auc_score

CANDIDATE = joblib.load("artifacts/candidate.joblib")["pipeline"]
PRODUCTION = joblib.load("artifacts/production.joblib")["pipeline"]
TEST = pd.read_parquet("data/frozen_test_set.parquet")      # frozen: same rows for every CI run
X, y = TEST.drop(columns=["churned"]), TEST["churned"]

def test_metric_threshold_and_no_regression():
    auc_new = roc_auc_score(y, CANDIDATE.predict_proba(X)[:, 1])
    auc_old = roc_auc_score(y, PRODUCTION.predict_proba(X)[:, 1])
    assert auc_new >= 0.80, f"absolute floor: {auc_new:.3f}"
    assert auc_new >= auc_old - 0.005, f"regression vs production: {auc_new:.3f} < {auc_old:.3f}"

def test_invariance_to_id_like_columns():
    a = X.head(200).copy(); b = a.copy(); b["customer_id"] = "someone-else"
    assert np.allclose(CANDIDATE.predict_proba(a), CANDIDATE.predict_proba(b))

def test_directional_expectation():
    a = X.head(200).copy(); b = a.copy(); b["support_calls"] = b["support_calls"] + 5
    p_a, p_b = CANDIDATE.predict_proba(a)[:, 1], CANDIDATE.predict_proba(b)[:, 1]
    assert (p_b >= p_a - 1e-6).mean() > 0.95, "more support calls should not lower churn risk"

def test_latency_budget():
    import time; row = X.head(1)
    t0 = time.perf_counter(); [CANDIDATE.predict_proba(row) for _ in range(100)]
    assert (time.perf_counter() - t0) / 100 < 0.02, "single-row prediction must stay under 20 ms"

Key idea

The model test that matters most is "not worse than production on a frozen test set." An absolute threshold catches disasters; the comparison catches slow decay and the subtle bug where a "fix" to feature code silently drops two AUC points. And the test set must be frozen — if it is regenerated from live data every run, you are comparing models on different exams.

At work

CI for the churn model does not need Kubernetes, Airflow or a feature store. It needs: a frozen test set in object storage, a train.py that runs on a sample in under five minutes, and the four tests above. That setup catches most of the failures that actually happen — broken feature code, leaked columns, a regression versus production — and a two-person team can build it in a week. Continuous training on a schedule comes later, and only if the data actually drifts (Section 7 tells you whether it does).

7. Monitoring & drift detection

A deployed model is a bet that the future looks like the training data. The bet decays. Customers change, products change, a marketing campaign brings in a new segment, an upstream team renames a field, a pandemic happens. Ordinary software monitoring — is the service up, is latency fine — sees none of this. The model keeps returning numbers with the same confidence while their meaning silently drifts away. ML monitoring exists to notice.

Explain it like I'm 9

You learned to spot ripe mangoes at the market by colour: yellow means ripe. Then the market starts selling a different variety that is green when ripe. You keep confidently picking yellow ones — and they're all bad. Nothing about you changed; the world did. The only way to notice early is to check what you're seeing (lots of green mangoes lately: input drift), what you're deciding (I'm rejecting almost everything: prediction drift), and, when you finally taste them, how often you were right (performance, which you only learn later).

Drift detection: PSI and the KS test

The workhorse for "has this feature's distribution moved?" is the Population Stability Index, borrowed from credit scoring. Bin the feature using quantiles of the reference (training) data — ten bins, 10% of reference rows each — count the production sample into the same bins, and compare the two sets of proportions:

The math (optional)
PSI = ∑b=1B (qb − pb) · ln(qb / pb)

pb is the fraction of reference rows in bin b, qb the fraction of production rows in the same bin, and B the number of bins (10 is conventional). Each term is non-negative (the sign of the difference matches the sign of the log), so PSI ≥ 0 and equals 0 only when the histograms match. It is a symmetrised KL divergence between the two binned distributions. Because it depends on B and on the sample size, treat the thresholds as conventions, not laws.

KS = maxx | Fref(x) − Fprod(x) |

The two-sample Kolmogorov–Smirnov statistic is the largest vertical gap between the two empirical cumulative distribution functions F. Its p-value tests "could these two samples come from the same distribution?" — which, with production samples of 100,000 rows, is always rejected for trivial shifts. Use the KS statistic as an effect size and PSI for alerting; use the p-value only for small samples.

# Drift detection: Population Stability Index and the Kolmogorov–Smirnov test
import numpy as np
from scipy import stats

def psi(reference, current, bins=10, eps=1e-6):
    """PSI = sum over bins of (cur% - ref%) * ln(cur% / ref%). Bins are quantiles of the reference."""
    edges = np.quantile(reference, np.linspace(0, 1, bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf                          # catch values outside the reference range
    ref_pct = np.histogram(reference, edges)[0] / len(reference) + eps
    cur_pct = np.histogram(current, edges)[0] / len(current) + eps
    return float(np.sum((cur_pct - ref_pct) * np.log(cur_pct / ref_pct)))

rng = np.random.default_rng(0)
ref = rng.normal(loc=100, scale=15, size=20_000)                   # e.g. "monthly_spend" in the training data
scenarios = {"same distribution": rng.normal(100, 15, 5_000),
             "small shift (+3)":  rng.normal(103, 15, 5_000),
             "big shift (+12)":   rng.normal(112, 15, 5_000),
             "wider (std 25)":    rng.normal(100, 25, 5_000)}

print(f"{'production sample':<20}{'PSI':>7}{'KS stat':>9}{'KS p-value':>12}   verdict")
for name, cur in scenarios.items():
    p = psi(ref, cur); ks = stats.ks_2samp(ref, cur)
    verdict = "stable" if p < 0.1 else ("investigate" if p < 0.25 else "ALERT: retrain candidate")
    print(f"{name:<20}{p:7.3f}{ks.statistic:9.3f}{ks.pvalue:12.2e}   {verdict}")
# production sample       PSI  KS stat  KS p-value   verdict
# same distribution     0.003    0.013    4.75e-01   stable
# small shift (+3)      0.038    0.078    2.14e-21   stable
# big shift (+12)       0.603    0.313    0.00e+00   ALERT: retrain candidate
# wider (std 25)        0.312    0.139    1.53e-67   ALERT: retrain candidate

Look at the "small shift" row: a 3-unit move (one fifth of a standard deviation) gives a PSI of 0.04 — stable by every convention — while the KS p-value is 10−21. With 5,000 rows the KS test is certain the distributions differ, and it is right; they do. But the difference is too small to matter to the model. This is why alerting on p-values is a recipe for alert fatigue, and why PSI's conventional thresholds are useful despite being arbitrary:

Concept drift versus data drift

Everything above watches the inputs. There is a second, nastier kind of change: the inputs look exactly the same, but the relationship between inputs and outcome has changed. That is concept drift. A competitor launches a cheaper plan: the same customers with the same features now churn at twice the rate. No PSI will fire. Only performance, computed once labels arrive, can see it — which is why the delayed-label panel exists even though it is always late.

# "Performance with delayed labels": the truth arrives weeks later, so accuracy must be backfilled as labels land
import numpy as np, pandas as pd

rng = np.random.default_rng(7)
DAYS, N, LABEL_DELAY = 90, 300, 21                         # a churn label is only known 21 days after the prediction
rows = []
for d in range(DAYS):
    p_model = rng.beta(2, 5, N)                            # what the model believes (its inputs look the same every day)
    score = np.clip(p_model + rng.normal(0, 0.12, N), 0, 1)
    concept_drift = 0.0 if d < 45 else 0.30                # from day 45 customers behave differently: CONCEPT drift
    label = (rng.random(N) < np.clip(p_model + concept_drift, 0, 1)).astype(int)
    rows.append(pd.DataFrame({"day": d, "score": score, "label": label, "label_known_on": d + LABEL_DELAY}))
log = pd.concat(rows, ignore_index=True)

def dashboard(today):
    """What monitoring can show on `today`: prediction rate now, accuracy only for days whose labels have arrived."""
    seen = log[log.day <= today]
    pred_rate = seen.groupby("day")["score"].apply(lambda s: (s > 0.5).mean())            # available immediately
    labelled = seen[seen.label_known_on <= today]
    acc = labelled.groupby("day").apply(lambda g: ((g.score > 0.5).astype(int) == g.label).mean())
    return pred_rate, acc

for today in [44, 60, 75, 89]:
    pr, acc = dashboard(today)
    print(f"day {today:2d}: predicted-churn rate (last 7 d) = {pr.iloc[-7:].mean():.3f} | "
          f"accuracy known up to day {acc.index.max():2d}, last 7 labelled days = {acc.iloc[-7:].mean():.3f}")
pr, acc = dashboard(89)
print(f"\nprediction rate never moved ({pr[:45].mean():.3f} -> {pr[45:].mean():.3f}): input monitoring is blind to concept drift")
print(f"accuracy fell ({acc[:45].mean():.3f} -> {acc[45:].mean():.3f}) but became visible only {LABEL_DELAY} days late")
# day 44: predicted-churn rate (last 7 d) = 0.145 | accuracy known up to day 23, last 7 labelled days = 0.717

# day 75: predicted-churn rate (last 7 d) = 0.140 | accuracy known up to day 54, last 7 labelled days = 0.499

On day 60, fifteen days after the world changed, the dashboard still shows accuracy 0.72 — because the newest labelled day is 39. On day 75 it finally shows the collapse. The lesson is structural, not statistical: the label delay is a blind spot the size of the delay, and the only mitigations are proxies that arrive sooner (a support ticket within 7 days as an early churn signal), a faster label pipeline, or a small labelled sample you pay to get quickly.

Key idea

Monitor at three speeds. Instant: inputs and predictions (drift) plus system health. Delayed: performance and fairness, backfilled as labels arrive, indexed by prediction date not label date. Structural: the reference profile you compare against is an artifact of the training run (Figure 21.2) and must be versioned with the model — comparing v1.4's inputs against v1.2's profile alerts on the wrong thing.

Common mistake

Alerting on everything. Thirty features × daily PSI × a p-value threshold = a pager that fires every morning, and within a month the team mutes it. Alert only on features with high permutation importance (Chapter 20), only on PSI > 0.25 or a schema violation, and route "investigate" levels to a weekly review, not to on-call. An alert that nobody acts on is worse than no alert, because it trains people to ignore the next real one.

8. Retraining & safe rollout

When to retrain

Monitoring tells you the model is decaying. Retraining is the response, and there are three ways to schedule it:

StrategyTriggerProsRisks
ScheduledCalendar: weekly, monthly, quarterlyPredictable, simple to automate, easy to explain to auditorsRetrains when nothing changed (waste, churn of versions) and fails to retrain when something changed on day 2 of the month
TriggeredDrift alert or performance drop crosses a thresholdRetrains exactly when needed; cheaperThreshold tuning; a broken upstream pipeline can trigger a retrain on garbage; requires trustworthy monitoring
Continuous / onlineEvery batch of new labels updates the modelFastest adaptation (ads, recommendations, fraud)Feedback loops (the model shapes the data it learns from), no stable version to audit, poisoning risk, hard to roll back

For most business models the honest answer is scheduled retraining with a triggered override: retrain monthly because the process is then routine and tested, and retrain early when the drift alert fires. Either way, a retrain produces a candidate, never a deployment. The candidate goes through the CI model tests of Section 6 and then the rollout ladder.

Common mistake

Retraining automatically on drifted data without asking why it drifted. If PSI fired because an upstream job started writing monthly_spend in cents instead of euros, retraining "fixes" the alert by learning the bug. The first response to a drift alert is a human asking "is the data wrong or is the world different?"; only the second answer justifies a retrain. Data validation (Section 4) is your defence: a unit change should fail validation before it ever reaches a training job.

The rollout ladder

Two things about the A/B rung deserve emphasis. First, randomise by customer, not by request: a customer who sees the v1.4 score today and the v1.3 score tomorrow gives you a corrupted experiment and a confused customer. Second, the metric is the business outcome, not the model metric. A model with a better AUC can lose an A/B test — because the retention team acts on the top 500 scores only and the two models rank that top 500 identically, or because the new model's top 500 are customers who would have stayed anyway. Pre-register the metric, the sample size and the stopping rule (Chapter 22 covers the statistics of experiments and why peeking inflates false positives).

Explain it like I'm 9

You've made a new recipe for the bakery. You don't swap it in for all 10,000 cakes tomorrow. First you bake it alongside the old one and just look (shadow). Then you sell it at one counter (canary). Then you sell both at random and count which one customers come back for (A/B). And the whole time, yesterday's recipe is still on the shelf in case tonight's batch is a disaster (rollback).

At work: the rollback drill

Before the first production deployment, do a rollback on purpose: promote v1.3, roll back to v1.2, confirm the service is serving v1.2 (the /health endpoint returns the version — that is why it does). Time it. If it takes more than a few minutes or needs someone who is on holiday, fix that before you need it. Every model incident I have seen become a crisis was one where rollback was theoretically possible and had never been tried.

9. Governance, cost & the maturity ladder

Governance: the boring parts that keep you employed

  • Model cards (Chapter 20) for every production version, generated by the training pipeline, stored with the artifact.
  • Audit log. For every prediction that drives a decision: input features, output, model version, timestamp, request id. This is the structured log line in the FastAPI service. Retention period set by legal (often years for credit and health). This log is also what makes the delayed-label performance panel possible — you cannot backfill accuracy for predictions you did not store.
  • PII handling. Features containing personal data are minimised (do you need the full postcode?), pseudonymised where possible, encrypted at rest, and excluded from the monitoring dashboards and experiment tracker (which everyone can see). Hashing an ID is not anonymisation.
  • Access control. Who can promote a model to production? Who can read the audit log? Who can change a threshold? Two-person approval for production promotion is cheap and prevents most "I was just testing" incidents.
  • Model risk tiers. Not every model needs the full treatment. A tiering — Tier 1: automated decisions affecting people or money (credit, pricing, hiring); Tier 2: decisions with a human in the loop; Tier 3: internal analytics — sets the required rigour. A Tier 3 dashboard model needs a JSON log and a schema check; a Tier 1 model needs everything in this chapter plus independent validation.

Cost and latency engineering

Once a model works, the next conversation is about money and milliseconds. The levers, in the order to pull them:

  1. Batch what you can. Moving a decision from real-time to nightly batch reduces cost per prediction by 10–100× and removes the on-call burden. Ask whether the decision truly needs the freshest data.
  2. Batch inside the request. Scoring 256 rows in one predict_proba call costs about the same as scoring one — NumPy and tree libraries are vectorised. Streaming and REST services should accumulate micro-batches (a few ms of waiting) when throughput is high.
  3. Cache. Feature lookups (the slow part of most REST services) and even predictions for entities that change slowly. A five-minute cache on customer features often removes 90% of feature-store reads.
  4. Shrink the model. Fewer trees, lower depth, feature pruning by permutation importance. A 300-tree GBM at depth 6 is rarely better than 150 trees at depth 4 by more than the measurement noise, and it is twice as fast.
  5. Quantise and compile. For neural networks, int8 quantisation cuts memory 4× and latency 2–3× with negligible accuracy loss; ONNX Runtime or TensorRT compiles the graph. For trees, ONNX or Treelite gives 5–10× over Python.
  6. Autoscale on the right signal. Scale on request queue depth or p95 latency, not CPU; set minimum replicas ≥ 2 so a single crash is not an outage.

The maturity ladder — and what you actually need first

At work: what your team actually needs first

If you have one or two models and a small team, do these in this order and stop when it is enough: (1) a train.py that reproduces the model from versioned data with a seed; (2) a JSON experiment log; (3) a packaged bundle with a version-checked loader and a schema; (4) data validation at the input of both training and scoring; (5) a frozen test set and the "not worse than production" test in CI; (6) a weekly drift report and a monthly backfilled performance report by email; (7) a rehearsed rollback. That is Level 1, it fits in a month, and it prevents 90% of the incidents you would otherwise have. Feature stores, canaries and triggered retraining come when the pain of not having them is real and specific.

Quiz

Check your understanding

1. A colleague saved only the fitted GBM estimator (not the pipeline) and re-implemented the scaling in the serving code. Offline AUC is 0.87; production AUC is 0.71. What is the most likely cause?

Re-implementing preprocessing separately is the textbook source of skew. Package the whole pipeline so the same fitted transformers run in both places, and add a skew test that recomputes production features offline.

2. A retention team wants a list of at-risk customers each Monday. Which serving pattern should you choose first?

The inputs exist ahead of time and the decision is weekly, so latency tolerance is days. Batch is the cheapest, simplest and easiest to test. Real-time is justified only when the input exists at request time.

3. PSI for monthly_spend is 0.04 but the KS test p-value is 10−20 on a 50,000-row production sample. What should you do?

With large samples, KS rejects for trivial shifts. PSI 0.04 is well under the 0.10 "investigate" convention. Use PSI (or the KS statistic as an effect size) for alerting.

4. Input drift panels are all green, prediction rates are flat, yet backfilled accuracy for predictions made 30 days ago has dropped from 0.72 to 0.55. What is happening?

Same inputs, different outcomes is the definition of concept drift. No input monitor can see it; only delayed-label performance can, which is why that panel exists despite its lag.

5. A new model version has a higher AUC on the frozen test set. Which rung of the rollout ladder answers "does it improve retention?"

Shadow and canary answer operational questions (does it run, is it stable). Only a properly randomised A/B test on the business outcome answers whether the model is better for the business. AUC is not the business metric.

6. The drift alert fires on monthly_spend (PSI 0.9) the morning after the billing team deployed a change. What is the correct first action?

Retraining on a unit change teaches the model the bug. A drift alert coinciding with an upstream deploy is almost always a pipeline problem. Data first, deploy second, model last.

Exercises

Exercise 21.1 — Make PSI lie

Using the psi function from Section 7, construct a production sample that has the same mean and standard deviation as the reference but a PSI above 0.25 (hint: a mixture of two normals). Then construct one with a visibly different shape but PSI below 0.10 (hint: change only the tails beyond the reference's 1st and 99th percentiles). What does this tell you about relying on a single statistic?

Show answer

A bimodal mixture, e.g. 50% N(85, 5) + 50% N(115, 5), has mean 100 and std ≈ 15.8 but empties the central bins and overfills two others: PSI ≈ 0.3–0.6. Conversely, moving 1% of the mass from the far tails to even further out leaves the ten quantile bins almost unchanged: PSI ≈ 0.01, although the maximum and the mean of the top 1% changed a lot. PSI sees binned proportions and nothing else; monitor summary statistics (mean, std, min/max, null rate) alongside it, and for important features look at the histogram.

Exercise 21.2 — Add a directional test that fails

Train a GradientBoostingClassifier on load_breast_cancer restricted to five features. Write a pytest-style function asserting that increasing mean radius by one standard deviation never increases the predicted probability of "benign" for more than 5% of test rows. Run it. If it fails, inspect the ICE curves (Chapter 20) for the offending rows: is the model wrong, or is your expectation too strict?

Show answer

It typically fails for a few percent of rows: boosted trees are not monotone, and for rows where other features dominate, a small radius change can move the prediction either way by a hair. Two honest fixes: (a) tolerate tiny violations (compare with a tolerance of 0.01 in probability), or (b) enforce the domain knowledge in the model with monotonic_cst in HistGradientBoostingClassifier, which guarantees the direction and makes the test exact. Directional tests are most valuable for encoding what the business knows must be true.

There is no universal answer, but a typical honest audit finds: training reproducible from a notebook only (partial), no experiment log (missing), a pickle with no version check (partial), no input validation (missing), a test set that is regenerated each time (partial), no drift monitoring (missing), rollback = "redeploy last week's container, I think" (missing). The four questions usually get: (a) a customer complains, (b) weeks, (c) unknown, (d) unclear. Each "missing" is a one-to-three-day task from this chapter; ordering them by the answers to (a)–(d) is your MLOps roadmap.

Chapter summary

  • The model is ~5% of an ML system. Data collection, validation, features, serving, monitoring and governance are where production failures live.
  • Reproducibility = seeds + pinned environment + versioned data and code + lineage. An append-only JSON run log gets you most of MLflow's value on day one.
  • Package the whole pipeline in a version-stamped bundle with a loader that refuses library-version mismatches; never unpickle what you didn't produce; use a registry alias so promotion and rollback are metadata changes.
  • Choose the serving pattern by latency tolerance and throughput: batch by default; REST when the input exists only at request time; streaming for continuous high-volume events; edge for no-network or sub-10 ms.
  • An inference service loads the model once, validates inputs with a schema, exposes /health and /ready, and writes a structured log line per prediction — that log is your monitoring data and your audit trail.
  • Training–serving skew and point-in-time leakage are the two feature bugs that destroy offline gains; define features once and test skew.
  • CI for ML = data tests + model tests (threshold, no regression vs production on a frozen set, invariance, direction, latency) + pipeline tests. Continuous training on a schedule comes after.
  • Monitor at three speeds: instant (inputs, predictions, system), delayed (performance, fairness, backfilled by prediction date), structural (versioned reference profile). PSI > 0.25 alerts; p-values do not.
  • Data drift is visible in inputs; concept drift only in delayed labels. A drift alert means "check the data, then the deploy, then the world" — retrain only when the world changed.
  • Roll out via shadow → canary → A/B (by customer, on the business metric) → full; rehearse rollback; build Level 1 before dreaming about Level 2.
