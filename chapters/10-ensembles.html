Ensembles: Forests & Boosting

A single decision tree is a nervous, over-confident expert. A few hundred of them, combined the right way, are the strongest general-purpose models for tabular data that exist. This chapter teaches the two ways to combine them — averaging (random forests) and correcting (gradient boosting) — and how to tune, stack and ship them at work.

Throughout this chapter we will keep one example in mind: a loan-default model at a lender. Each row is a loan application with ~40 features (income, debt-to-income ratio, number of late payments in the last two years, months since the oldest account was opened, employment length, loan purpose, and so on), and the label is whether the borrower defaulted within 12 months. It is the archetypal tabular problem, and the archetypal place where ensembles of trees win.

1. Wisdom of crowds: why averaging works

In Chapter 9 you saw that a fully grown decision tree has low bias and very high variance: it fits the training data perfectly, and a slightly different training set produces a completely different tree. In Chapter 7 you learned that variance is the part of the error that comes from sensitivity to the particular sample you happened to get. Ensembles attack exactly that part.

Explain it like I'm 9

Ask one person to guess how many jelly beans are in a jar and they'll be way off. Ask 200 people and average their guesses, and the average is usually startlingly close — because everyone is wrong in a different direction, and the wrongness cancels out. That only works if the guessers don't all copy each other. A random forest is 200 slightly different jelly-bean guessers who were deliberately shown different parts of the jar.

Figure 10.1 shows the effect on a one-dimensional regression. Each blue line is a fully grown tree trained on a different bootstrap sample of the same 40 noisy points; every one of them is a jagged staircase that chases noise. Their average (orange) is smooth and hugs the true curve. No individual tree was made better. The average is better because the jaggedness is in different places for different trees.

The math (optional): variance of an average of correlated models

Suppose you have B models, each with prediction variance σ² at some input, and any pair of them has correlation ρ. The variance of their average is:

Var( (1/B) ∑b fb(x) ) = ρ σ² + (1 − ρ) σ² / B

Read it in two pieces. (1 − ρ)σ²/B is the part that shrinks as you add models — with independent models (ρ = 0) it goes all the way to zero. ρσ² is the floor: the part of the variance the models share, which no amount of averaging removes. So an ensemble's variance is controlled by two levers: B (how many models: cheap, just compute) and ρ (how correlated they are: the interesting lever). Everything clever in bagging and random forests is a trick to push ρ down without making each tree much worse. Symbols: B = number of models, σ² = variance of one model's prediction, ρ = average pairwise correlation between models' predictions.

Key idea

Ensembles work when the members are accurate enough and diverse. Diversity comes from training on different rows (bootstrap), different columns (random feature subsets), different algorithms (stacking), or different targets (boosting fits each model to what the previous ones got wrong). Averaging clones buys you nothing.

2. Bagging: bootstrap + aggregate

Bagging (Breiman, 1996) is short for bootstrap aggregating. The recipe has two lines:

  1. Bootstrap. Draw n rows from your n-row training set with replacement, B times. Each bootstrap sample has about 63.2% of the unique rows (some appear twice or three times), and leaves out about 36.8% — those left-out rows are called out-of-bag (OOB) for that sample.
  2. Aggregate. Train one model per sample. To predict, average the B outputs (regression) or take a majority vote / average the class probabilities (classification).

Two facts make bagging practical. First, because the trees are independent given the data, you can train them in parallel; n_jobs=-1 in scikit-learn does this. Second, the OOB rows give you an honest error estimate for free: for each row, average the predictions of only the trees that did not see it, then score. With enough trees this is nearly as good as a cross-validated estimate, and costs nothing extra.

Bagging works with any high-variance learner, but it is nearly always used with deep trees, because trees are the model whose variance is worth reducing. Bagging a linear model is pointless — the models barely differ (ρ ≈ 1), so the formula above tells you the average is no better than one of them.

3. Random forests

Bagged trees have a weakness. Suppose one feature is very strong — in the loan example, "number of late payments in the last 24 months". Almost every bootstrap sample will pick it for the root split, and often for the next splits too. The trees end up looking alike; ρ is high; the averaging floor ρσ² is high. Breiman's fix (2001) is deliberately crude: at every split, only let the tree consider a random subset of the features.

That is the whole algorithm: random forest = bagging + random feature subsets at each split. Each tree is grown deep (usually to purity or to a small leaf size) so that its bias is low; the averaging handles the variance. The default subset size is √p for classification and p/3 (or all p) for regression, and it is the one hyperparameter that changes the character of the model.

Out-of-bag error: your free validation set

Set oob_score=True and scikit-learn scores each training row using only the trees that did not see it. On the breast-cancer data below, the OOB accuracy and the held-out test accuracy agree closely. At work this means you can often skip a separate validation split for a forest — although you still need a proper test set, and OOB does not protect you from leakage or time-ordering problems (Chapter 13).

# Random forest with out-of-bag scoring and impurity-based feature importance
import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.ensemble import RandomForestClassifier
from sklearn.model_selection import train_test_split
from sklearn.metrics import accuracy_score

data = load_breast_cancer()
X, y = data.data, data.target
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.25, random_state=42, stratify=y)

rf = RandomForestClassifier(n_estimators=500, max_features="sqrt", min_samples_leaf=1,
                            oob_score=True, n_jobs=-1, random_state=42)
rf.fit(X_tr, y_tr)
print(f"OOB accuracy : {rf.oob_score_:.3f}")
print(f"Test accuracy: {accuracy_score(y_te, rf.predict(X_te)):.3f}")

top = np.argsort(rf.feature_importances_)[::-1][:5]
for i in top:
    print(f"{data.feature_names[i]:<22s} {rf.feature_importances_[i]:.3f}")

Feature importance, and why you should not trust the default one

The feature_importances_ attribute is mean decrease in impurity (MDI): how much Gini or MSE each feature's splits removed, summed over all trees. It is free, and it is misleading in two well-documented ways:

  • It favours high-cardinality features. A continuous column or a column with many unique values offers far more candidate split points, so it gets picked "by chance" more often. A pure noise column with unique values can rank above genuinely useful binary flags.
  • It is computed on training data. A feature that helped the tree memorize noise scores well even though it hurts generalization.

The fix is permutation importance (Chapter 20 covers this and SHAP in depth): shuffle one column of the held-out data, re-score the model, and see how much the metric drops. A feature the model does not actually rely on gives a drop of zero. The block below adds a pure-noise column and a row-ID column to the breast-cancer data: impurity importance ranks the meaningless row ID 19th of 32, ahead of many real measurements, while permutation importance correctly says both junk columns are worthless.

# Impurity importance vs permutation importance on held-out data
import numpy as np, pandas as pd
from sklearn.datasets import load_breast_cancer
from sklearn.ensemble import RandomForestClassifier
from sklearn.inspection import permutation_importance
from sklearn.model_selection import train_test_split

data = load_breast_cancer()
X = pd.DataFrame(data.data, columns=data.feature_names)
rng = np.random.default_rng(0)
X["random_noise"] = rng.normal(size=len(X))   # pure noise
X["row_id"] = np.arange(len(X))               # unique per row, carries no signal
y = data.target
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.3, random_state=0, stratify=y)
rf = RandomForestClassifier(n_estimators=300, random_state=0, n_jobs=-1).fit(X_tr, y_tr)

mdi  = pd.Series(rf.feature_importances_, index=X.columns)
perm = permutation_importance(rf, X_te, y_te, n_repeats=10, random_state=0, scoring="roc_auc")
pi   = pd.Series(perm.importances_mean, index=X.columns)
tbl  = pd.DataFrame({"impurity_rank": mdi.rank(ascending=False).astype(int),
                     "permutation": pi.round(4)})
print(tbl.loc[["worst radius", "mean concave points", "random_noise", "row_id"]])
#                      impurity_rank  permutation
# worst radius                     3       0.0068
# mean concave points              5       0.0027
# random_noise                    31      -0.0001
# row_id                          19       0.0023
Common mistake

Presenting feature_importances_ to stakeholders as "what drives default". It measures how often the trees used a feature, on training data, with a bias toward features that have many distinct values. Customer IDs, timestamps and free-text hashes routinely float to the top. Use permutation importance on held-out data (and SHAP, Chapter 20), and remember that no importance measure is causal.

Why random forests are hard to overfit — and a great first model

A forest's training error is almost always near zero (deep trees memorize), yet its test error is usually good. Adding trees never increases test error — the formula in Section 1 is monotone in B. The remaining risk is that each tree is too wild for very noisy data, which min_samples_leaf tames. Because there is essentially one knob to think about (max_features), no scaling requirement, no sensitivity to monotone transformations, native handling of interactions and a built-in error estimate, the random forest is the model to fit first on any new tabular problem. It tells you within minutes roughly how much signal there is.

At work

My first hour on any new tabular dataset: RandomForestClassifier(n_estimators=300, oob_score=True, n_jobs=-1) inside a pipeline with the minimum preprocessing (Chapter 8), then look at OOB AUC and permutation importances. If OOB AUC is 0.55, you have a data problem, not a modeling problem, and no amount of boosting will save you. If it is 0.99, look for leakage before celebrating. Only then do I reach for gradient boosting.

Extremely randomized trees (ExtraTreesClassifier) push the randomization one step further: instead of searching for the best threshold on each candidate feature, they draw the threshold at random and keep the best of those random cuts. Trees get individually worse but even less correlated, and training is faster because no threshold search happens. On noisy data extra-trees sometimes beat forests; treat them as a one-line alternative worth trying.

4. Boosting: the opposite idea

Bagging builds many independent models in parallel and averages them. Boosting does the reverse: it builds models sequentially, and each new model is trained to fix what the ensemble so far gets wrong. The members are deliberately weak (shallow trees, often called stumps when they have one split), and the ensemble is a weighted sum, not an average. Where bagging reduces variance, boosting reduces bias — it turns a pile of weak models into one strong one.

Explain it like I'm 9

You are painting a portrait with a group of friends, but each friend is only allowed one big brush stroke. The first friend paints the rough shape. The second looks at what is still wrong and paints the biggest missing patch. The third fixes the next-biggest mistake. After fifty strokes the portrait is detailed, even though no single friend could have painted it. That is boosting: every new painter looks only at the leftover mistakes.

Figure 10.4 shows three rounds on a one-dimensional regression. Start with the mean (a flat line). Compute the residuals, y − F0(x): what is left to explain. Fit a stump to the residuals; add it to the ensemble. Recompute residuals, fit another stump, add. Each stump is a laughable model on its own; the sum begins to trace the sine wave.

With depth 1 and learning rate 1.0 the fit jumps in big steps and quickly starts chasing noise; with learning rate 0.1 it needs many more trees but moves smoothly. AdaBoost, in one paragraph

The first practical boosting algorithm, AdaBoost (Freund & Schapire, 1997), does the "focus on the mistakes" step with sample weights rather than residuals: after each round, misclassified rows get their weight increased and correctly classified rows get it decreased, the next stump is trained on the re-weighted data, and each stump's vote in the final sum is proportional to its accuracy. It was a revelation in the late 1990s, and it turns out to be a special case of the general framework below (gradient boosting with exponential loss). At work you will essentially never choose AdaBoostClassifier over a modern gradient-boosting library — but you should recognize the name and the mechanism.

5. Gradient boosting, properly

Friedman's insight (2001) was that "fit the residuals" is a special case of something more general: fit the negative gradient of the loss. Think of the ensemble's prediction for every training row, F(x1), …, F(xn), as a very long vector of parameters. Gradient descent (Chapter 5) would improve the loss by nudging each prediction in the direction of the negative gradient. We cannot nudge predictions directly — we need a function that generalizes to new rows — so we fit a small tree to the negative gradient values and add a shrunken copy of that tree. For squared-error loss the negative gradient is exactly the residual, which is why Figure 10.4 looks like residual fitting. For log-loss on a classifier it is y − p̂: the difference between the label and the current predicted probability.

The math (optional): one boosting round
ri = − ∂L(yi, F(xi)) / ∂F(xi)   (pseudo-residuals)
hm = tree fit to {(xi, ri)}
Fm(x) = Fm−1(x) + η · hm(x)

Symbols: L is the loss (squared error, log-loss, Poisson deviance, …); Fm−1 is the ensemble after m−1 rounds, starting from F0 = a constant (the mean, or the log-odds of the base rate); ri is the negative gradient for row i, which for squared error is simply yi − Fm−1(xi); hm is the new small tree; η (eta, the learning_rate) shrinks its contribution. Modern libraries additionally compute the second derivative and choose each leaf's value as −(∑g)/(∑h + λ), a Newton step regularized by λ, which is where reg_lambda enters.

The knobs and what they really do

learning_rate × n_estimators. The learning rate η scales every tree's contribution. A small η means each tree fixes only a fraction of the current error, so you need more trees to reach the same training fit — but the resulting model generalizes better, because each step is a cautious, averaged-over-many-trees move rather than a lurch. The two parameters trade off almost exactly: halving η roughly doubles the number of trees needed. The practical rule is: pick η small enough (0.03–0.1), then let early stopping choose n_estimators.

Tree depth = interaction depth. A depth-1 stump can only model additive effects: each stump depends on one feature, so the sum is a function of the form f1(x1) + f2(x2) + …. Depth 2 lets the model capture pairwise interactions ("late payments matter more when income is low"), depth 3 three-way interactions, and so on. In practice depth 3–8 (XGBoost) or 15–63 leaves (LightGBM) covers almost all tabular problems; deeper trees overfit and slow everything down.

Subsampling (stochastic gradient boosting). Fitting each tree on a random 50–90% of the rows (subsample) and a random subset of the columns (colsample_bytree) makes the trees more diverse, exactly the bagging trick, and it is faster. It usually improves accuracy slightly and is on by default in most tuned configurations.

Regularization. min_child_weight (XGBoost) or min_child_samples (LightGBM) forbids leaves with too little data, preventing the model from carving out tiny special cases. reg_lambda (L2 on leaf values) shrinks every leaf toward zero, so no single tree can make a big claim; reg_alpha is the L1 version. gamma (XGBoost) / min_split_gain (LightGBM) requires a split to reduce loss by at least that much before it is accepted — a pruning threshold.

Early stopping: the one thing you must always do

Unlike a forest, a boosted model does overfit as you add trees: after some point each new tree is fitting noise in the residuals. Figure 10.5 shows it on the diabetes data: training error falls forever; validation error bottoms out around 30 trees and then climbs. Early stopping watches a validation set during training and stops after the metric has failed to improve for a patience window (early_stopping_rounds, typically 50–100). It then reports the best iteration, which is your n_estimators.

# Gradient boosting with staged_predict to draw the validation curve yourself
import numpy as np
from sklearn.datasets import load_diabetes
from sklearn.ensemble import GradientBoostingRegressor
from sklearn.model_selection import train_test_split
from sklearn.metrics import mean_squared_error

X, y = load_diabetes(return_X_y=True)
X_tr, X_va, y_tr, y_va = train_test_split(X, y, test_size=0.3, random_state=0)

gbr = GradientBoostingRegressor(n_estimators=1000, learning_rate=0.05, max_depth=3,
                                subsample=0.8, random_state=0)
gbr.fit(X_tr, y_tr)

# staged_predict yields the prediction after 1, 2, ..., 1000 trees without refitting
train_rmse = [np.sqrt(mean_squared_error(y_tr, p)) for p in gbr.staged_predict(X_tr)]
val_rmse   = [np.sqrt(mean_squared_error(y_va, p)) for p in gbr.staged_predict(X_va)]
best = int(np.argmin(val_rmse)) + 1
print(f"best n_estimators = {best}")
print(f"val RMSE at best  = {val_rmse[best-1]:.1f}")
print(f"val RMSE at 1000  = {val_rmse[-1]:.1f}   (overfit)")
print(f"train RMSE at 1000= {train_rmse[-1]:.1f}   (memorized)")
# best n_estimators = 29
# val RMSE at best  = 56.7
# val RMSE at 1000  = 64.5   (overfit)
# train RMSE at 1000= 4.1   (memorized)
Key idea

A random forest's n_estimators is a budget: more is safe. A GBM's n_estimators is a regularization parameter: too many overfits. Never hard-code it; set the learning rate, give the model a validation set, and let early stopping find the number of trees. Then, when you retrain on all the data for production, use that number (or ~10% more, since you have slightly more data).

Common mistake

Using the test set as the early-stopping validation set. Early stopping is model selection; the set it watches has influenced the model and can no longer give an unbiased estimate. Split three ways (train / validation-for-early-stopping / test), or use cross-validation with early stopping inside each fold (Chapter 13).

6. The modern libraries

Scikit-learn's GradientBoostingRegressor is the textbook algorithm and is fine for tens of thousands of rows. For anything larger, or anything you will tune seriously, use one of the four implementations below. They all do the same math from Section 5; they differ in how they find splits, how they grow trees, and how they treat categorical columns.

# XGBoost classifier with early stopping on a separate validation split
import xgboost as xgb
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.metrics import roc_auc_score

X, y = load_breast_cancer(return_X_y=True)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.2, random_state=1, stratify=y)
X_fit, X_va, y_fit, y_va = train_test_split(
    X_tr, y_tr, test_size=0.2, random_state=1, stratify=y_tr)

clf = xgb.XGBClassifier(
    n_estimators=2000,          # an upper bound; early stopping picks the real number
    learning_rate=0.05, max_depth=3,
    subsample=0.8, colsample_bytree=0.8, reg_lambda=1.0,
    eval_metric="logloss", early_stopping_rounds=50,
    random_state=1, n_jobs=1)
clf.fit(X_fit, y_fit, eval_set=[(X_va, y_va)], verbose=False)

print("best iteration:", clf.best_iteration)
print(f"val logloss   : {clf.best_score:.4f}")
print(f"test AUC      : {roc_auc_score(y_te, clf.predict_proba(X_te)[:, 1]):.4f}")
# best iteration: 181
# val logloss   : 0.0589
# test AUC      : 0.9944
# LightGBM: same idea, leaf-wise trees, early stopping via a callback
import lightgbm as lgb
from sklearn.datasets import load_breast_cancer
from sklearn.model_selection import train_test_split
from sklearn.metrics import roc_auc_score

X, y = load_breast_cancer(return_X_y=True)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.2, random_state=1, stratify=y)
X_fit, X_va, y_fit, y_va = train_test_split(
    X_tr, y_tr, test_size=0.2, random_state=1, stratify=y_tr)

model = lgb.LGBMClassifier(
    n_estimators=2000, learning_rate=0.05,
    num_leaves=15, min_child_samples=10,          # capacity + regularization
    subsample=0.8, subsample_freq=1, colsample_bytree=0.8,
    verbose=-1, random_state=1, n_jobs=1)
model.fit(X_fit, y_fit, eval_set=[(X_va, y_va)],
          callbacks=[lgb.early_stopping(50, verbose=False)])

print("best iteration:", model.best_iteration_)
print(f"test AUC      : {roc_auc_score(y_te, model.predict_proba(X_te)[:, 1]):.4f}")
# best iteration: 168
# test AUC      : 0.9884
At work

Set n_jobs to your real core count on your own machine (the blocks above use 1 so they run identically anywhere). Save the trained booster with the library's own format (clf.save_model("model.json"), model.booster_.save_model(...)) rather than pickle — it survives version upgrades. And pin the library version in production: split-finding details change between releases and a retrain can silently produce a different model.

7. Tuning a GBM: order of operations

GBMs have a dozen hyperparameters and most of them interact. Tuning all of them at once with a giant grid wastes days. The order below, refined over many projects, gets 95% of the achievable gain in a few hours. Fix a small learning rate first, use early stopping throughout so n_estimators is never a free parameter, and tune capacity before regularization.

StepParameter(s)Sensible rangeWhy in this order
0learning_rate + early stopping0.05–0.1 while tuning; 0.01–0.03 for the final fitFix it so every later comparison is fair. Early stopping sets n_estimators automatically.
1max_depth (XGB) / num_leaves (LGBM)depth 3–8; leaves 15–127Capacity is the biggest lever. Too shallow underfits interactions; too deep overfits and is slow.
2min_child_weight / min_child_samples1–100 (scale with n)The main guard against carving tiny leaves on noisy rows. Tune jointly with step 1.
3subsample, colsample_bytree0.5–1.0 eachAdds diversity and speed. Rarely hurts; 0.8/0.8 is a robust default.
4reg_lambda, reg_alpha, gammaλ 0–10, α 0–1, γ 0–5Fine-tuning. Usually small gains; matters most on small or noisy data.
5Lower learning_rate, re-run early stopping0.01–0.03The final polish: same settings, smaller steps, more trees; typically +0.1–0.5% metric.
6Class weights / objectivescale_pos_weight, custom lossesOnly if the business metric calls for it (see Section 9). Do this last, because it changes what "best" means.

Use random search or a Bayesian optimizer (Optuna is the usual choice; Chapter 13) rather than a grid for steps 1–4: 30–60 random configurations with early stopping beat a 500-point grid. Whatever you search, evaluate with the same cross-validation folds so that differences between configurations are not just fold noise.

Key idea

The learning rate is not something you "tune" — it is a compute budget. Smaller is always at least as good, given enough trees. Set it low enough that you can afford the trees, and let early stopping do the rest.

8. Stacking, blending and voting

Forests average copies of the same algorithm. What if you average different algorithms — a logistic regression, a forest and a GBM — that make different kinds of mistakes? The simplest version is voting (VotingClassifier): average their probabilities (soft voting) or take the majority class (hard voting), with weights you pick by hand. It often gains a little, because a linear model and a tree ensemble disagree in useful ways.

Stacking replaces the hand-picked weights with a second-level model — the meta-learner — that learns how much to trust each base model, possibly differently in different regions. The catch is subtle and important: if you train the base models on the full training set and then feed their training predictions to the meta-learner, the meta-learner sees predictions that are far too good (the forest has memorized the training set) and learns to trust the most overfit model. The fix is out-of-fold (OOF) predictions: split the training data into K folds, and for each fold generate predictions from base models trained on the other K−1 folds. Every training row then has base-model predictions that were made without seeing it. That is what StackingClassifier(cv=5) does for you.

# Stacking three different learners with out-of-fold predictions (sklearn does the folds)
from sklearn.datasets import load_breast_cancer
from sklearn.ensemble import (StackingClassifier, RandomForestClassifier,
                              HistGradientBoostingClassifier)
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.model_selection import train_test_split
from sklearn.metrics import roc_auc_score, log_loss

X, y = load_breast_cancer(return_X_y=True)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.3, random_state=7, stratify=y)

base = [("lr",  make_pipeline(StandardScaler(), LogisticRegression(max_iter=2000))),
        ("rf",  RandomForestClassifier(n_estimators=200, random_state=0)),
        ("hgb", HistGradientBoostingClassifier(max_iter=200, learning_rate=0.05, random_state=0))]
stack = StackingClassifier(estimators=base, final_estimator=LogisticRegression(),
                           cv=5, stack_method="predict_proba")   # cv=5 → out-of-fold predictions

for name, model in base + [("stack", stack)]:
    model.fit(X_tr, y_tr)
    p = model.predict_proba(X_te)[:, 1]
    print(f"{name:<6s} AUC = {roc_auc_score(y_te, p):.4f}   log-loss = {log_loss(y_te, p):.3f}")
print("meta-learner weights on [lr, rf, hgb]:", stack.final_estimator_.coef_[0].round(2))
# lr     AUC = 0.9988   log-loss = 0.057
# rf     AUC = 0.9974   log-loss = 0.092
# hgb    AUC = 0.9969   log-loss = 0.099
# stack  AUC = 0.9988   log-loss = 0.064
# meta-learner weights on [lr, rf, hgb]: [3.65 2.15 2.07]
Explain it like I'm 9

Out-of-fold predictions are like grading a study group fairly. If you ask each friend "how sure are you about question 7?" after they have seen the answer key, everyone says "100%!" and you learn nothing about whom to trust. So you hide the answers for question 7 from each friend while they answer it. Then the friend who is right most often without peeking is the one whose opinion should count most — and that is what the meta-learner works out.

Three practical notes. First, stacking adds the most when the base models are genuinely different (linear + trees + maybe kNN or a neural net), not three GBMs with different seeds. Second, keep the meta-learner simple — a logistic regression or ridge — because it sees only a handful of columns and a complex meta-learner will overfit them. Third, stacking multiplies training and serving cost by the number of base models; at work it earns its keep in competitions and in high-value models (credit, pricing), and rarely in a model that needs to be retrained hourly.

9. Choosing at work, and the classic pitfalls

Why GBMs dominate tabular data

On structured, tabular business data — rows of mixed numeric and categorical columns — gradient-boosted trees have been the best-performing model family since roughly 2014, and repeated benchmarks (and most Kaggle tabular competitions) confirm it still holds against deep learning. The reasons are concrete: trees are invariant to feature scaling and monotone transforms, so they forgive sloppy preprocessing; they model interactions and non-linear thresholds natively, which is how business rules actually look ("if utilization > 80% and account age < 12 months"); they handle missing values by learning a default direction; and boosting drives bias down while early stopping and shrinkage keep variance in check. Neural networks need far more data and care to match this on tables.

When random forests or linear models still win

Reach for a GBM when

You want the best accuracy on ≥ a few thousand rows, you have a validation set for early stopping, and you can afford a tuning loop. Default choice for churn, default, pricing, demand, fraud.

Reach for a random forest when

You need a robust result in ten minutes with no tuning; the data are small or very noisy; you want well-behaved probabilities with min_samples_leaf; or you need OOB estimates without a validation split.

Reach for a linear model when

Rows are few relative to features (text, genomics); the relationship is nearly linear (the GBM will barely beat it and cost 10× more to explain); regulators require coefficients; or you need to extrapolate beyond the training range — trees cannot.

Pitfall 1: silent overfitting with a tiny learning rate and huge trees

A learning rate of 0.001 with depth-12 trees and 20,000 rounds can reach a low validation loss, but each tree is a memorizer and the model is a 20,000-memorizer ensemble that is hypersensitive to distribution shift. The symptom is a validation curve that keeps creeping down forever without a clear minimum, and a production model that degrades in the first month. Prefer shallow trees (depth 3–6) with a moderate learning rate (0.03–0.1) and a firm early-stopping window. If the loss keeps improving past several thousand trees, the model is usually finding leakage, not signal.

Pitfall 2: leakage via target encoding

High-cardinality categoricals (zip code, merchant ID, product SKU) are often target-encoded: replace each category with the mean target of rows in that category (Chapter 8). If you compute those means on the same rows you then train on, each row's own label leaks into its feature, and a GBM — which is superb at exploiting tiny signals — will latch onto it and show a spectacular validation score that evaporates in production. The rule: compute target statistics out-of-fold (the same K-fold trick as stacking), add smoothing toward the global mean for rare categories, or let CatBoost's ordered target statistics do it for you. Any time a GBM jumps from 0.80 to 0.95 AUC after you add one feature, assume leakage until proven otherwise.

Pitfall 3: class imbalance handled by reflex

With 5% positives, the reflex is to set scale_pos_weight = 19 (XGBoost) or class_weight="balanced". That multiplies the gradient of every positive row by 19, which does two things: it shifts the whole probability scale upward (average predicted probability ≈ 17% instead of 4%), and it changes which splits are chosen. It does not reliably improve the ranking quality, as the block below shows — AUC actually drops slightly here. If your business metric is a ranked list or a threshold you will tune anyway (Chapter 13), leave the weights alone, train on log-loss, and choose the threshold afterwards. Use weights when the minority class is so rare that trees never see enough of it to split on, and always re-calibrate the probabilities afterwards.

# Class weighting changes calibration much more than it changes ranking quality
from sklearn.datasets import make_classification
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.model_selection import train_test_split
from sklearn.metrics import roc_auc_score

X, y = make_classification(n_samples=4000, n_features=20, n_informative=8,
                           weights=[0.95, 0.05], random_state=3)
X_tr, X_te, y_tr, y_te = train_test_split(X, y, test_size=0.3, random_state=3, stratify=y)
print(f"positive rate in training data: {y_tr.mean():.3f}")

for cw in [None, "balanced"]:
    m = HistGradientBoostingClassifier(max_iter=300, learning_rate=0.05, early_stopping=True,
                                       validation_fraction=0.2, class_weight=cw, random_state=3)
    m.fit(X_tr, y_tr)
    p = m.predict_proba(X_te)[:, 1]
    print(f"class_weight={cw!s:<9s} trees={m.n_iter_:<3d} AUC={roc_auc_score(y_te, p):.3f} "
          f"mean predicted p={p.mean():.3f}")
# positive rate in training data: 0.055
# class_weight=None      trees=59  AUC=0.882 mean predicted p=0.039
# class_weight=balanced  trees=38  AUC=0.851 mean predicted p=0.167
Explain it like I'm 9

Imagine a teacher who marks every mistake on the rare kind of question as 19 mistakes. The student will start answering "rare kind!" far more often — sometimes wrongly — because being wrong on those hurts so much. Class weights do the same to a model: they make it shout "positive" more often, which is not the same thing as making it better at telling positives from negatives.

At work: the ensemble checklist before shipping
  • Early stopping used a validation set that is not the test set; the final n_estimators is written down.
  • Any target encoding or stacking used out-of-fold statistics; CV folds respect time and groups (Chapter 13).
  • Permutation importances make sense to a domain expert; no IDs or timestamps at the top.
  • Probabilities are calibrated (Chapter 13) if anyone downstream will treat them as probabilities.
  • Library version pinned; model saved in the library's native format; a baseline (logistic regression) is in the same report.

Quiz

Check your understanding

1. You bag 500 trees and the variance of the average is still high. According to Var = ρσ² + (1−ρ)σ²/B, what should you change?

With B = 500 the shrinking term is already tiny; what remains is the floor ρσ². Only decorrelating the trees (random feature subsets, smaller bootstrap samples, extra-trees) lowers that floor.

2. What does gradient boosting fit each new tree to?

Each round computes pseudo-residuals ri = −∂L/∂F(xi), fits a small tree to them, and adds a learning-rate-shrunk copy to the ensemble. For squared error the pseudo-residual is simply y − F(x).

3. Which statement about n_estimators is correct?

Forest averaging is monotone in B. Boosting keeps fitting residual noise, so its validation curve has a minimum — which is why early stopping is mandatory for GBMs.

4. A colleague trains a random forest, a GBM and a logistic regression on the full training set, then trains a meta-model on their training-set predictions. What is wrong?

The forest's training predictions are nearly perfect, so the meta-learner learns to trust it blindly. Out-of-fold predictions (StackingClassifier with cv=5) give the meta-learner honest inputs.

5. You halve the learning rate of a well-tuned GBM and retrain with early stopping. What do you expect?

Learning rate and number of trees trade off almost one-for-one. Smaller steps take more trees but generalize as well or better — the standard "final polish" in the tuning table.

6. The default feature_importances_ of a forest ranks a customer-ID column in the top 10. The most likely explanation is…

Mean-decrease-in-impurity rewards features with many possible split points, computed on training data. A unique ID offers a split for every row. Permutation importance on held-out data will show it is worthless — and you should drop it.

Exercises

Exercise 10.1 — Read the variance formula

With σ² = 1, compare Var of the average for (a) ρ = 0.6, B = 10; (b) ρ = 0.6, B = 1,000; (c) ρ = 0.1, B = 10; (d) ρ = 0.1, B = 1,000. Which change bought more: 100× more trees, or lowering the correlation?

Show answer

(a) 0.6 + 0.4/10 = 0.64. (b) 0.6 + 0.4/1000 ≈ 0.600. (c) 0.1 + 0.9/10 = 0.19. (d) 0.1 + 0.9/1000 ≈ 0.101. Going from 10 to 1,000 trees at ρ = 0.6 gained 0.04; lowering ρ from 0.6 to 0.1 at only 10 trees gained 0.45. Diversity is the lever; tree count just has to be "enough" (a few hundred).

Exercise 10.2 — Tune a GBM in the right order

On load_breast_cancer (or better, a dataset from your job), use HistGradientBoostingClassifier(early_stopping=True, validation_fraction=0.2, learning_rate=0.05). Step 1: try max_leaf_nodes ∈ {7, 15, 31, 63} with 5-fold CV AUC. Step 2: at the best value, try min_samples_leaf ∈ {5, 20, 50}. Step 3: at the best pair, set learning_rate=0.02 and re-run. Record the number of iterations chosen at each step and the CV AUC. Did the last step help, and how much longer did it take?

Show answer

On breast-cancer, expect CV AUC ≈ 0.99 for most settings — the dataset is easy, so differences will be within fold noise (compare against the standard deviation across folds!). The instructive part is that iteration counts roughly double when the learning rate goes from 0.05 to 0.02, and that min_samples_leaf of 20–50 on 455 training rows costs accuracy. On a noisier work dataset, step 1 will typically move AUC by 1–3 points and step 3 by a few tenths.

Exercise 10.3 — At work: the leakage audit

Take a tabular model you or your team have shipped (or the loan-default framing from this chapter). Train a GBM with early stopping and print permutation importances on the validation set. For each of the top 10 features answer, in writing: (1) Is this value known at the moment the prediction is made? (2) Was it derived from the target in any way (target encoding, post-hoc aggregation)? (3) Would a domain expert accept it as a plausible driver? Then remove any feature that fails a question and re-train. How much did the validation metric drop?

Show answer

There is no fixed answer, but a common outcome: one or two features are "future" information (e.g. number of collection calls for a default model — calls happen after default) or are target-derived, the validation AUC drops by 5–15 points when they are removed, and the honest model is the one that will actually work in production. Document the audit — it is the most persuasive artifact you can bring to a model review.

Chapter summary

  • Averaging B models cuts variance to ρσ² + (1−ρ)σ²/B: tree count only has to be "enough"; decorrelation is the real lever.
  • Bagging = bootstrap rows + average deep trees; out-of-bag rows give a free validation estimate.
  • Random forest = bagging + random feature subsets per split. Tune max_features and min_samples_leaf; more trees never hurt. Fit it first on any new table.
  • Impurity feature importance is biased toward high-cardinality features; use permutation importance on held-out data (and SHAP, Chapter 20).
  • Boosting builds trees sequentially, each fit to the negative gradient (residuals) of the ensemble so far, shrunk by the learning rate.
  • For GBMs, n_estimators is a regularization parameter: fix the learning rate, use early stopping on a validation set that is not the test set.
  • Depth = interaction depth (3–8); subsample rows and columns; regularize with min child weight and λ; tune in the order capacity → regularization → lower learning rate.
  • XGBoost, LightGBM, CatBoost and HistGradientBoosting are near-equivalent in accuracy; choose by ecosystem, categorical handling and speed.
  • Stack different model families with out-of-fold predictions and a simple meta-learner; blending is the one-holdout shortcut.
  • Watch for the three pitfalls: tiny-learning-rate/huge-tree overfitting, target-encoding leakage, and reflexive class weighting that distorts probabilities.
